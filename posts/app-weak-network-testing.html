弱网测试：限速、丢包与断网恢复

弱网不是边缘场景，而是主场景

2025 年第三季度，我们给一个日活 80 万的电商 App 做了一次网络质量抽样：2G、3G 与弱 WiFi（信号强度低于 -95dBm）的会话合计占 11.4%，地铁与电梯场景下平均 RTT 超过 900ms 的会话占 6.2%。同一时期，客服工单里和「提交没反应」「点了两次下了两单」相关的条目，占到订单类工单的 38%。

而在测试环境里，这套系统跑在千兆内网加本地 mock 上，接口平均响应 40ms。所有与网络相关的缺陷，在测试阶段一条都复现不出来。

这不是测试不努力，是测试环境的网络太好了。弱网测试要解决的核心问题，是把线上真实存在的坏网络，变成一台可以反复按开关的机器：限速、丢包、抖动、断流都要能被脚本精确控制，并且能被自动化用例断言。做不到可控制、可重复，弱网测试就只是手工点几下，既进不了 CI，也沉淀不成资产。

先把弱网场景列成清单

不要笼统地说「测一下弱网」。我们最终把它固化成六类场景，每一类都有明确参数和对应的业务动作，见下表。这张表是后续所有用例的输入，也是和产品、后端对齐优先级的依据。

场景网络参数重点动作优先级
2G / GPRS下行 40kbps，RTT 500ms，丢包 2%冷启动首屏、登录P1
3G / UMTS下行 384kbps，RTT 200ms，丢包 1%列表翻页、商品详情P0
地铁与电梯RTT 300ms 到 3s 抖动，丢包 5% 到 30%，频繁断流下单、支付结果查询P0
高铁基站切换，RTT 突增到 800ms，短时完全断流订单状态轮询、消息推送P1
跨境链路RTT 200ms 到 400ms，丢包 1% 到 3%登录、支付回调P1
弱 WiFi1Mbps 带宽，20% 丢包，信号 -90dBm图片加载、视频播放P2

几个取舍需要说明。第一，2G 只测登录和首屏，不测完整下单链路，因为真实 2G 用户几乎走不到支付。第二，地铁与电梯的痛点不是慢，而是切换瞬间的请求悬挂，所以重点放在断流那一刻界面是否卡死、恢复后状态是否自洽。第三，跨境链路主要影响登录态与支付回调，300ms 以上的 RTT 会让基于短轮询的结果页直接失效，必须单独验。

用 netem 造一个可复现的弱网

Android 侧的 tc netem 是最贴近真实的方案，因为它作用在内核网卡队列上，TCP 握手、TLS 协商、DNS 解析全部会被影响。前提是设备有 root 权限，模拟器天然满足。我们固定用 Pixel 7、API 34 的 AVD，系统镜像选带 Google APIs 的 x86_64 版本，adb 版本 35.0.2。

bash — 在模拟器上注入弱网
# 1. 模拟器默认已 root，真机需要先解锁并 su
adb root
adb shell getprop ro.product.model   # 确认目标设备

# 2. 查看现有队列，确认网卡名（WiFi 一般是 wlan0，蜂窝是 rmnet_data0）
adb shell tc qdisc show dev wlan0

# 3. 注入：基础时延 300ms + 正态抖动 100ms + 5% 丢包 + 1% 重复 + 乱序
adb shell tc qdisc add dev wlan0 root netem \
  delay 300ms 100ms distribution normal \
  loss 5% 25% \
  duplicate 1% \
  reorder 25% 50%

# 4. 验证：把结果贴进报告
adb shell tc -s qdisc show dev wlan0

参数含义值得逐条记一下。delay 300ms 100ms distribution normal 表示基础时延 300ms、标准差 100ms 的正态抖动，比固定时延更接近真实无线环境。loss 5% 25% 是 5% 随机丢包，后一个数字是相关性，让丢包呈现连片特征，模拟信号衰减而不是均匀噪声。reorder 25% 50% 表示 25% 的包乱序、其中一半与上一个包相关。如果只写 loss 2% 而不加相关性，TCP 靠快速重传就能轻松扛过去，测不出任何问题。

用完必须清理。建议把清理放进 pytest fixture 的 teardown，避免一条用例失败后整台设备长期停在 5% 丢包的状态，把后续用例全部污染。

bash — 恢复原始网络
# 删除根队列即可恢复，重复执行会报 No such file，用 || true 容忍
adb shell tc qdisc del dev wlan0 root 2>/dev/null || true

# 确认已恢复：应该只剩 pfifo_fast 或 noqueue
adb shell tc qdisc show dev wlan0

真机没有 root 时 netem 用不了，有两个替代。一是 Android Studio 模拟器 Extended Controls 的 Cellular 面板，可以选 GPRS、EDGE、UMTS、HSDPA 等预设，参数固定。二是 iOS 的 Network Link Conditioner，需要单独安装 Additional Tools。这两者的缺点是参数不可自定义，适合做冒烟，不适合做回归对比。

代理侧限速：Charles 与 mitmproxy

需要按域名或按接口粒度限速时，代理层更灵活。Charles 的 Throttle 提供 2G、3G、4G 预设，也能自定义带宽、利用率和 MTU，并且可以只对匹配的域名生效。这非常适合「只把图片 CDN 打慢、接口保持正常」这类定向实验，因为用 netem 做不到按域名区分。

mitmproxy 的优势是可以用代码控制，天然能接进 CI。下面这个插件把每个请求延迟 400ms，并让 8% 的请求直接返回 504，用来模拟网关超时。需要清楚它的边界：代理工作在应用层，只能模拟请求级别的失败，做不出真正的 TCP 丢包与乱序，所以它和 netem 是互补关系。

python — mitmproxy 弱网插件
from mitmproxy import http
import random
import time


class WeakNetwork:
    def __init__(self, delay=0.4, fail_rate=0.08):
        self.delay = delay
        self.fail_rate = fail_rate

    def request(self, flow: http.HTTPFlow) -> None:
        time.sleep(self.delay)
        if random.random() < self.fail_rate:
            flow.response = http.Response.make(
                504,
                b"gateway timeout",
                {"Content-Type": "text/plain"},
            )


addons = [WeakNetwork(delay=0.4, fail_rate=0.08)]

启动命令是 mitmdump -s weak_net.py --mode regular@8080。设备侧把 WiFi 代理指向宿主机内网 IP 的 8080 端口，再安装并信任 mitmproxy 的 CA 证书。注意 Android 7 以后用户证书默认不被应用信任，被测包如果不支持 user CA，要么改用 debug 包，要么把证书装进系统证书目录，这一步经常卡住新人半天。

关键指标：首屏、超时率、重试次数

弱网测试如果只断言「页面最终能打开」，等于什么都没测。我们固定采五个指标，每个都有明确口径和阈值，写进用例的断言里。

指标口径采集方式参考阈值
首屏时间冷启动到首帧内容绘制am start -W 的 TotalTime，三次取中位数3G 下 ≤ 2.5s，2G 下 ≤ 5s
请求超时率超时请求数 / 总请求数代理层按耗时与状态码统计≤ 1%
平均重试次数总请求次数 / 业务单数服务端按 client_request_id 聚合≤ 1.2
断网恢复成功率恢复网络后 5s 内数据可用的比例用例断言 + 埋点≥ 99%
重复提交率同一业务产生多单的比例数据库唯一键冲突计数0

首屏时间用 adb shell am start -W 拿 TotalTime 最省事，它的口径是冷启动到首帧绘制完成，和线上 APM 的统计不完全一致，但做版本间对比足够。下面这段脚本在 3G 档位下连续启动三次取中位数，避免单次抖动导致误判。

python — 采集冷启动耗时
import re
import statistics
import subprocess

PACKAGE = "com.demo.app"
ACTIVITY = "com.demo.app/.ui.SplashActivity"


def cold_start_ms(serial: str, rounds: int = 3) -> int:
    values = []
    for _ in range(rounds):
        subprocess.run(
            ["adb", "-s", serial, "shell", "am", "force-stop", PACKAGE],
            check=True,
        )
        out = subprocess.run(
            ["adb", "-s", serial, "shell", "am", "start", "-W", ACTIVITY],
            capture_output=True,
            text=True,
            check=True,
        ).stdout
        match = re.search(r"TotalTime:\s+(\d+)", out)
        if match is None:
            raise RuntimeError(f"未解析到 TotalTime: {out}")
        values.append(int(match.group(1)))
    return int(statistics.median(values))


if __name__ == "__main__":
    print("3G 档冷启动中位数:", cold_start_ms("emulator-5554"), "ms")

超时率不要靠 App 日志猜，最可靠的做法是在代理层统计：记录每个 flow 的耗时与状态码，超过客户端超时阈值的记为一次超时。重试次数只能靠埋点，服务端按 client_request_id 聚合请求次数，再除以业务单数，就得到平均重试次数。这两个指标一升一降，往往能定位到是网络问题还是客户端重试策略写错了。

断网重连与请求重放的正确姿势

先说监听。不要用轮询 isConnected 的方式判断网络，Android 7 以后应该用 ConnectivityManager.NetworkCallback 的 onAvailable 与 onLost，并且用 registerDefaultNetworkCallback 只关心默认网络，否则双卡设备会收到一堆无关回调。

再说重放。重试必须有上限、有退避、有抖动：最多 3 次，间隔按 0.5s、1s、2s 指数增长，再叠加 0 到 300ms 的随机抖动。断网恢复的瞬间，几千个客户端会同时重连，没有抖动就会把网关打出一个尖峰，这一点在压测里也复现过。更关键的是只有幂等请求才允许自动重试：GET、PUT、DELETE 天然幂等，POST 必须携带幂等键，否则重试就是制造重复订单。

python — 带幂等键的退避重试
import random
import time
import uuid

import requests


def submit_order(session: requests.Session, payload: dict,
                 max_attempts: int = 3, timeout: float = 8.0) -> requests.Response:
    payload.setdefault("client_request_id", str(uuid.uuid4()))
    headers = {"Idempotency-Key": payload["client_request_id"]}
    last_error = None
    for attempt in range(max_attempts):
        try:
            resp = session.post(
                "https://api.demo.com/v1/orders",
                json=payload,
                headers=headers,
                timeout=timeout,
            )
            if resp.status_code < 500:
                return resp
            last_error = RuntimeError(f"服务端错误 {resp.status_code}")
        except (requests.Timeout, requests.ConnectionError) as exc:
            last_error = exc
        backoff = min(0.5 * 2 ** attempt + random.uniform(0, 0.3), 4.0)
        time.sleep(backoff)
    raise last_error

还有一点容易漏：页面销毁时要取消重试。用户点了提交、等了两秒没反应就退出去了，后台还在继续重放，等他再进来会看到一个莫名其妙的新订单。取消的实现可以挂 Lifecycle，也可以在 ViewModel 的 onCleared 里置一个 cancel 标志。

弱网下的数据一致性：重复提交与订单幂等

重复提交有三个来源，必须分别测。一是用户在同一按钮上连点两次，客户端防抖只做了 300ms，手指快一点就能穿透。二是请求超时后自动重试，而服务端第一次其实已经写库成功。三是用户从结果页返回上一页再点一次提交。

验证方法很直接：在 30% 丢包下把客户端超时阈值压到 1s，强制触发重试，然后以 120ms 间隔连点两次提交，最后查数据库。正确的实现是订单表对 client_request_id 建唯一索引，重复插入时返回已存在的订单号，客户端按幂等结果处理，直接展示同一单，而不是弹一个失败提示让用户再试。

python — 弱网重复提交断言
import pytest


@pytest.mark.parametrize("loss", ["0%", "30%"])
def test_duplicate_submit_creates_single_order(app, api, loss, set_netem):
    set_netem(loss=loss, delay="400ms")
    app.goto_checkout(sku="A1001", qty=1)
    app.tap_submit_twice(interval_ms=120)
    order_id = app.wait_order_result(timeout=20)
    detail = api.get(f"/v1/orders/{order_id}").json()
    assert detail["item_count"] == 1
    assert detail["status"] == "created"
    request_id = detail["client_request_id"]
    assert api.count_orders(client_request_id=request_id) == 1

除了订单，优惠券领取、点赞、余额提现都是同一个模型。判断要不要做幂等有个简单标准：这个接口被重复调用一次，会不会让用户或公司损失钱与权益。会，就必须有幂等键加数据库唯一约束，而不是只靠前端按钮置灰。

超时与 loading 兜底的验收点

兜底 UI 是弱网体验的最后一道防线，但它最容易被写成「随便加个转圈」。我们把验收点固化成下面八条，每条都能被自动化或人工对照检查。

  • 300ms 内不显示 loading：快网络下转圈一闪而过，比不显示更让人焦虑。
  • 300ms 到 8s 显示骨架屏：骨架屏高度必须和最终内容一致，否则数据回来时会跳一下。
  • 8s 触发第一条提示：文案要说明是网络问题，不能只写「系统繁忙」，后者会让用户以为是服务故障。
  • 15s 切错误页：必须带重试按钮，且重试复用同一幂等键，不能生成新单。
  • 断网时常驻 banner：恢复网络后 1s 内自动消失，不能等到下次打开页面才更新。
  • 只刷新当前可见页：恢复网络时不要把所有后台页面一起刷新，否则会形成并发请求风暴。
  • 支付结果用轮询：间隔 2s、最多 15 次，超时后引导用户去订单列表核对，而不是直接判失败。
  • 按钮状态可复位：请求期间置灰，失败、重试、返回页面后都要能正确恢复可点。

踩坑与边界

症状：在模拟器上注入了 30% 丢包，用例里的接口却几乎不超时。原因：被测 App 走的是蜂窝网卡 rmnet_data0，而命令加在了 wlan0 上，两个网卡完全没有交集。处理：先跑 adb shell ip route 看默认路由走哪张网卡，再决定 qdisc 加在哪。

症状：Charles 限速到 2G 后，页面加载时间几乎没有变化。原因：App 开启了 HTTP/3，QUIC 走 UDP，代理只拦了 TCP，图片实际从 QUIC 通道下完了。处理：测试包临时关闭 QUIC，或在服务端按 UA 回退到 HTTP/2，否则所有代理类限速都会失真。

症状：用飞行模式模拟断网，恢复后 App 直接重启了。原因：飞行模式在某些 ROM 上会触发网络相关的进程重启，而真实地铁隧道只是链路断开，进程不会退出。处理：断网优先用 netem 的 100% 丢包或代理中断，飞行模式只用于补充验证系统级广播。

症状：本地跑得好好的弱网用例，上了 CI 就大面积失败。原因：CI 的 android emulator 跑在容器里，网络经过宿主机 NAT，netem 叠加后时延变成两倍且不可预测。处理：CI 只跑固定预设的限速，精确的 netem 回归留在本地设备或真机集群做。

最后提醒一句：弱网测试的目标不是让 App 在 2G 下也丝滑，而是让它在坏网络下不崩、不重复、不误导用户。把「可接受的降级」写进验收标准，比追求全场景通过更有意义。
