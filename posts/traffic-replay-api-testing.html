把真实流量录成接口测试：Keploy 的录制回放怎么落地

给上线半年的服务补接口测试，最耗时间的通常不是写断言。一条 GET 请求的断言五分钟能写完，真正卡住人的是让它跑起来：它依赖一个数据库、一个缓存、一个第三方支付回调，还有一条消息队列。每个依赖要么搭环境，要么单独做 Mock；服务一多，Mock 的维护成本会超过业务代码。

Keploy 换了个方向：先跑业务，把真实流量录下来，用例和依赖 Mock 一起自动生成。按原文记录，项目 2022 年初开源，Go 编写，Apache-2.0 协议，发文时约 19.8K star，最新版本 v3.7.3，已进入 CNCF Landscape。README 里「帮你做到 90% 测试覆盖率」属于宣传口径，原文也说明这类数字无法核验。

一、写接口测试的时间，最后都花在了哪里

把成本拆开：一是设计用例，二是准备数据，三是搭环境，四是维护。前两项是测试本身的活，后两项是工程负担，而且随服务数量线性增长。一个服务对接五个外部依赖，十个服务就是五十个 Mock，任何一个上游改了返回结构，都要回来改 Mock。

录制回放把「准备数据」和「搭环境」一起省掉了，代价是覆盖上限由录制决定：真实用户没走到的分支，录不到，也就测不到。这不是缺陷，是这类工具必须先说清的前提。

二、eBPF 抓包为什么能做到业务零改造

流量录制不是新概念，差别在抓包位置。Keploy 在网络层用 eBPF 抓内核里流过的流量，不侵入应用：代码一行不改，SDK 一个不装，也不依赖某种语言的 agent 注入。录制时应用照常启动，正常操作页面或打接口，请求、响应以及背后真实的数据库查询都会落进 keploy 目录，一边是用例文件，一边是 Mock 文件。

bash · 录制与回放
# 安装（Linux / macOS / Windows）
source /dev/stdin <<<"$(curl -fsSL https://keploy.io/install.sh)"

# 录制：应用照常启动，正常操作产生流量
keploy record -c "python main.py"

# 回放：重放录制的请求，与录制响应做对比
keploy test -c "python main.py" --delay 10

--delay 10 是给应用启动留的时间。这个参数说明回放是在真实启动应用的前提下进行，只把依赖换成快照，而不是在纯 Mock 层做字符串比对，业务逻辑仍被真实执行。

三、数据库和队列也录成 Mock，回放凭什么离线跑

多数 Mock 工具只管 HTTP 接口，数据库和队列要另想办法。Keploy 录得更深：Postgres、MySQL、MongoDB、Redis 的查询，Kafka、RabbitMQ 的消息，gRPC 与 GraphQL 调用都跟着请求一起录。回放时这些依赖不用启动，应用发出的查询直接命中录制数据，官方把这个能力叫基础设施虚拟化。

对开发者，本地不用再装一整套中间件；对测试，回归不再被环境卡住，录一次可以反复回放，产物也能直接进 GitHub Actions 或 Jenkins。原文提到 Keploy 自己用自己的工具测自己，README 挂着 75% 的自测覆盖率，算一个正面信号，但终究是它自家团队的数据。另一处值得学的设计是覆盖率拆分：开发者看语句与分支覆盖，测试看接口结构与业务场景覆盖，同一份录制产物分别统计。

四、第一次回放大面积失败，先查什么

回放是快照对比，任何每次都变的字段都会判失败：时间戳、随机 ID、自增主键、trace id。第一次跑 test 大面积挂，先别怀疑业务回归，按顺序处理这些不变量，再看差异。

子命令作用什么时候用
record录制真实流量，生成用例与 Mock补测试覆盖的第一步
test回放请求并对比响应本地回归与 CI
test-genAI Agent 从录制与 OpenAPI 文档补边界用例真实流量覆盖不到的边角场景
sanitize对用例中的敏感数据脱敏提交进 Git 之前
templatize / normalize参数化时间戳、随机数等不稳定字段回放误报过多时
export导出为 Postman 集合交给习惯 Postman 的同学

test-gen 由 AI Agent 驱动，从已有录制和 Swagger、OpenAPI 文档里找问题，边界值、缺字段、多字段、类型错误、调用顺序颠倒，找到就补成新用例。它补的是「录制没覆盖的输入组合」，不是替代人工设计业务场景。想看这类自动补用例的边界，可参考从接口文档生成用例的做法，两者思路互补。

五、什么团队不适合用它

第一类是接口还在快速改结构、契约一天一变的服务。录制的用例绑定了当时的请求与响应形态，契约一动，回放产物就腐烂，维护成本并不比手写低。第二类是核心结果依赖外部服务实时返回的流程，把对方响应录成快照后，回放验证的只是「同样的输入我们处理对不对」，验证不了「对方变了我们会怎样」。

第三类是合规压力大的业务。录制产物里会有真实账号、手机号，进 Git 前必须用 sanitize 过一遍，而脱敏规则本身要评审，漏一个字段就是数据事故。第四类是环境太旧的团队：原文给出的要求是 Linux 内核 5.10 以上、macOS Apple Silicon、Windows x86-64，支持 Docker 与 Podman。还有一条要提前问清：核心 CLI 是 Apache-2.0，但 Mock Registry、时间冻结、Console 挂在官方云服务下，用到就得看付费方案。

六、怎么判断它值不值得接

原文的标准很实用：后端服务多、依赖杂的团队值得认真试一次，因为它把成本从写用例挪到了跑业务上，而跑业务本来每天都在发生。落地可分三步：拿一个本地小服务确认 record 与 test 能跑通；脱敏、参数化后进仓库跑一次完整 CI，重点看误报率；最后挑一个真实复杂服务试点，与现有requests 测试脚本并存，比较谁先发现问题。像并发扣库存这类依赖数据库时序的场景，仍要专门设计用例，录制回放补不了。

不装它也能学走思路：流量就是用例，依赖可用录制数据顶替，回放前先处理不稳定字段。对照自己的测试方案，通常能找到几处可省掉的重复劳动。
