把测试经验做成可复用 Skill：八个部件从零搭起

做 AI 测试做久了会陷进一个循环：想让模型写用例或拆 Bug，第一步永远是重新描述背景——什么业务、按什么标准判、输出成什么格式。这次勉强能用，隔天新开会话，同样的指令产出又变了味道；一年攒下的踩坑记录与评审口径，一条都没跟着过去。外链的解法是把这些沉淀成可复用的测试 Skill，并拿消息中心当样板，从目录怎么建讲到怎么验收。

一、提示词管这一次的输出，Skill 管这一类任务的下限

外链里最值得抄走的一句话是：提示词决定这一次的输出，Skill 决定这一类任务的下限。区别不在长短，而在有没有把身份、标准、案例与验收口径钉下来。

维度单条提示词测试 Skill
生命周期用完即弃常驻角色与边界，每次从同一身份出发
质量来源好坏靠运气，人眼验收内置验收口径，先自检再交人
上下文只见当前对话挂着案例库与经验资产，可被检索引用
知识归属留在个人脑子里流程与模板固化，换人不换标准
产出形态格式随模型心情字段固定，产出来就能进流程

外链把最小单位写成公式：system + prompts + cases + workflows + outputs + scoring + templates + assets。八个部件各管一件事，缺哪个，偏科就出在哪个方向。

二、先摆八个分区，再往里填内容

第一步不是写内容，而是摆骨架。目录建错位置、命名不统一，模型就找不到该读哪份文件，这是后面所有问题的根源。

bash · 初始化目录
mkdir -p msg_test_skill/{system,prompts,cases,workflows,outputs,scoring,templates,assets}
cd msg_test_skill
分区职责消息中心至少要放什么
system角色与规矩角色文件加风险优先、边界取值两份原则
prompts任务入口用例生成、故障定位两个入口
cases踩坑记忆重复推送、离线丢失、已读数不一致
workflows执行顺序七步链路加每步产出物
outputs交付格式八列用例表加编号规则
scoring合格标准百分制维度与两档阈值
templates必测清单送达、重连、乱序等勾选项
assets经验资产高危规则库、故障库、日志特征库

三、system、cases、scoring 三块决定产出像不像老手

system 钉死角色与红线。角色写四件事：身份是资深消息通道测试工程师；判断顺序强制固定，先送达与不丢，再顺序与去重，然后延迟与限流、多端同步，最后才是文案与展示兜底；禁止只写发送成功与失败这种二分场景，禁止跳过弱网、断线重连与重复点击；禁止漏掉风险等级和是否需要回归两个字段。验证办法很直接：丢一句「按消息测试角色，分析群消息未读数同步的需求」，它若主动提到乱序、多端已读回写、离线补推，角色才算钉住。

cases 提供踩坑记忆。案例用固定字段记：触发场景、表现、涉及链路、原因概括、回归关注点，再补一段同类风险延伸。入口指令里必须写死一条：出用例前先检索 cases 并标注引用了哪条，否则案例库只是摆设。

scoring 把合格变成可量化。外链给的维度是送达与可靠性 20 分、顺序与去重 20 分、异常与弱网 15 分、历史案例引用 15 分、高敏链路 20 分、判定依据可验证性 10 分。85 分以上直接评审，70 到 84 分补缺口再用，70 分以下推倒重来。产出后追加一句「按评分文件自检，列出扣分项」，比人工逐条挑刺快得多。

四、workflows 与 outputs：让产出能直接进流水线

七步链路是：读需求拆模块、对照风险库定高危点、补边界与异常取值、检索历史案例、产出用例、按评分自检、给出回归建议。每步都有产出物，一步做完再进下一步，模型才不会一口气吐一大坨。

outputs 的价值在字段固定：编号、所属链路、验证场景、前置状态、操作路径、判定依据、优先级、回归标记。编号自定规则，比如 MSG-链路代码-三位序号；优先级按 P0 消息丢失或错乱、P1 主链路不可用、P2 体验与展示来分。字段固定后，导表格、贴用例平台都不用重排。用模型生成用例时最容易丢判定依据与回归标记两列，靠模板反而不会漏。

templates 是勾选表：正常送达、发送失败、断线重连补推、离线拉取、重复推送、乱序到达、多端已读同步、免打扰与折叠、通知权限关闭、弱网与超时。出用例前先输出勾选状态，再逐项展开；模型不会漏项，评审的人只看没勾的几行。

assets 是唯一越用越强的一块。先列高危 Top 5：消息丢失、重复推送、乱序、已读不同步、限流误伤正常用户；再补改动牵连关系：改推送网关要回归离线补推与去重，改已读回写要回归多端同步与未读数。这张表决定了 测试点梳理能不能从改动直接推到风险。

判断一张资产表是不是活的，看一条硬指标：最近一次上线改动有没有对应的新条目。连续三个月没动，说明复盘结论根本没往这落，表只是建了个壳。活的资产表应该随着每次故障复盘长出一两行，一年下来从 5 条长成 40 条才正常。

五、端到端验收、四个高频坑与不适用场景

八个部件填完要跑一次验收：拿一段群消息未读数同步的需求，说「按消息测试角色出用例并自检」。合格产出应含风险清单、勾选表、固定字段用例、自评分数与扣分说明，四样齐全才算能交付。

练手可用一个 45 分钟的缩小版，把文件上传按同样八块填一遍：角色写安全与断点续传，案例放分片丢失与超大文件超时，评分覆盖正常、异常、边界、安全，资产放历史故障与牵连关系。做完跟同事互换目录，同一段需求各跑一遍，谁的产出先过评审一眼可见。

  • 只建空目录。八个文件夹不等于 Skill，每个目录至少一份可执行文件才算立起来。
  • 一次想做全业务。先挑一条重复度最高的链路跑通 1.0，案例与规则慢慢长出来。
  • 资产库不更新。复盘结论不进 assets，用一年还是第一天的水平。
  • 输出不贴现有流程。字段跟用例平台对不上，产出再漂亮也得人工重排。

上面四条坑都偏「人的习惯」，还有一类是「结构没立住」，用下面这段脚本在提交前拦一次：数每个分区有几个可执行文件、模板字段是不是平台认识的名字、评分维度有没有锚点描述。

python · demo_skill_structure_check.py
"""检查测试 Skill 目录结构是否立住，拦住空目录、缺锚点、字段名对不上。

用途：提交或评审前跑一次，输出结构分与具体缺口，避免「目录建了但内容没填」。
依赖：Python 3.9+，仅标准库。
运行：
    python demo_skill_structure_check.py msg_test_skill
    python demo_skill_structure_check.py msg_test_skill --strict --platform-fields case_id,priority
"""

import argparse
import re
import sys
from pathlib import Path

# 八个分区必须各自承担的职责：有可执行文件（非空）才算立住
ZONES = {
    "system": "role",        # 至少一份角色文件
    "prompts": "entry",      # 每个入口都要是文件
    "cases": "case",         # 案例用固定字段记
    "workflows": "flow",     # 七步链路
    "outputs": "template",   # 字段模板
    "scoring": "rubric",     # 评分维度
    "templates": "checklist",# 必测勾选表
    "assets": "knowledge",   # 经验资产
}

# 案例与资产条目的必备字段，缺一个都算没记全
CASE_FIELDS = ["scenario", "symptom", "impact", "cause", "regression"]


def check_zone(dir_path, zone, platform_fields):
    """返回 (得分 0~1, 问题列表)。每个目录至少一个非空文件得 0.5 起。"""
    problems = []
    files = [p for p in dir_path.iterdir() if p.is_file() and p.stat().st_size > 0]
    if not files:
        problems.append(f"{zone}/ 下没有任何非空文件")
        return 0.0, problems

    score = 0.5
    text = "\n".join(p.read_text(encoding="utf-8", errors="ignore") for p in files)

    if zone == "cases":
        # 至少一条案例要带完整字段
        ok_case = any(
            all(re.search(rf"\b{k}\b", seg, re.IGNORECASE) for k in CASE_FIELDS)
            for seg in re.split(r"\n\s*\n|^---$", text, flags=re.MULTILINE)
        )
        if not ok_case:
            problems.append("cases/ 没有一条案例带齐 scenario、symptom、impact、cause、regression")
        else:
            score += 0.3

    if zone == "scoring":
        # 每个维度必须带锚点（1~10 分描述），不能只有维度名
        anchors = re.findall(r"\b\d+\s*分[:：]?\s*\S+", text)
        if not anchors:
            problems.append("scoring/ 维度没有 1~10 分锚点，模型会全打满")
        else:
            score += 0.2

    if zone == "outputs" and platform_fields:
        missing = [f for f in platform_fields if f not in text]
        if missing:
            problems.append(f"outputs/ 缺少平台字段：{', '.join(missing)}")
        else:
            score += 0.2

    if zone == "assets":
        # 资产表应该是「长出来」的，至少 5 行才有复用价值
        lines = [ln for ln in text.splitlines() if ln.strip()]
        if len(lines) < 5:
            problems.append("assets/ 条目不足 5 行，还处在建壳阶段")
        else:
            score += 0.3

    return min(score, 1.0), problems


def main():
    ap = argparse.ArgumentParser(description="测试 Skill 结构检查")
    ap.add_argument("root", help="Skill 目录根路径")
    ap.add_argument("--strict", action="store_true", help="存在任何缺口即以非零码退出")
    ap.add_argument(
        "--platform-fields",
        default="case_id,priority,judge_basis,regression_mark",
        help="平台列头，逗号分隔，用于校验 outputs 是否对得上",
    )
    args = ap.parse_args()

    root = Path(args.root)
    if not root.is_dir():
        print(f"[失败] 目录不存在：{root}")
        return 2

    platform = [f.strip() for f in args.platform_fields.split(",") if f.strip()]
    report = {}
    total = 0.0
    all_problems = []

    for zone, _ in ZONES.items():
        zdir = root / zone
        if not zdir.is_dir():
            report[zone] = {"score": 0.0, "problems": [f"{zone}/ 目录不存在"]}
            all_problems.append(f"{zone}/ 目录不存在")
            continue
        s, probs = check_zone(zdir, zone, platform)
        report[zone] = {"score": s, "problems": probs}
        total += s
        all_problems.extend(probs)

    total = round(total / len(ZONES), 2)
    print(f"结构分：{total} / 1.00")
    for zone, item in report.items():
        mark = "✓" if not item["problems"] else "✗"
        print(f"  {mark} {zone}: {item['score']:.2f}")
        for p in item["problems"]:
            print("    - " + p)

    if total >= 0.8:
        print("\n[结论] 可以进评审")
    elif total >= 0.5:
        print("\n[结论] 补齐缺口再评审，先处理 ✗ 的分区")
    else:
        print("\n[结论] 骨架还没立住，别急着填内容")

    # 严格模式：有任何缺口就非零退出，方便接进 CI 前置检查
    return 1 if (args.strict and all_problems) else 0


if __name__ == "__main__":
    sys.exit(main())

重点看两件事。一是八个分区各自拿了多少分，0.5 起步代表「有内容」，加分项代表「内容立住了」；二是平台字段校验，列头写错一个，产出再漂亮也得人工重排一次。把它接进提交前检查，结构问题就不会再拖到评审现场才暴露。

六、排错清单：产出总是偏，按顺序查哪一块

用了半个月发现产出质量上不去，别从头重写。按八块逐一对照，通常卡点很集中。

症状可能原因验证命令处理方式
用例只有正常与失败两类system 没钉死判断顺序与禁止项把 system 文件原文丢给模型，问「弱网场景你怎么处理」在 system 里写死「先可靠性再异常最后展示」的顺序
案例库从未被引用入口指令没要求先检索 cases看产出里有没有标注引用了哪条在 prompts 入口加「出用例前先检索并标注」的硬性要求
产出字段缺判定依据outputs 模板与用例平台对不上把模板字段列表与平台列头逐一比对按平台字段名改 outputs，别用平台不认识的名字
评分自检走形式scoring 维度太粗，模型全打满手动把一条用例的各维度分数打出来看给每个维度写 1 到 10 分的锚点描述
一次想覆盖全业务范围太大，资产库空转数一数 cases 目录里实际有几个文件砍到一条链路跑通 1.0，再往外扩
资产库一年没更新复盘结论没进 assets 的流程看最近一次复盘的产出物落没落进目录把「复盘必落 assets」写进 workflows 最后一步

七、不适用的场景与判断标准

也有明确不适用的时候：一次性临时任务，为它建八个目录纯属浪费；团队没有复盘机制，assets 会长期空转，Skill 退化成写得比较长的提示词；需求还在剧烈变动，模板与评分维度刚写下就过期。判断标准很简单——这条链路一年要重复很多次、每次判断标准基本一致，才值得沉淀。

它真正的意义不在省下写用例的几十分钟，而在于把判断、踩过的坑、评审口径从「只有你知道」变成「拷个目录就带走」：人走了经验还在，新人不必再靠口口相传。
