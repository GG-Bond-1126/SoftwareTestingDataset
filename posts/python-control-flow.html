Python 控制流：if、for、while 在测试里怎么用

为什么测试脚本里的控制流要单独讲

if、for、while 是最基础的语法，但测试脚本对它们的用法和业务服务不一样。服务代码追求分支完整、每种情况都有兜底；测试脚本追求的是分支可读、失败可定位、任何情况下都不会卡死。同一段 if，写在服务里是防御性编程，写在用例里可能就变成了掩盖问题的开关。

最常见的退化路径是这样的：一开始每条用例都是直线代码，后来要兼容 dev 和 staging 两个环境，加了一层 if；再后来要覆盖三种订单状态，又加了一层 if；某天需要等异步任务完成，写了个 while True；最后这段脚本没人敢改，改一次要重跑两小时。读者画像就是走到第三步、准备把脚本交给团队的一线测试工程师。

下面按「场景—写法—边界」组织。每个模式都给一个反例，说明它在线上会以什么形式崩掉；凡是涉及耗时的数字都标为示例值，需要按你们自己的接口实测。

前置条件与两条约定

本篇的代码需要 Python 3.10 以上，match 语句从 3.10 才进入语法。如果项目还停在 3.8，看到 match 那一节可以先跳过，用文末的映射表方案替代，两者解决的问题是同一个。依赖只需要 pytest，不需要额外库。

第一条约定：控制流只负责选路径，不负责判定通过。用例是否通过由断言决定，失败就让它失败，用 pytest.skip 表达跳过，用 xfail 表达预期失败。把判定写进 if 里再 print 一句，是后面所有假通过问题的源头。

第二条约定：每个循环必须有可证明的退出条件。写完一个 while，先不看循环体，只看条件表达式，能不能说出它在什么情况下会停。说不出来就先补上，再往里写逻辑。

if / elif：按环境分支、按数据分类

测试脚本里 if 的合理用途只有两类：按运行环境切换配置，按数据分类切换断言策略。除此之外的分支，大多可以换成表、换成异常，或者干脆删掉。

环境分支的关键是「收敛」。dev、staging、prod 的 base_url、超时、是否允许写操作都不同，这类判断应该在建会话的阶段做一次，产出一个配置对象，用例里不再出现 if env == ...。如果一百条用例里各写一遍环境判断，新增一个预发环境就要改一百个文件，而且必然漏改几处。

数据分类是真正需要 if 的地方。订单状态 pending 可以取消、paid 不可以，这是业务规则本身，用 if 表达比硬编码更清楚。判断标准是：分支条件来自被测业务，而不是来自你的脚本结构。来自脚本结构的 if，通常意味着职责混在了一起。

滥用边界有两条。第一，不要用 if 决定用例是否算通过，那会让失败在报告里消失。第二，嵌套超过两层就该抽函数：两层 if 说明你在同时处理两个维度，把它拆成「选数据」和「做断言」两个函数，可读性会立刻回来。

python — 环境收敛与按状态分支
import os

# 环境差异收敛成一张表，只在这里出现一次
ENVIRONMENTS = {
    "dev":     {"base_url": "https://dev.api.example.com",  "timeout": (2, 5),  "writable": True},
    "staging": {"base_url": "https://stg.api.example.com",  "timeout": (3, 10), "writable": True},
    "prod":    {"base_url": "https://api.example.com",      "timeout": (5, 20), "writable": False},
}


def load_env() -> dict:
    name = os.getenv("TEST_ENV", "staging")
    if name not in ENVIRONMENTS:
        raise RuntimeError(f"未知环境 {name}，可选值为 {list(ENVIRONMENTS)}")
    return {"name": name, **ENVIRONMENTS[name]}


def assert_cancel_allowed(status: str, resp):
    # 这里的 if 来自业务规则：只有待支付订单可以取消
    if status == "pending":
        assert resp.status_code == 200
        assert resp.json()["data"]["status"] == "cancelled"
    elif status in ("paid", "shipped"):
        assert resp.status_code == 409
    else:
        pytest.skip(f"状态 {status} 不在本用例覆盖范围")

反例：if resp.status_code == 200: print('通过') else: print('失败')。这段代码永远不会让用例失败，报告里全是绿色，线上问题照旧漏出去。判定必须交给断言，打印只用于附加信息。

for 的三类形态

测试里的 for 基本只有三种用途：遍历用例数据、遍历响应或页面里的集合、遍历文件。三种用途的注意点完全不同，混在一起写是复杂度失控的主要原因。

第一类遍历用例数据，首选 pytest.mark.parametrize，而不是在函数里手写 for。parametrize 会把每条数据拆成独立的用例，失败互不影响，报告里能看到具体是哪一组挂了；手写 for 则是一整条用例，第一条失败后面全停，还会掩盖后面的问题。只有在「同一条用例内要对多个对象做同一串操作」时，才值得手写循环。

第二类遍历集合做聚合断言，最大的陷阱是空集合。for 在空列表上会安静地跳过，all([]) 返回 True，any([]) 返回 False，这三件事组合起来，一个返回空数组的接口会被判成通过。所以遍历之前先断言集合非空，或者显式检查长度。

第三类遍历文件，坑在顺序。os.listdir 的返回顺序由文件系统决定，同一份代码在不同机器上可能不同；用例只要隐含依赖顺序，就会出现「本地过、CI 偶发失败」。统一用 sorted() 排序，或者让文件名带零填充的序号。

python — 三类遍历与空集合保护
import pathlib

import pytest

    {"qty": 2, "price_cents": 4999},
    {"qty": 100, "price_cents": 1},
]

def test_create_order(order_client, payload):
    resp = order_client.create(**payload)
    assert resp.status_code == 201


# 2) 集合遍历：先确认非空，再逐项断言
def test_order_items(order_client, order_id):
    items = order_client.detail(order_id).json()["data"]["items"]
    assert len(items) >= 1, "订单明细为空，接口可能返回了空集合"
    for item in items:
        assert item["qty"] > 0, f"明细 {item['sku']} 数量非法"
        assert item["price_cents"] >= 0


# 3) 文件遍历：排序保证顺序稳定
def test_import_all_fixtures(import_client):

    assert files, "fixtures 目录为空，检查测试数据是否随代码一起提交"
    for path in files:
        with path.open("rb") as fh:
            resp = import_client.upload(path.name, fh)
        assert resp.json()["code"] == 0, path.name

while 轮询：超时、间隔与中止条件

异步接口、消息消费、状态机流转，都需要「等某个条件成立」。这类等待是测试脚本里最容易出事的地方：写对了只是多几秒，写错了就是整条流水线卡死，而且日志断在被强杀的那一行，什么线索都没有。

正确写法只有三要素：总超时、轮询间隔、明确的中止条件。总超时用截止时间而不是重试次数，因为按次数算的话，接口变慢时会提前放弃，接口变快时又白等一大截；截止时间则直接表达「最多等多久」，和接口快慢解耦。

为什么不用 while True：它把退出的责任分散到了循环体的每个分支里，只要漏掉一个分支就是死循环，而且新增一个状态时极容易忘记加退出。用 while time.monotonic() < deadline 把退出条件写在抬头，任何人读第一行就知道它一定会停。用 monotonic 而不是 time.time，是为了避开系统时间校准导致的时间跳变。

轮询间隔不要低于一秒。零点几秒的间隔对缩短等待帮助有限，对被测服务却是实打实的压力，尤其在 CI 上并行跑几十条用例时，轮询本身就能把服务打慢。长任务可以退避：间隔从 1 秒逐步涨到 5 秒，但要有上限。超时之后必须抛异常并带上最后看到的状态，不要 return False 让上层去猜。

python — 带截止时间的轮询等待
import time


class WaitTimeout(AssertionError):
    pass


def wait_until(fetch, predicate, timeout=60.0, interval=1.0, desc="条件"):
    """轮询直到 predicate 成立，超时抛异常。

    fetch 无参，返回当前状态；predicate 接收状态返回布尔值。
    """
    deadline = time.monotonic() + timeout
    last = None
    while time.monotonic() < deadline:
        last = fetch()
        if predicate(last):
            return last
        time.sleep(interval)
    raise WaitTimeout(f"等待{desc}超过 {timeout} 秒，最后一次状态：{last!r}")


def test_order_reaches_paid(order_client, order_id):
    state = wait_until(
        fetch=lambda: order_client.detail(order_id).json()["data"]["status"],
        predicate=lambda s: s in ("paid", "failed"),
        timeout=30.0,
        desc="订单进入终态",
    )
    assert state == "paid"

注意 predicate 把失败状态也视为「可以停止」，这样失败会立刻退出而不是傻等三十秒，然后再由断言给出结论。这个细节能把一次失败反馈的时间从半分钟压到一两秒，长跑时非常值得。

break、continue 与循环的 else

break 用于「找到就停」，continue 用于「跳过这一条」，else 用于「循环正常结束才执行」。三者组合起来，可以把重试、查找这类逻辑写成不需要标志变量的形状，代码短一截，正确性也更好验证。

for-else 是最被低估的一个语法。它的语义是：循环没有被 break 打断时执行 else。用来做「在列表里找符合条件的元素，找不到就报错」非常自然，省掉了 found = False 这种标志位，也避免了标志位忘记更新导致的假通过。

边界要记清：break 只跳出最近的一层循环。嵌套两层想一次跳出，要么把内层抽成函数用 return，要么抛一个自定义异常，不要在里层设标志位再到外层判断，那种写法三周后自己都读不懂。

continue 最好写在循环开头做过滤，形成「不满足条件就直接下一条」的节奏。写在循环末尾、再套一层 if 的写法，会让主体逻辑缩进两层，评审时最容易看漏。

python — 重试、过滤与 for-else
import time

# break + else：重试到成功，全部失败才报错
def call_with_retry(client, path, attempts=3, interval=1.0):
    last = None
    for attempt in range(1, attempts + 1):
        last = client.get(path)
        if last.status_code == 200:
            break
        time.sleep(interval)
    else:
        raise AssertionError(f"{path} 连续 {attempts} 次失败，末次状态 {last.status_code}")
    return last


# continue：开头过滤无效数据
def sum_amounts(rows):
    total = 0
    for row in rows:
        if row.get("amount_cents") is None:
            continue
        total += row["amount_cents"]
    return total


# for-else：找元素，找不到就报错
def find_case(cases, case_id):
    for case in cases:
        if case["id"] == case_id:
            return case
    else:
        raise KeyError(f"用例集中不存在 {case_id}")

推导式与生成器表达式的取舍

造数时推导式很诱人，一行就能生成一百个用户。取舍标准只有一条：读代码的人能不能在五秒内说出它产出什么。满足就用，不满足就老老实实写 for 循环，循环不丢人，看不懂的推导式才丢人。

适合推导式的场景：单层、无副作用、条件简单，比如从响应里取出所有失败的用例名。不适合的场景：嵌套两层以上、带函数调用、带副作用。嵌套推导式的执行顺序是从左到右由外到内，和阅读顺序相反，评审时几乎每写必错一次。

生成器表达式适合数据量大或者只需要遍历一次的场景。把它传给批量接口，不会一次性把所有元素堆进内存；但它只能消费一次，调试时 print 一下内容就空了，之后再取长度得到 0。这个特性造成过不少「明明有数据却断言为空」的困惑，遇到就先确认它有没有被提前遍历过。

还有一条硬规矩：推导式里不要调用有副作用的函数。写文件、发请求、改全局状态都不行。一旦出错，堆栈只会指向那一行，你分不清是第几个元素出的问题，排查成本远高于循环里的显式下标。

python — 推导式与生成器的边界
# 适合：单层、无副作用
failed_names = [c["name"] for c in results if c["status"] == "failed"]

# 不适合：嵌套 + 条件 + 函数调用，改成循环更清楚
user_payloads = []
for index in range(100):
    payload = build_user_payload(index)
    if payload["phone"]:
        user_payloads.append(payload)


# 生成器：大数据量批量提交，内存友好
def iter_payloads(total: int):
    for index in range(total):
        yield build_user_payload(index)


def test_bulk_create(bulk_client):
    payloads = iter_payloads(10_000)
    # 只能消费一次：这里不再 len()，也不提前 list()
    resp = bulk_client.create_stream(payloads)
    assert resp.json()["data"]["accepted"] == 10_000

用异常替代大段分支

当分支的判断条件本质是「这一步可能失败」，用 try/except 比写一串 if 更贴近语义，也更容易把错误上下文带出来。典型场景是解析多种格式的响应、可选字段缺失、清理逻辑必须执行。

举一个真实例子：接口返回的时间字段，正常情况下是 ISO 字符串，历史数据里可能是秒级时间戳，还可能是空字符串。用 if 判断要写三种类型检查再各自解析；用 try 依次尝试解析，成功后统一返回 datetime，失败时把原值放进异常信息，代码短且错误信息更准。

取舍也要说清楚：不要用异常做正常流程控制。比如用 KeyError 判断字段是否存在，用 StopIteration 判断遍历结束，这类判断有更直接的写法 dict.get 和 for。异常应该留给「不该发生但可能发生」的事，用多了会掩盖真正的 bug，还会让性能变差。

清理逻辑放 finally，比如关闭临时文件、删除测试账号、还原配置。不要依赖用例末尾的几行代码，因为断言失败时它们根本不会执行，脏数据会留到下一次运行，制造出一批看起来毫不相关的失败。

python — 解析兜底与资源清理
from datetime import datetime, timezone


class FieldParseError(ValueError):
    """字段格式不符合任何已知形态"""


def parse_time(raw):
    if isinstance(raw, (int, float)):
        return datetime.fromtimestamp(raw, tz=timezone.utc)
    if isinstance(raw, str):
        for fmt in ("%Y-%m-%dT%H:%M:%S%z", "%Y-%m-%d %H:%M:%S"):
            try:
                return datetime.strptime(raw, fmt)
            except ValueError:
                continue
    raise FieldParseError(f"无法解析时间字段：{raw!r}")


def test_cleanup_always_runs(account_client):
    account_id = account_client.create(name="qa-temp")["id"]
    try:
        resp = account_client.freeze(account_id)
        assert resp.json()["data"]["status"] == "frozen"
    finally:
        # 断言失败也要还原，避免脏数据污染下一轮
        account_client.delete(account_id)

match：3.10 之后的状态分发

当你要根据「响应的形状」或者「状态机当前处于哪个状态」决定做什么，而且分支数量有限、每个分支做的事情结构相似，match 比 if 链更紧凑。它的强项是解构：可以直接从字典里匹配某个键的值，并顺手把需要的字段绑成变量。

典型用法是对接口返回做分发。支付结果有成功、待确认、失败三种，失败里还带错误码。用 if 要先取字段再逐层判断；用 match 可以一次写清「哪种形状走哪条路」，读起来像一张决策表。

必须记住它不是 switch。match 做的是模式匹配，裸变量名在模式里是「捕获」而不是「比较」，写 case status: 会匹配一切并把值绑到 status，而不是比较它等于某个变量。想比较常量要用点号形式（比如 Status.PAID）或者加 guard，这个坑几乎每个人都会踩一次。

版本边界也要交代：3.9 及以下没有这个语法，团队里只要有一个环境是 3.8，就不能在公共模块里用。替代方案就是下一节的映射表，表达力差一点，但兼容性和可测试性更好。

python — match 处理三种支付结果
def classify_payment(body: dict) -> str:
    match body:
        case {"code": 0, "data": {"status": "paid", "paid_at": str}}:
            return "success"
        case {"code": 0, "data": {"status": "processing"}}:
            return "pending"
        case {"code": 0, "data": {"status": "failed", "error": {"code": err}}}:
            return f"failed:{err}"
        case {"code": int(code)} if code != 0:
            return f"business_error:{code}"
        case _:
            raise AssertionError(f"响应形状不在预期内：{body!r}")

把 if 链重构成映射表

判断信号很明确：一个 if 链超过四个分支，每个分支做的事情结构相同，只是返回不同的值或者调用不同的函数。这时候它本质上是一张表，只是被写成了分支。

重构手法很直接：把「条件值 → 处理函数」写成字典，用一次查表代替整条 if 链。查不到时给默认值或者抛 KeyError 并带上可用键，后者更适合测试脚本，因为拼错状态名会立刻暴露，而不是安静地走到一个兜底分支。

收益有两方面。新增一种状态只改表，不动逻辑，评审 diff 只有一行；表本身也容易被测试覆盖，遍历字典的键就能确认每个分支都有用例。代价是函数签名必须统一，如果各分支参数差异很大，硬塞进一张表反而比 if 更绕，这种情况下抽成策略类或者拆函数更合适。

还有个工程细节：表放在模块级而不是函数内部。放在函数里每次调用都要重建，而且测试时无法直接读取它来做覆盖率校验；放模块级则可以被导入、被断言，也能在收集阶段做一次完整性检查。

python — 从 if 链到映射表
# 重构前：新增状态必须改这段逻辑
def describe_before(status):
    if status == "pending":
        return "待支付"
    elif status == "paid":
        return "已支付"
    elif status == "shipped":
        return "已发货"
    elif status == "refunded":
        return "已退款"
    else:
        return "未知状态"


# 重构后：数据与逻辑分离
STATUS_TEXT = {
    "pending": "待支付",
    "paid": "已支付",
    "shipped": "已发货",
    "refunded": "已退款",
    "cancelled": "已取消",
}


def describe(status: str) -> str:
    try:
        return STATUS_TEXT[status]
    except KeyError:
        raise AssertionError(f"未知订单状态 {status!r}，可用值：{sorted(STATUS_TEXT)}")


def test_all_status_documented():
    # 表本身可测：每个状态都能得到非空描述
    for status in STATUS_TEXT:
        assert describe(status)

常见坑与排查

现象：CI 上的用例跑到一半停住，二十分钟后被平台杀掉，日志末尾没有任何报错。原因：某处写了 while True，等待一个永远不会出现的状态，退出依赖循环体里的 if，而那个 if 的条件写错了字段名。处理：把退出条件提到抬头写成截止时间，等待函数统一封装，禁止在用例里手写无限循环。

现象：遍历删除测试账号时，总有几个账号残留。原因：在遍历列表的同时删元素，索引整体前移，相邻元素被跳过。处理：改为遍历副本 list(accounts)，或者先收集待删 ID，循环结束后统一删除。

现象：接口返回空数组，用例判为通过。原因：for item in items 空转，后面的 all() 又对空集合返回 True。处理：遍历前断言 len(items) >= 1，并在断言信息里说明空集合意味着什么。

现象：同一个筛选逻辑在两条用例里结果不同。原因：其中一条用了嵌套推导式，内层条件依赖外层变量但顺序写反，边界数据上没有报错，只是结果偏了。处理：嵌套超过一层就改成显式循环，边界数据单独写用例。

现象：用例在本地稳定通过，换一台机器必失败。原因：遍历目录用了 os.listdir，顺序依赖文件系统，而用例隐式依赖了导入顺序。处理：统一 sorted()，或者在文件名里带零填充序号。

上线前检查清单

这份清单针对的是「脚本要进 CI 长期跑」这个阶段。每条都对应过真实事故，逐条核对比通读代码更快。

检查项合格标准不做的后果
分支判定通过与否只由断言决定，if 里不 print 结果失败用例显示为通过，缺陷漏出
环境分支环境差异在会话构建时收敛成一份配置新增环境要改几十个文件，必漏改
数据遍历用例数据交给 parametrize 并带业务 id一条失败导致后续数据全不执行
集合断言遍历前断言非空，不依赖 all/any 的空集合语义空响应被判为通过
等待逻辑截止时间 + 间隔 + 中止状态，超时抛异常job 卡死到平台超时，日志无结论
分支规模if 链超过四个分支就改成映射表新增状态靠复制粘贴，重复分支越积越多
清理逻辑资源回收写在 finally 里断言失败后留下脏数据，污染下一轮

最后给一个判断标准：把这段脚本交给三个月后的自己，能不能只看结构就说出「它在什么条件下会停、失败会以什么形式出现」。如果能，控制流就算写清楚了；如果还要逐行推演，那就还没到可以交给团队的程度。
