字节 NL2Test Agent 落地复盘：让 QA 真正用起来

环境搭建

terminal
# 安装 Python 3.10+
python -m venv venv
venv\Scripts\activate
pip install pytest
pytest --version

基础应用：第一个测试用例

python
def test_basic():
    assert 1 + 1 == 2
    print("基础用例通过 ✓")

项目进阶：fixture + 参数化 + CI

python
import pytest

@pytest.fixture
def data():
    return [1, 2, 3, 4, 5]

@pytest.mark.parametrize("n, expected", [(3, 6), (5, 15)])
def test_sum(data, n, expected):
    assert sum(data[:n]) == expected

字节跳动质量保障团队联合复旦大学 CodeWisdom 团队做了一个面向测试自动化的 NL2Test Agent：QA 用自然语言描述测试场景，Agent 自动生成可运行的回归测试用例。相关工作总结被 ISSTA 2026 接收。

比起“又一个大模型用例生成工具”，这篇文章更值得读的是它公开的落地数据和设计取舍。

先看数据：什么叫“跑通了”

指标结果

这几个数字里，最关键的其实是第一个。生成出来不等于用起来，只有当产物能进 CI/CD、能长期回归，才说明它真的嵌入了工作流。

取舍一：不做“替代 QA”，做“用例转译”

他们没有让 Agent 直接完成测试设计，而是选了一个边界清晰、确定性更高的任务：把 QA 用自然语言描述的测试场景，翻译成符合框架规范、可执行的回归用例。

输入输出都有明确约束：QA 负责测试意图和业务判断，Agent 负责代码生成与规范化。这个场景的真实痛点是——QA 基于 App 操作流程写场景不难，难的是识别背后的后端 API 再写接口自动化。Agent 借助测试流量提取相关请求，正好补上这一环。

落地场景的选择原则：任务边界清晰、输入输出可约束、失败可被检测。反过来，「帮我测一下这个需求」这种开放式目标，目前还不适合交给 Agent 闭环。

取舍二：全流程无人干预，比单点准确更重要

用例生成是多阶段流程：请求识别、依赖分析、参数处理、断言生成、代码生成。任何一步需要人工介入修复，效率收益就会被抵消。

所以系统目标不是每一步都最优，而是整条链路容错：结构校验、异常内容丢弃，保证后续阶段能继续执行。哪怕初版用例不够完美，也要先产出可运行结果。

取舍三：能用程序解决的，不交给 LLM

这条最值得抄进自己的方案里。分工原则很明确：

  • LLM 负责：语义理解与模糊判断——业务步骤映射到具体请求、根据测试意图推断预期结果。
  • 程序负责：字段查找、schema 校验、值匹配、请求过滤、参数替换、断言校验。

把模型的不确定性限制在必要范围内，系统才可验证、可维护。

取舍四：把 LLM 任务拆小，小到可以校验

端到端一次生成看起来简单，但出错后无法定位问题环节，前面的错误还会被带到后面放大。做法是拆成多个小任务：请求匹配、依赖关系提取、断言意图识别、受约束代码生成。每次调用只产出一个小的结构化结果，进入下一阶段前完成校验。

取舍五：给模型干净的证据，而不是完整流量

原始测试流量噪声极大：静态资源、轮询请求、重复流量、时间戳、trace id、运行时临时字段。直接塞给模型只会干扰判断。

他们的做法是先治理再调用：过滤无关请求、摘要响应结构、突出候选字段、排除不稳定字段。上下文不是越多越好，而是越相关越好。

取舍六：用 schema 约束输出，而不是靠语气叮嘱

“不要编造字段”“不要生成不存在的变量”——这类自然语言指令并不可靠，模型依然会编。真正有效的做法是给允许集合：合法的请求标识、候选字段、支持的断言类型、已有变量名，输出后继续做约束校验。

超约束的输出不直接接受：只有存在唯一确定性修复方式时才自动修复，否则丢弃。

取舍七：稳定断言优先于断言数量

回归测试里，断言不是越多越好。稳定断言指断言对象与业务结果直接相关、多次执行保持一致、不会因正常运行时变化而波动。否则业务没问题也会误报，团队很快就不信任自动化了。

他们的策略是只对业务相关、可重复验证的字段生成断言；目标缺失或依赖运行时状态的断言直接移除，而不是为了“看起来完整”硬留。

可直接借鉴的落地清单

  1. 先选一个「意图 → 可执行资产」的窄场景，别一上来做开放式测试设计。
  2. 把链路拆成可校验的小步骤，每步都有结构校验和失败兜底。
  3. 明确 LLM 与确定性程序的分工边界，并写进架构文档。
  4. 调用前做上下文治理，调用后做约束校验。
  5. 用「进入 CI/CD 的比例」衡量成功，而不是「生成了多少条」。
