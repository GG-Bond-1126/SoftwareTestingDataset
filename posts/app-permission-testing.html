APP 权限测试：定位 / 相机 / 通知

权限缺陷为什么总在生产上翻车

权限问题的特点是测试环境里几乎不出现，一放量就集中爆发。它不是一个功能，而是一个状态机：同一个定位按钮，在已授予、已拒绝、不再询问、仅此一次、用户在系统设置里改过这几种状态下，表现完全不同，而手工测试通常只走了最顺的那一条。

失败形态也很隐蔽。权限问题很少弹错误框，更多是白屏、按钮点了没反应、永远转圈、推送永远收不到。提交缺陷时如果只写一句「定位用不了」，开发大概率判为无法复现，因为现场已经没了。

这篇写给正在做 App 回归的一线测试，假设你会用 adb 和 Appium，但权限测得不够系统。目标是把权限从「点几下弹窗」变成一张状态矩阵：每格可复现、可复位、失败能自证。

前置条件与环境准备

最低配置是一台 Android 8 以上的真机、一台 iOS 16 以上的真机，加上可用的 adb。Android 8 是通知渠道的分界线，再低的机器测通知权限意义有限。模拟器只能冒烟，权限控制器版本常与真机不一致，国产 ROM 没有对应实现。

测试包要可调试，且权限已在清单里声明，否则 pm grant 会静默失败。另外准备两台能随时清数据的设备：权限弹窗只在「尚未决定」时出现，一旦点过拒绝并勾选不再询问，后续所有请求都不再弹，用例第二天就会集体失效。

把设备语言固定为简体中文。弹窗按钮文案会随系统语言变化，用文案定位的脚本在英文机器上必然失败；同理，CI 里也不要混用不同语言设置的设备。

Android 运行时权限的三态与不可逆状态

Android 6.0 起危险权限改为运行时申请，代码能观察到的只有三态：已授予、已拒绝、已拒绝且不再询问。第三种是坑：用户第二次拒绝同一权限时，系统会自动勾上不再询问，此后 requestPermissions 会立刻回调拒绝，连弹窗都不会出现。很多团队把它当成「弹窗不弹」的 bug 提给开发，其实是系统按设计工作。

版本演进又叠了几层。Android 11 对定位、相机、麦克风引入「仅此一次」，退到后台一段时间后权限被自动收回；Android 12 把定位拆成精确与大致两档；Android 13 把通知变成运行时权限。这三件事意味着，不能用一套弹窗断言覆盖所有 targetSdk。

另一个不可逆状态是系统设置里的用户固定：用户手动关掉某权限后，系统会打上标记，应用再申请同样不弹。从测试角度看，这两种状态必须能主动复位，最可靠的是 pm clear 或重装，只做 revoke 并不保证能清掉标记。

应用侧一般会写成下面这样，测试看到的每一种行为都能从这里推出来：shouldShowRequestPermissionRationale 返回 true，说明还值得解释一次；返回 false 且尚未授权，通常意味着已被固定为不再询问。

kotlin — 应用侧的三态分支
private fun requestCamera() {
    when {
        ContextCompat.checkSelfPermission(this, Manifest.permission.CAMERA)
            == PackageManager.PERMISSION_GRANTED -> openCamera()

        shouldShowRequestPermissionRationale(Manifest.permission.CAMERA) ->
            showRationaleThenRequest()

        else -> requestPermissions(arrayOf(Manifest.permission.CAMERA), REQ_CAMERA)
    }
}

iOS 权限模型：没有不再询问，只有一次机会

iOS 的权限弹窗是单次的。用户点了不允许，这条权限就永久停在拒绝，应用再调用授权接口不会出现任何界面，只能引导用户去设置页手动打开。它没有不再询问的勾选项，因此也不存在「拒绝两次自动不再弹」的行为，把 Android 的三态用例直接搬过去，第二步就会卡住。

几个 iOS 特有差异要单独记：后台定位需要二次确认，即使你声明了始终允许，系统也会单弹一次并给出「稍后询问」；iOS 14 起定位有精确与模糊开关；iOS 14.5 起还有独立的应用跟踪授权弹窗，它不属于系统权限框架，却同样会打断首次启动的主流程。

对自动化最直接的影响是处理方式不同。Android 弹窗是普通系统窗口，可以用 resource-id 点；iOS 弹窗由系统进程托管，不在 App 视图树里，必须走 XCUITest 的中断处理器或 Appium 的 mobile: alert 命令。跨平台脚本到这里必然分叉。

三条时间线：首次授权、二次进入、设置页改完回来

第一条是首次授权：从冷启动走到真正需要权限的功能点，弹窗应该在这时出现。不少 App 一进首页就把定位、相机、通知、通讯录全部申请一遍，用户还没看懂产品是什么就连吃四个框，这是流失率最高的写法，也是合规审查的重点。

第二条是二次进入。权限已经授予，再进同一功能不应出现任何弹窗，功能直接可用。这条回归频率最高，也最容易在版本迭代中被改坏。验证方法是授权后杀进程重开，再走一遍入口，确认没有多余弹窗，也没有短暂的「权限校验中」白屏。

第三条是去系统设置改完权限再回来。这里有两个坑：进程可能在后台被回收，回前台走冷启动，页面状态全部重建；应用往往缓存上次读到的权限结果，回前台不重新检查，于是用户开了权限页面还显示未授权。正确做法是在 onResume 里重读状态，测试时在设置页多停留一会儿。

这条路径要用代码固定下来，否则每次都靠手点太慢。用 adb 直接打开本应用的详情页，比在设置里一层层找菜单稳定；改完之后让应用回到前台，断言它在短时间内同步新状态，而不是继续用缓存。

python — 打开详情页并验证回访
import subprocess

from appium.webdriver.common.appiumby import AppiumBy
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.support.ui import WebDriverWait

PKG = "com.demo.app"


def open_app_detail(udid: str) -> None:
    subprocess.run([
        "adb", "-s", udid, "shell", "am", "start",
        "-a", "android.settings.APPLICATION_DETAILS_SETTINGS",
        "-d", f"package:{PKG}",
    ], check=True)


def assert_state_refreshed(driver) -> None:
    driver.activate_app(PKG)
    WebDriverWait(driver, 8).until(
        EC.presence_of_element_located((AppiumBy.ID, "com.demo.app:id/permission_banner"))
    )

拒绝之后的降级路径怎么设计断言

拒绝后的处理有三种可接受形态：入口禁用并附一行说明、局部降级（定位拿不到就用城市级粗略位置）、引导跳系统设置页。三种都可以，混用也行，唯独不能什么都不做。断言也不同：前两种看页面元素，最后一种看跳转后的包名。

不可接受的是静默失败：点了「获取位置」，转圈三秒回到原页面，没有提示也没有降级，只在 logcat 里留一行被吞掉的异常。断言应该写成「拒绝后 3 秒内出现可读文案或可继续的替代路径」，而不是「页面不崩」。还有一种反模式是反复请求权限，系统不弹框、点击无反应，用户会以为按钮坏了。

用 adb 把权限状态批量摆好

经验上，把权限状态做成用例前置，比让脚本去点弹窗稳得多。系统弹窗的 resource-id、按钮顺序、文案都在变，而 pm 与 appops 是命令行接口，不依赖界面。代价是你绕开了弹窗本身，所以要另外保留少量端到端用例专门验弹窗，否则「弹窗根本没弹」这类问题会被前置脚本掩盖。

pm grant 与 pm revoke 只对危险权限有效，且权限必须已在清单里声明。grant 之后应用申请会直接拿到结果、不弹窗；revoke 之后申请才会重新走弹窗。注意 revoke 改的是授权位，不保证清掉用户固定标记，验证三态时如果结果和真机对不上，先 pm clear 再试。

terminal — 查状态与复位
adb devices
adb shell pm list permissions -g -d                      # 全部危险权限
adb shell dumpsys package com.demo.app | Select-String "granted"
adb shell appops get com.demo.app CAMERA                 # 指定 op 的当前值
adb shell pm clear com.demo.app                          # 授权位与「不再询问」标记一起清掉
terminal — 批量摆状态
$PKG = "com.demo.app"

# 1. 直接授予，不触发弹窗
adb shell pm grant $PKG android.permission.ACCESS_FINE_LOCATION
adb shell pm grant $PKG android.permission.CAMERA

# 2. 撤销，下次申请会重新弹窗
adb shell pm revoke $PKG android.permission.CAMERA

# 3. 用 appops 模拟「拒绝但不弹窗」的中间态
adb shell appops set $PKG CAMERA ignore
adb shell appops set $PKG POST_NOTIFICATION deny

# 4. 确认结果（不同 ROM 的 op 名有差异，先打印再断言）
adb shell appops get $PKG

appops 比 pm 低一层，能表达「忽略」这种中间状态，适合模拟用户拒绝过、但系统仍允许查询的场景。各家 ROM 对 op 名的支持不一致，脚本里先把要用的 op 打印出来确认，别把 CAMERA 写成猜测的 android:camera。

厂商 ROM 与非标准权限

国产 ROM 在 AOSP 之上加了一批非标准权限：自启动、后台弹出界面、悬浮窗、锁屏显示、后台运行、省电策略。它们不在危险权限列表里，pm grant 完全管不到，却直接决定推送能不能到、后台任务会不会被掐、从通知点进来能不能拉起页面。

策略上不要试图全自动化，这些设置页每家路径不同、元素 id 也在变，维护成本高于收益。更现实的做法是主流 ROM 各留一台机器，关键路径手工跑一遍记成矩阵；自动化只检测前置条件，不满足就跳过并标记缺失，而不是判失败。

通知渠道、通知开关与免打扰

Android 8.0 之后每条通知都必须归属一个渠道，能否显示由三层决定：渠道重要性、应用通知总开关、系统免打扰。任何一层关掉，界面上看到的结果都是「没有通知」，但原因完全不同。只断言通知栏有没有卡片，等于把三个变量揉成一个结论。

渠道有两个特性要记住。第一，渠道创建后重要性只能由用户改，代码里再调 setImportance 不会生效，想提升只能新建一个渠道 id，这也是很多团队版本迭代后通知突然变安静的原因。第二，用户关掉应用通知总开关再打开，渠道级设置会被保留。免打扰是系统开关，用例前复位。

terminal — 通知三层检查
# 渠道是否注册、重要性是多少（比看通知栏可靠）
adb shell dumpsys notification --noredact | Select-String "com.demo.app" -Context 8

# 通知总开关
adb shell cmd appops get com.demo.app POST_NOTIFICATION

# 免打扰：0 关闭 / 1 优先 / 2 全部静音 / 3 仅闹钟
adb shell settings get global zen_mode

# 主动投递一条通知，验证通道是否真的通
adb shell cmd notification post -S bigtext -t "订单" tag "订单已创建"

Appium 处理系统弹窗的正确姿势

Appium 有两条路。第一条是在启动能力里加 autoGrantPermissions，会话建立时一次性授予所有危险权限，弹窗不会出现，适合只想测业务功能的回归集，快且稳，但完全覆盖不到弹窗与拒绝路径。第二条是自己定位并点击，适合权限专项集。两套能力应并存，按标记拆分执行。

自己点弹窗的坑集中在三处：Android 11 之后按钮分裂成仅使用时允许、仅此一次、始终允许三套 id，不同版本还会缺其中一个；弹窗宿主进程从 packageinstaller 换成了 permissioncontroller，写死旧包名的脚本会直接找不到元素；iOS 的系统弹窗不在应用上下文里，必须走中断处理器。

python — 多候选 id 依次尝试
import time

from appium.webdriver.common.appiumby import AppiumBy

ALLOW_IDS = (
    "com.android.permissioncontroller:id/permission_allow_foreground_only_button",
    "com.android.permissioncontroller:id/permission_allow_one_time_button",
    "com.android.permissioncontroller:id/permission_allow_button",
)
DENY_ID = "com.android.permissioncontroller:id/permission_deny_button"


def click_allow(driver, timeout: float = 6.0):
    end = time.time() + timeout
    while time.time() < end:
        for rid in ALLOW_IDS:
            for el in driver.find_elements(AppiumBy.ID, rid):
                if el.is_displayed():
                    el.click()
                    print("命中策略", rid)
                    return rid
        time.sleep(0.3)
    print("未找到允许按钮，可能未弹窗或已被 autoGrantPermissions 接管")
    return None

建议维护一组候选 id 按优先级尝试，全部失败再退回文案匹配，无论成败都记一条日志说明命中的策略。否则失败时无法判断是「弹窗没出现」还是「出现了没点到」，这两种情况的处理方向完全相反。

隐私合规检查点

权限测试的另一半是合规，核心是最小必要与场景触发：不能在用户还没使用某项功能时就申请对应权限，不能在隐私政策弹窗出现前收集设备标识，也不能在后台静默读取剪贴板或位置。这些要求落到测试上是可逐条验证的行为，不是一句口号。

静态先看清单：导出安装包里的全部 uses-permission，逐个问它对应哪个功能、在哪个页面申请，答不上来的就是风险项，通讯录、短信、通话记录、精确与后台位置尤其敏感。动态再看首启日志：清数据后冷启动，只停留在首页，抓一段 logcat，看有没有权限请求和设备标识读取的痕迹。

terminal — 静态清点权限
# 需要 Android SDK cmdline-tools，apkanalyzer 在 tools/bin 下
apkanalyzer manifest permissions app-release.apk

# 顺带确认 targetSdk，它决定运行时权限的具体形态
apkanalyzer manifest print app-release.apk | Select-String "targetSdkVersion"

常见坑与排查

症状：本地全过，CI 全挂。原因：CI 设备是英文语言，且没有预置权限状态，弹窗文案与流程都对不上。处理：固定设备语言，用例开头用 adb 把状态摆到明确位置，别指望上一次运行留下的状态。

症状：同一条用例第二次必挂。原因：上次执行残留了不再询问标记，弹窗不再出现。处理：每条用例前 pm clear 或重装，不要依赖 revoke。

症状：断言「去设置」偶发失败。原因：文案匹配命中的是 Toast，一闪而过，page_source 抓不到。处理：改成等待固定元素，或者从 logcat 校验，不要赌时序。

症状：iOS 用例第一次跑就失败。原因：全局能力开了 autoAcceptAlerts，把本该点拒绝的弹窗自动点了允许。处理：拒绝类用例显式关掉该能力，或改用 mobile: alert 精确控制。

上线前检查清单

发版前按下面这张表过一遍，五项全绿再提测。除了 ROM 那一项需要人工核对，其余都能塞进 CI 自动跑。把矩阵写成参数化用例后，新增一个权限只需往列表里添一行。

python — 权限矩阵参数化
PERM_CASES = [
    ("android.permission.ACCESS_FINE_LOCATION", "grant"),
    ("android.permission.ACCESS_FINE_LOCATION", "revoke"),
    ("android.permission.CAMERA", "grant"),
    ("android.permission.CAMERA", "revoke"),
    ("android.permission.POST_NOTIFICATIONS", "grant"),
    ("android.permission.POST_NOTIFICATIONS", "revoke"),
]


@pytest.mark.parametrize("perm, action", PERM_CASES)
def test_permission_path(perm, action, device):
    apply_permission(device.udid, perm, action)
    reach_feature(device, perm)
    assert_no_crash(device)
检查项方法通过标准
启动不申请无关权限清数据冷启动抓 logcat首页停留期间无权限请求
三态路径覆盖pm clear 后分别授权 / 拒绝 / 拒绝两次三条路径表现符合设计
设置页回访改权限后 activate_app3 秒内状态同步，无残留白屏
通知三层dumpsys notification 加 zen_mode渠道存在，重要性符合预期
主流 ROM 非标准权限自启动、后台弹窗手工核对关键路径可用或明确降级
合规清单apkanalyzer 导出权限逐个对场景每个权限都有可指认的触发点
