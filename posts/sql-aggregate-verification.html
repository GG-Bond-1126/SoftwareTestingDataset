项目进阶：并发测试 + 数据一致性

python
import mysql.connector, threading

def deduct(uid, qty):
    c = mysql.connector.connect(host="localhost", user="root", password="test123", database="testdb")
    cur = c.cursor()
    cur.execute("UPDATE products SET stock=stock-%s WHERE product_id=1 AND stock>=%s", (qty, qty))
    c.commit(); cur.close(); c.close()

threads = [threading.Thread(target=deduct, args=(i, 2)) for i in range(10)]
[t.start() for t in threads]
[t.join() for t in threads]

统计接口为什么容易出 Bug

统计接口的坑，几乎都出在「口径」上，而不是计算本身：

  • 时间范围处理不一致：接口按「自然日 00:00-24:00」算，数据库查询时用了 BETWEEN 漏掉了边界那一秒，或者时区没对齐（服务器是 UTC，界面显示的是东八区）；
  • 状态过滤范围不一致：「已支付」到底包不包括「已退款」，开发和测试各理解各的；
  • NULL 值处理：SUM 会把 NULL 直接跳过，但业务上可能期望按 0 处理，结果就悄悄偏了；
  • 分组维度不一致：按「用户」分组还是按「用户+渠道」分组，数字会差很多。

所以测试统计接口，核心动作不是「看一眼数字对不对」，而是先把数据库侧的「基准值」算出来，再跟接口返回值做严格对比，差在哪就追到哪。

GROUP BY + HAVING 基础速通

先用一张小表把语感练出来：

setup.sql — 造一批订单数据
CREATE TABLE orders (
  id INT PRIMARY KEY AUTO_INCREMENT,
  user_id INT NOT NULL,
  amount DECIMAL(10,2) NOT NULL,
  status TINYINT NOT NULL DEFAULT 0,  -- 0 待支付 1 已支付 2 已退款
  paid_at DATETIME NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO orders (user_id, amount, status, paid_at) VALUES
 (1, 10, 1, NOW()),
 (1, 20, 1, NOW()),
 (1, 30, 2, NOW()),      -- 退款
 (2, 50, 1, NOW()),
 (2, 5,  1, NOW());

GROUP BY 是「按某个维度分组」，聚合函数（COUNT/SUM/AVG/MAX/MIN）是「每组算一个数」，两者配合就是统计的主力：

agg1.sql
-- 每个用户，已支付订单的笔数和总金额
SELECT user_id,
       COUNT(*) AS paid_orders,
       SUM(amount) AS total_paid
FROM orders
WHERE status = 1
GROUP BY user_id;

结果：user 1 有 2 笔共 30 元，user 2 有 2 笔共 55 元（退款那笔因为 WHERE status=1 被提前排除了，不参与统计——这正是「口径过滤」的位置）。

WHERE 和 HAVING 到底什么区别

这是面试高频题，也是实际写统计 SQL 时最容易写错的地方。一句话：WHERE 在分组前过滤「行」，HAVING 在分组后过滤「组」。

WHEREHAVING
作用时机分组之前，过滤原始行分组之后，过滤分组结果
能用聚合函数吗不能（比如不能写 WHERE COUNT(*) > 1）能
典型用途「只看已支付订单」 WHERE status = 1「只看下单超过 3 笔的用户」 HAVING COUNT(*) > 3
agg2.sql — WHERE + HAVING 配合
-- 找出"已支付订单笔数 >= 2"的用户
SELECT user_id, COUNT(*) AS paid_orders
FROM orders
WHERE status = 1          -- 先过滤行：只看已支付
GROUP BY user_id
HAVING COUNT(*) >= 2;     -- 再过滤组：只留笔数达标的

测试方法：DB 基准值 vs 接口返回值

假设接口 GET /api/stat/daily 返回「今日成交单数」。验证分三步：

  1. 先算 DB 基准值：直接查库，把「该是多少」先钉死；
  2. 调接口拿返回值；
  3. 严格对比，不一致时按「时间口径→状态口径→分组维度」的顺序排查。
check1.sql — 今天的成交基准值
-- "今天 00:00 起，到现在的已支付订单数"，左闭右开写法，避免边界缝隙
SELECT COUNT(*) AS expected_paid_orders
FROM orders
WHERE status = 1
  AND paid_at >= CURDATE()
  AND paid_at < CURDATE() + INTERVAL 1 DAY;

Python 脚本：调接口 + 查库 + 断言对比

verify_stat_api.py
import requests
import pymysql

def db_expected_paid_orders():
    """直接查库，算出'该是多少'的基准值"""
    conn = pymysql.connect(
        host="127.0.0.1", port=3306,
        user="test_user", password="test_pwd",
        database="shop", charset="utf8mb4",
    )
    try:
        with conn.cursor() as cur:
            cur.execute("""
                SELECT COUNT(*) AS cnt
                FROM orders
                WHERE status = 1
                  AND paid_at >= CURDATE()
                  AND paid_at < CURDATE() + INTERVAL 1 DAY
            """)
            return cur.fetchone()["cnt"]
    finally:
        conn.close()

def api_actual_paid_orders():
    """调被测接口，拿到它返回的统计值"""
    resp = requests.get("http://127.0.0.1:8000/api/stat/daily")
    resp.raise_for_status()
    return resp.json()["paid_orders"]

def main():
    expected = db_expected_paid_orders()
    actual = api_actual_paid_orders()
    print(f"数据库基准值 = {expected}，接口返回值 = {actual}")
    if expected == actual:
        print("✅ 统计一致")
        return 0
    print(f"❌ 不一致，差值 = {actual - expected}")
    print("   排查方向：1) 时区/时间边界  2) status 过滤口径  3) 是否漏算/多算")
    return 1

if __name__ == "__main__":
    import sys
    sys.exit(main())

两个最容易踩的坑

时区没对齐：数据库里存的是 UTC 时间，接口展示和「今天」的判断用的是东八区，两边各自算「今天」，边界能差出 8 小时。写断言前，先确认库里的时间字段到底是哪个时区、接口返回的「今天」又是按哪个时区切的，两边统一口径再比。

NULL 值悄悄漏掉：SUM(amount) 遇到 NULL 直接跳过，不会报错也不会算 0。如果业务上「未支付金额」应该按 0 参与统计，得先做 COALESCE(amount, 0) 再求和，否则汇总值会比真实值偏大（少算了那些 NULL 行对应的「0」）。写统计 SQL 时，先确认参与聚合的字段允不允许为 NULL，不允许就显式处理。
