AI Agent 测试进阶：多步任务、工具调用与状态机

单轮问答的测试相对简单：给输入、看输出。Agent 把这件事复杂化了一个数量级——它要自己决定调哪个工具、传什么参数、失败后要不要重试、什么时候停止。最终答案对了，过程也可能完全错：用错了工具、查了别的租户、重试了六次才碰对。只看最后一句话，这些全都测不出来。

一、Agent 和单轮问答到底差在哪

维度单轮问答Agent测试影响
交互次数1 次模型调用平均 4 到 8 步耗时与成本成倍增长
状态无状态跨步保留上下文与业务状态需要状态机建模
副作用无会写库、发消息、改订单必须 Mock 或使用沙箱
失败模式答案不对选错工具、参数错、死循环、提前终止断言对象从文本变成轨迹
可重复性受采样影响受采样 + 工具返回 + 时序影响必须录制回放

我们测的是一个售后 Agent，支持查订单、改地址、发起退款三类操作。上线前跑 38 条轨迹用例，发现了 11 个问题，其中 7 个是「最终答案看起来对，但中间调了不该调的工具」。这类问题如果只做端到端文本断言，一条都发现不了。

举个具体的例子。用户说「我昨天买的那个耳机要退」，Agent 先调了 search_orders，再用关键词匹配找到订单号，最后调 create_refund。最终回复完全正确。但轨迹里 search_orders 没有带租户参数，实际走了跨租户查询，只是结果恰好只有一条。这种缺陷在文本层是隐形的，在参数层是一眼可见的。

二、轨迹断言的四个层次

轨迹（trajectory）就是 Agent 从收到请求到给出答案之间的完整步骤序列。断言它，建议按四层来写，从粗到细。

  1. 步骤序列：关键工具是否按顺序出现。用子序列断言而不是全等，允许中间有合理的辅助步骤。
  2. 工具参数：必填参数是否存在、取值是否在当前租户范围内、订单号是否与输入一致。
  3. 终止条件：步数是否超上限、是否以 final 动作结束、有没有重复调用同一工具超过阈值。
  4. 终态：业务状态是否到达预期，比如订单状态从 created 变成 refunded，而不只是回复里写了「已退款」。

四层里最容易漏的是第三层。Agent 死循环时往往还在「正常工作」，每步都有输出，日志看起来一切正常，只是账单在涨。终止条件必须显式断言。

第二个容易漏的是参数层。大部分团队只断言「调了 create_refund」，不断言它传的 order_id 是不是用户说的那个。我们遇到过 Agent 把「12345」听成「12354」，因为用户口述时含糊，模型自己补了一位。回复里写着退款成功，实际退的是别人的单。参数断言必须和输入做一致性比对，不能只看工具名。

三、环境与可复现的执行骨架

Agent 测试的第一原则是可控：模型输出可控、工具返回可控、时间可控。做法是把模型换成脚本化的假模型，把工具换成记录器，这样每次运行的轨迹完全一致。

tests/agent/harness.py
from dataclasses import dataclass, field

@dataclass
class Step:
    tool: str
    args: dict
    output: str = ""
    status: str = "ok"

class ScriptedLLM:
    """按预设脚本产出动作，去掉采样带来的不确定性"""
    def __init__(self, script):
        self.script = list(script)
        self.calls = 0

    def next_action(self, messages):
        self.calls += 1
        if not self.script:
            return {"type": "final", "content": "已完成"}
        return self.script.pop(0)

class RecordingToolbox:
    """真实工具替身：记录调用，按配置返回或抛错"""
    def __init__(self, responses=None, failures=None):
        self.responses = responses or {}
        self.failures = failures or {}
        self.calls = []

    def call(self, name, **kwargs):
        self.calls.append(Step(tool=name, args=kwargs))
        if name in self.failures:
            raise self.failures[name]
        return self.responses.get(name, {"ok": True})

def run_agent(llm, toolbox, user_input, max_steps=8):
    steps = []
    for _ in range(max_steps):
        action = llm.next_action([{"role": "user", "content": user_input}])
        if action["type"] == "final":
            return {"steps": steps, "final": action["content"], "stopped": "final"}
        try:
            out = toolbox.call(action["tool"], **action["args"])
            steps.append(Step(action["tool"], action["args"], str(out)))
        except Exception as e:
            steps.append(Step(action["tool"], action["args"], str(e), status="error"))
    return {"steps": steps, "final": None, "stopped": "max_steps"}

骨架里有两个设计值得保留。第一，max_steps 是必填参数而不是默认无限循环，强制每个用例都考虑终止。第二，工具替身默认记录调用而不是直接返回成功，这样即使某个断言写漏了，事后也能从记录里补查。测试数据的隔离同样重要：每个用例使用独立的租户前缀和订单号，跑完即销毁，避免上一个用例的残留状态影响下一个。

四、轨迹断言怎么写

有了可控骨架，断言就是纯 Python。核心是写一个 assert_subsequence，因为 Agent 常会插入一些合理步骤，比如先查用户再查订单，硬要求全等会让用例非常脆。

test_trajectory.py
import pytest

def tools_of(result):
    return [s.tool for s in result["steps"]]

def assert_subsequence(actual, expected):
    it = iter(actual)
    assert all(any(x == e for x in it) for e in expected), \
        f"期望顺序 {expected}，实际 {actual}"

def test_refund_flow():
    llm = ScriptedLLM([
        {"type": "tool", "tool": "get_order", "args": {"order_id": "12345"}},
        {"type": "tool", "tool": "check_refund_policy", "args": {"order_id": "12345"}},
        {"type": "tool", "tool": "create_refund", "args": {"order_id": "12345", "reason": "七天无理由"}},
        {"type": "final", "content": "退款已提交，预计 3 个工作日到账"},
    ])
    box = RecordingToolbox(responses={"get_order": {"tenant": "t-01", "amount": 199}})
    result = run_agent(llm, box, "订单 12345 我要退款")

    assert_subsequence(tools_of(result), ["get_order", "check_refund_policy", "create_refund"])
    assert result["stopped"] == "final"
    assert len(result["steps"]) <= 8

    refund = [s for s in result["steps"] if s.tool == "create_refund"][0]
    assert refund.args["order_id"] == "12345", "退款订单号被改"
    assert "reason" in refund.args

def test_no_write_tool_when_policy_denies():
    llm = ScriptedLLM([
        {"type": "tool", "tool": "get_order", "args": {"order_id": "99999"}},
        {"type": "tool", "tool": "check_refund_policy", "args": {"order_id": "99999"}},
        {"type": "final", "content": "该订单已超过退款期限，无法退款"},
    ])
    box = RecordingToolbox(responses={"check_refund_policy": {"allowed": False}})
    result = run_agent(llm, box, "订单 99999 我要退款")

    assert "create_refund" not in tools_of(result), "策略拒绝后仍调用了写接口"
    assert "无法退款" in result["final"]

第二条用例是关键。很多人只测「能退款」的正向流程，不测「策略拒绝时绝不能写库」。后者才是资损来源，而且它经常发生在模型「热心帮忙」的时候。

写这类用例时，断言要落在「副作用」而不是「文本」。具体做法是让工具替身记录每一次调用，用例结束后检查调用集合里有没有写操作。只要出现过 create_refund、update_address 这类工具，无论回复写得多客气，都判失败。这个口径比读回复可靠得多，也更容易在评审时达成一致。

五、状态机建模与非法转移

Agent 的业务状态要单独建模，不能藏在 Prompt 里。把状态和合法转移列成表，测试用例从表里生成，非法转移单独构造。

当前状态合法转移非法示例
createdpaid、cancelledshipped
paidshipped、refundingcancelled
shippedcompleted、refundingcreated
refundingrefunded、paidshipped
refunded无终态shipped、paid
test_state_machine.py
import pytest

LEGAL = {
    "created": {"paid", "cancelled"},
    "paid": {"shipped", "refunding"},
    "shipped": {"completed", "refunding"},
    "refunding": {"refunded", "paid"},
    "refunded": set(),
}

ILLEGAL = [
    ("created", "shipped"),
    ("created", "refunded"),
    ("shipped", "created"),
    ("refunded", "shipped"),
    ("cancelled", "paid"),
]

def can_transit(src, dst):
    return dst in LEGAL.get(src, set())

@pytest.mark.parametrize("src,dst", ILLEGAL)
def test_illegal_transition_blocked(src, dst, order_service):
    with pytest.raises(ValueError):
        order_service.transition(src, dst)

@pytest.mark.parametrize("src,dst", ILLEGAL)
def test_agent_refuses_illegal_request(src, dst, build_agent, order_service):
    order_service.force_state(src)
    agent = build_agent(tools=order_service)
    reply = agent.run(f"把订单直接从 {src} 改成 {dst}").text
    assert "不支持" in reply or "无法" in reply, \
        f"Agent 未拒绝非法转移 {src} -> {dst}"
    assert order_service.state == src, "非法转移被真实执行"

def test_no_step_skip_in_happy_path(order_service):
    order_service.force_state("created")
    order_service.pay("12345")
    order_service.ship("12345")
    assert order_service.state == "shipped"
    assert "paid" in order_service.history, "跳过了支付状态"

非法转移用例要同时断言两件事：Agent 拒绝，且底层的状态没有被改。只断言回复文本，会出现「嘴上说不行、后台已经改了」的假通过。

六、失败注入：让工具按最坏情况返回

线上工具不会永远成功。超时、返回脏数据、权限拒绝、部分成功、重复提交，这五种情况必须逐个注入。注入点放在工具替身上，不改业务代码。

test_failure_injection.py
import pytest
import socket

class TimeoutError_(Exception):
    pass

SCENARIOS = {
    "timeout": TimeoutError_("tool timeout after 3000ms"),
    "permission": PermissionError("403 scope order:write required"),
    "bad_data": ValueError("response missing field order_id"),
}

@pytest.mark.parametrize("name,error", SCENARIOS.items())
def test_tool_failure_is_handled(name, error):
    llm = ScriptedLLM([
        {"type": "tool", "tool": "get_order", "args": {"order_id": "12345"}},
        {"type": "final", "content": f"查询暂时失败（{name}），请稍后重试"},
    ])
    box = RecordingToolbox(failures={"get_order": error})
    result = run_agent(llm, box, "查订单 12345")

    assert result["steps"][0].status == "error"
    assert result["stopped"] == "final", "工具失败后没有正常收口"
    assert "稍后重试" in result["final"]

def test_retry_is_bounded():
    llm = ScriptedLLM([
        {"type": "tool", "tool": "get_order", "args": {"order_id": "12345"}},
    ] * 12)
    box = RecordingToolbox(failures={"get_order": TimeoutError_("timeout")})
    result = run_agent(llm, box, "查订单 12345", max_steps=8)

    assert result["stopped"] == "max_steps"
    assert len(result["steps"]) == 8, "重试次数未被上限截断"

失败注入的判定重点不是「有没有报错」，而是「报错后有没有收口」。好的 Agent 会在两次重试后给用户明确的失败说明，差的 Agent 会一直重试到步数耗尽，最后返回一段半截话。

还有一种更隐蔽的失败叫「部分成功」。比如改地址时省市区写进去了、详细地址写失败，接口返回 200 但 partial=true。测试必须专门构造这种返回，断言 Agent 不会对用户说「地址已更新」然后就此结束。我们要求它必须识别部分成功并继续补齐，或者明确告知用户哪一部分没成功。

七、录制回放：把不确定变成确定

脚本化假模型适合单测，但真实模型的决策路径需要定期校准，否则测试和线上会越走越远。折中方案是录制回放：线上或预发跑一遍，把模型动作、工具返回、时间戳全部落成 cassette，回归时重放。

replay.py
import json
from pathlib import Path

class CassetteLLM:
    def __init__(self, path):
        self.actions = json.loads(Path(path).read_text(encoding="utf-8"))["actions"]
        self.i = 0

    def next_action(self, messages):
        action = self.actions[self.i]
        self.i += 1
        return action

def record_run(result, path):
    payload = {
        "actions": [{"type": "tool", "tool": s.tool, "args": s.args} for s in result["steps"]]
                   + [{"type": "final", "content": result["final"]}],
        "stopped": result["stopped"],
    }
    Path(path).write_text(json.dumps(payload, ensure_ascii=False, indent=2), encoding="utf-8")

# 回归时
result = run_agent(CassetteLLM("cassettes/refund_12345.json"), box, "订单 12345 我要退款")
assert result["stopped"] == "final"

录制的关键是去掉不稳定字段：时间戳、trace id、随机 id 都要替换成固定值，否则每次 diff 都是噪音。我们规定 cassette 里只保留工具名、参数、业务相关返回，其余全部裁剪。回放让回归从 9 分钟降到 40 秒，也终于能在 CI 里跑。

回放也有边界：它只能验证「同一条路径上逻辑没变」，验证不了「模型是否会选另一条路径」。所以回放用来守回归，脚本模型用来测分支，真实模型每周跑一次用来校准。三者分工明确，不要指望一种手段覆盖全部。

八、成本与步数上限

Agent 的成本是步数的线性函数，而步数服从长尾分布。我们统计过一个改地址场景：中位数 4 步，P95 9 步，最长一次 23 步——那一次是模型把「地址格式不合法」误判成工具故障，反复重试。没有上限，这一单的成本是正常单的六倍。

建议设三道闸：单次任务最大步数 8、单工具最多调用 3 次、单任务 token 上限 12000。任何一道触发都终止并把轨迹写入告警日志。终止不是失败，而是一种正确的兜底行为，测试要断言它确实触发了。

预算要按 P95 而不是均值算。按均值 4 步估成本，实际账单会被长尾拉高 30% 以上。我们的做法是给每个场景单独记步数分布，取 P95 作为容量规划依据，再留 20% 余量。这样即使某天模型状态不好，也不会出现单日成本失控。

九、踩坑与边界

  • 症状：本地轨迹全绿，线上偶尔调错工具。原因：本地用脚本模型，线上是真实模型，决策分布完全不同。处理：每周用真实模型跑一次同样的用例，把差异补进脚本，至少保证关键路径两条都覆盖。
  • 症状：断言步骤全等，用例三天两头红。原因：Agent 会插入合理辅助步骤。处理：改子序列断言，只在关键顺序上做强约束。
  • 症状：回放时结果对不上。原因：工具返回里带时间戳和随机 id，且每次重放都重新生成。处理：录制时归一化，回放时使用冻结时钟。
  • 症状：并发跑用例时状态互相污染。原因：共用同一个沙箱租户和订单号。处理：每个用例生成独立租户前缀，结束即清理，禁止跨用例复用业务主键。
  • 症状：断言全过，但用户投诉「答非所问」。原因：只断言了轨迹和工具，没有断言最终回复是否回答了用户问题。处理：补一层轻量语义检查，比如回复必须提到订单号或金额中的至少一个业务实体。

Agent 测试的核心不是把每一步都写死，而是把「不允许发生的轨迹」钉住：顺序不能反、写操作要有前置检查、失败必须收口、步数必须有上限。这四条守住，剩下的表述差异可以交给抽样。
