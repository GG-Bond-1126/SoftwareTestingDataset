项目进阶：并发测试 + 数据一致性

python
import mysql.connector, threading

def deduct(uid, qty):
    c = mysql.connector.connect(host="localhost", user="root", password="test123", database="testdb")
    cur = c.cursor()
    cur.execute("UPDATE products SET stock=stock-%s WHERE product_id=1 AND stock>=%s", (qty, qty))
    c.commit(); cur.close(); c.close()

threads = [threading.Thread(target=deduct, args=(i, 2)) for i in range(10)]
[t.start() for t in threads]
[t.join() for t in threads]

cur = c.cursor()
cur.execute("SELECT stock FROM products WHERE product_id=1")
assert cur.fetchone()[0] >= 0
print("并发测试通过 ✓")

先回到 ACID：事务到底保证了什么

ACID 四个字母，测试最需要盯住的是两个：

  • 原子性（A）：一组操作要么全成、要么全不做，中间不能「卡在半截」；
  • 持久性（D）：一旦提交了，断电、宕机都拿不走这份数据。

一致性（C）和隔离性（I）是 A 和 D 配合出来的「结果」。所以测试异常恢复场景，核心就一句话：把系统逼进「卡在半截」的状态，再检查数据到底有没有回到一致的样子。

5 种异常场景，逐个拆

① 死锁（Deadlock）

怎么模拟：两个会话按相反顺序锁同一批行。

deadlock.sql
-- 会话 A
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- （此时会话 B 先锁了 id=2）
UPDATE accounts SET balance = balance - 50 WHERE id = 2;  -- 等 B 放锁，卡住

-- 会话 B
START TRANSACTION;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
UPDATE accounts SET balance = balance + 50 WHERE id = 1;  -- 等 A 放锁，卡住
-- 两个都在等对方，MySQL 的 InnoDB 会检测到死锁，主动回滚其中一个，报 1213

验证数据一致性：确认被回滚的那个会话，它的修改一条都没生效，另一个会话的修改正常提交。

deadlock_check.sql
SELECT id, balance FROM accounts WHERE id IN (1, 2);
-- 对照"死锁发生前"的快照，验证最终值是否符合"只保留了成功会话的改动"这一预期

修复/规避：固定加锁顺序（所有会话都先锁小 id），业务层捕获 1213 报错后整体重试。

② 锁等待超时

怎么模拟：一个会话长时间持有行锁不提交，另一个会话去 UPDATE 同一行，超过 innodb_lock_wait_timeout（默认 50s）。

-- 会话 A：持有锁，故意不提交
START TRANSACTION;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
-- （挂起 60 秒，期间不做任何事）

-- 会话 B：50 秒后触发超时
UPDATE accounts SET balance = 0 WHERE id = 1;
-- 报 1205 Lock wait timeout exceeded; try restarting transaction

验证：B 的修改没有生效（它被整体回滚了），A 后续正常提交后数据是符合「只含 A 改动」的状态。

③ 网络断连（客户端侧）

这是测试最该盯的场景：客户端以为「发出去了」，其实连接已经断了，服务端事务可能压根没收到 COMMIT。

sim_crash.sql — 用 KILL 模拟连接中断
-- 会话 A 开了事务、做了修改，但还没提交
START TRANSACTION;
UPDATE accounts SET balance = balance - 200 WHERE id = 1;
-- 此时在另一个会话里直接杀掉 A 的连接：
SELECT CONNECTION_ID(); -- 先拿到 A 的连接号
KILL 那个连接号;
-- A 断开后，InnoDB 会自动把未提交的事务回滚

验证：A 断开后重新查 accounts，200 的扣减应当不存在，数据回到了 KILL 之前。

④ 进程崩溃 / 宕机

思路和网络断连一样——只要没 COMMIT，事务最终都会被回滚。区别在于：已提交的事务必须靠 redo log 的持久性保证「宕机不丢」。验证方法：提交一笔事务 → 立即 kill 掉 mysqld（模拟断电）→ 重启后查这笔数据还在不在。这是「持久性」最硬核的验证手段，建议至少每个版本跑一次。

⑤ 手动 ROLLBACK

最简单的对照组：正常开事务、做修改、显式 ROLLBACK，然后验证修改全部消失。这一步价值在于「确认业务代码里的 ROLLBACK 分支真的被执行了」，而不是写在那里没被触发过。

Python 脚本：模拟网络断连 + 验证回滚

test_disconnect_rollback.py
import pymysql

CONN = dict(host="127.0.0.1", port=3306, user="test_user",
            password="test_pwd", database="shop")

def get_balance(account_id):
    conn = pymysql.connect(**CONN)
    with conn.cursor() as cur:
        cur.execute("SELECT balance FROM accounts WHERE id = %s", (account_id,))
        v = cur.fetchone()[0]
    conn.close()
    return v

def main():
    before = get_balance(1)
    print(f"操作前余额 = {before}")

    # 开一个连接，做修改但不提交
    conn = pymysql.connect(**CONN)
    try:
        with conn.cursor() as cur:
            cur.execute("START TRANSACTION")
            cur.execute("UPDATE accounts SET balance = balance - 200 WHERE id = 1")
            # 故意不 commit，直接模拟"客户端断线/进程被杀"
            cur.execute(f"KILL {conn.open_connection.server_id if hasattr(conn.open_connection, 'server_id') else ''}")  # 占位，下面用更稳的写法
        conn.close()
    except Exception as e:
        print(f"连接过程出现预期内的异常：{e}")

    # 更稳妥的做法：拿到自己的连接号后，从另一个连接执行 KILL
    conn2 = pymysql.connect(**CONN)
    with conn2.cursor() as cur:
        cur.execute("SELECT CONNECTION_ID()")
        my_id = cur.fetchone()[0]
    # （真实脚本里，应该在"开了事务但还没提交"的那个连接上拿到它的 connection_id，再 KILL）

    after = get_balance(1)
    print(f"操作后余额 = {after}")
    assert after == before, f"回滚验证失败：期望 {before}，实际 {after}"
    print("✅ 未提交的事务在连接断开后被正确回滚")

if __name__ == "__main__":
    main()

脚本里 KILL 自己的连接这个动作，实际工程里更常见的做法是：在测试框架里开两个连接，连接 A 负责「做修改但不提交」，连接 B 负责执行 KILL A的connection_id，然后两边都重新查一遍数据对结果。上面代码是思路示意，落地时按这个双连接结构改一版更干净。

生产环境监控建议

  • 把 1213（死锁）、1205（锁等待超时）两类错误码单独打点，出现频次突增往往是并发设计出问题的早期信号；
  • 对「提交后立刻查不到」这类问题，优先怀疑读写分离下读到了延迟的从库，而不是事务本身没提交（下一篇会专门讲主从延迟）；
  • 关键业务表定期跑一遍「业务不变量」校验 SQL（比如「总流入=总流出」），比盯着报错日志更靠前。
