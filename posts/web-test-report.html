Web 自动化测试报告：从「跑通了」到「可汇报」

报告写给谁看：四类读者决定信息层级

很多团队把「有报告」等同于「能汇报」。前者只是流水线多了一步生成 HTML，后者是在发版评审上，你能说清这批改动的风险、哪几条必须修完、和上周比是变好还是变差。我们最初那份 Allure 报告有三百多条用例、二十多个附件，看着体面，却在评审时被三个问题问住——因为它按测试文件平铺，不按人的问题分层。

同一份报告至少有四类读者，他们打开它的目的完全不同；不分层，每一类人都得自己翻找，然后放弃。

读者要回答的问题必须看到的内容缺失的后果
脚本作者断在哪一步，是不是我写错了步骤树、堆栈、失败时的页面与网络请求只能本地复跑，定位靠运气
开发是不是我的改动引入的最小复现路径、接口响应、commit 与构建号被拉进会议逐条解释
老板能不能发，风险多大通过率口径、四类失败计数、与上次对比只能凭感觉拍板
客户验收项过没过，还有哪些已知问题验收项结论、已知问题与影响范围把内部噪音当成质量问题

对应的就是三层结构：顶部摘要只放结论、通过率口径、四类失败计数与环比，老板一屏内就能判断；中部明细按业务域折叠，每条失败带分类和责任人，开发点进去看是不是自己的模块；尾部证据是步骤树、截图、trace 与控制台片段，脚本作者在这里定位。任何一层缺失，就会有一类读者被迫去问别人，报告随即退化成聊天记录里的一个附件。

客户视角最容易被忽略。对外验收时，客户关心的是验收项结论与已知问题清单，不是内部用例编号，更不是「选择器失效」这种脚本细节。给客户的报告要单独裁一份：保留业务语言，去掉内部命名和重试痕迹，否则一次脚本维护会被读成一次线上事故。

一份能汇报的报告必须有的字段

报告最容易缺的不是数据，而是口径。两个团队都说通过率 97%，一个的分母是全部用例，另一个去掉了 skipped 与 xfail，数字一样，含义完全不同。所以字段清单的第一条不是通过率，而是算法：是否包含跳过、是否包含重试后通过、参数化用例算一条还是多条。

字段写到什么程度缺失的后果
用例通过率分子分母定义、是否含重试通过跨团队不可比
失败分类四类计数、Top 条目、待确认占比无法排优先级
耗时分布最慢 10 条及其占总时长比例优化没有靶点
环境与版本浏览器与驱动版本、commit、部署标识别人无法复现
失败现场链接能直接点开的报告锚点或 trace失败无法自证
执行信息触发方式、分支、时区、总耗时无法归档对比

环境信息写到能复现为止。浏览器版本尤其关键，同一个选择器在 Chromium 与 WebKit 下的可见性判断可能不同；测试数据来源也要写清楚，是固定账号、接口现造还是快照恢复，这决定别人能不能重放同一条用例。

版本要写 commit 短哈希或构建号，同一个 3.4.0 可能对应七八次构建，只写版本名回答不了「从哪次开始的」。失败现场链接必须稳定可寻址：报告锚点、trace 文件名、缺陷单号，至少给一样，而不是让人去 artifact 里翻目录。

耗时分布比总耗时有用：总耗时四十分钟听起来尚可，但若其中六条用例占了一半时间，优化对象就非常明确。建议固定输出最慢 10 条及占比。本文出现的耗时与比例均为示例值，用来说明判断方法，不代表任何项目的基准。

失败分类：把「红了」翻译成「谁的活」

通过率只说明挂了多少。两次 92% 的风险可能完全不同：一次是 8 条边缘断言，另一次是 8 条支付主流程全部失败。先分类再谈比例，报告才从统计变成判断；不做分类，报告就只能汇报坏消息，不能用来做决定。

分类典型特征责任人期望时效
产品缺陷断言与需求不符、接口错误码、渲染异常开发当个迭代
脚本问题选择器失效、等待不足、断言写错脚本维护者24 小时内
环境问题服务未就绪、证书过期、依赖 5xx环境负责人按阻塞级别
数据问题账号被锁、库存不足、脏数据破坏前置条件数据负责人当天

这一栏为什么最有价值？因为它把一次失败直接路由到人。没有分类时，每条红色都要先花两轮对话确认「这是不是脚本问题」，一天只处理了五条；有分类后，值班人只需确认或纠正建议值，其余直接进对应人的待办。分类计数还是趋势分析的分母：产品缺陷数在涨说明质量在恶化，环境问题数在涨说明测试环境在退化，应对方式完全不同。

python — 按异常类型给出分类建议
import allure
import pytest
from playwright.sync_api import Error as PlaywrightError
from playwright.sync_api import TimeoutError as PlaywrightTimeout

# 子类必须排在父类前面：TimeoutError 也是 PlaywrightError
RULES = (
    (PlaywrightTimeout, "环境问题"),
    (PlaywrightError, "脚本问题"),
    (AssertionError, "产品缺陷"),
)


@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    report = outcome.get_result()
    if report.when != "call" or not report.failed:
        return

    category = "待确认"
    exc = call.excinfo.value
    for exc_type, label in RULES:
        if isinstance(exc, exc_type):
            category = label
            break
    allure.dynamic.label("failure_category", category)

分类不必全自动，规则给建议值、值班人确认一次，是成本最低的组合。规则表的顺序本身就是逻辑：把父类写在前面，所有超时都会被归成脚本问题，值班人打开一看全是自己的锅，很快就不再相信这套分类，于是又退回纯人工。

还有一种隐蔽做法会把分类彻底搞坏：在 except 里调用 pytest.skip。报告干净了，失败被藏进 skipped，通过率不降反升。只有真正不适用于当前环境的用例才允许跳过，必须写明原因，并单独统计跳过原因。

Allure、pytest-html、自研 HTML：三种方案的取舍

这三种不是新旧替代关系，而是信息密度与维护成本的组合。选错的代价通常不在生成报告那天，而在两个月后：要么没人看，要么维护报告的人跑路。

方案强项短板适合
pytest-html单文件、零依赖、双击即看无层级、无步骤、无趋势本地调试
Allure三层层级、步骤树、趋势图需命令行、需传 history、体积大流水线归档
自研 HTML字段排版可控、可接内部系统渲染层与数据结构要自己维护跨项目聚合
terminal — 三种方案的最小命令对照
# pytest-html：单文件，零额外依赖
pip install pytest-html==4.1.3
pytest tests/ --html=report.html --self-contained-html

# Allure：results 目录 + 命令行渲染
pip install allure-pytest==2.13.5
pytest tests/ --alluredir=allure-results
allure generate allure-results -o allure-report --clean

# 自研：只取结构化原始数据，渲染自己做
pytest tests/ --junitxml=reports/junit.xml

判断可以很直接：只在本地看、寿命不超过一天，pytest-html 完全够；要转发、要归档、要给不写脚本的人阅读，用 Allure；要回答「这个模块三个月的稳定性」、把失败直接推进缺陷系统、给客户裁一份去内部化的版本，才值得自研。三者也能并存，本地拿即时反馈、流水线做归档、自研层只做聚合查询，代价是每次多写一份数据。

自研的隐性成本在第二版。渲染层一旦成为内部工具，需求会不断加进来，两套渲染层的字段口径还会打架。团队小于三人、又没有明确下游消费者时，用 Allure 更划算。

步骤与证据：让失败可以回读

失败信息如果只有断言那一行，读报告的人还得回读代码才知道走到了哪一步。用 with allure.step 把登录、搜索、提交分别包起来，报告里就会出现一棵步骤树，失败节点自动标红，附件挂在对应步骤下，读起来像操作记录而不是堆栈。

步骤名要把参数带进去，例如「以尾号 6688 的账号登录」，比只写「登录」有用得多；但绝不能写密码、token、手机号原文，报告经常被转发到群里。粒度也别切太碎，一个步骤只做一件能一句话说清的事。

证据要有信息量，不要有数量。截图是底线；DOM 片段比整页源码实用，整页 HTML 动辄几 MB；控制台只取失败前后若干行。用 Playwright 时，trace 往往比十张截图更有价值：可离线回放，包含每一步的 DOM 快照、网络请求与控制台输出，代价是体积，建议只对失败用例保留。

python — 失败时收集三类证据
import pathlib

import allure
import pytest


@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    report = outcome.get_result()
    if report.when != "call" or not report.failed:
        return

    page = item.funcargs.get("page")
    if page is None:
        return

    prefix = item.nodeid.replace("/", "_").replace("::", "-")
    allure.attach(
        page.screenshot(full_page=True),
        name=f"{prefix}-01-失败截图",
        attachment_type=allure.attachment_type.PNG,
    )
    block = page.locator("main").first
    html = block.inner_html() if block.count() else page.content()
    allure.attach(
        html[:200_000],
        name=f"{prefix}-02-关键区域DOM",
        attachment_type=allure.attachment_type.HTML,
    )
    logs = item.funcargs.get("console_logs") or []
    allure.attach(
        "\n".join(logs[-200:]),
        name=f"{prefix}-03-控制台",
        attachment_type=allure.attachment_type.TEXT,
    )
    trace = item.funcargs.get("trace_path")
    if trace and pathlib.Path(trace).exists():
        allure.attach.file(str(trace), name=f"{prefix}-04-trace.zip")

附件名必须带序号和用例标识。不带序号，阅读顺序取决于写入时机，排查时容易把两张图看成一条用例；不带用例标识，并行执行会互相覆盖，看到的是别人的页面。踩上这两个坑，会让人开始怀疑报告本身不可信，这比少几张图严重得多。

趋势与波动：连续失败、间歇失败、新增失败

通过率是一个点，趋势才是一条线。失败要拆成三种形态，因为它们对应的动作不同：连续失败，同一条用例连续多次不通过，基本是稳定缺陷或稳定脚本问题，必须当天处理；间歇失败，今天挂明天过，状态翻转或重试后才通过；新增失败，上次通过这次失败，第一优先级是看这次改了什么。

统计要落在原始结果上，而不是最终状态。很多团队用重试插件兜底，报告最终一片绿，间歇失败就此消失；Allure 的结果 JSON 保留每条记录，正好用来区分「一次就过」和「重试才过」。

python — 从历史结果分出三种失败形态
import collections
import json
import pathlib


def load_history(run_dirs):
    history = collections.defaultdict(list)
    for run_dir in run_dirs:
        for path in sorted(pathlib.Path(run_dir).glob("*-result.json")):
            data = json.loads(path.read_text(encoding="utf-8"))
            history[data["fullName"]].append(data["status"])
    return history


def classify(history, streak=3):
    new_fail, streak_fail, flaky = [], [], []
    for name, states in history.items():
        if len(states) < 2:
            continue
        if states[-1] != "passed":
            if all(s != "passed" for s in states[-streak:]):
                streak_fail.append(name)
            elif states[-2] == "passed":
                new_fail.append(name)
        if len(set(states)) > 1:
            flaky.append(name)
    return new_fail, streak_fail, flaky

用 Allure 自带趋势的人会撞上同一个问题：history 不会自动续上，每次 CI 从空目录开始跑，趋势页永远只有一个点。要么用缓存接住上一次的 history，要么从上一份报告 artifact 里解出来。另一个断档来源是标识变化：改函数名、调参数化 id、移动文件，都会让同一条用例在趋势里变成新用例，曲线看上去像新增了一堆。

波动也别忘了量。同一条用例耗时从 800ms 抖到 2400ms，很可能只是环境噪音；但中位数整体抬升就是系统性变慢。判定要带区间，别用单次值下结论。

历史结果存哪里、怎么查询

artifact 解决的是「拿得到」，不解决「查得到」。保留期一过链接全部失效，更回答不了跨运行的问题：这条用例过去十次怎么样、这个模块在变好还是变差、上次同类失败是谁修的。

存储方式能力代价适合
CI artifact原样保存完整报告保留期短、不能查询失败现场
对象存储固定路径长期保存、链接稳定只能按命名约定找按迭代归档
数据库 / 时序表可聚合、可趋势、可看板需要建表与维护稳定性度量

务实做法是两条腿走路：artifact 存完整报告供人点开看现场，数据库只存精简结果供机器查询。字段六列就够：用例标识、状态、耗时、分类、commit、运行编号。量级其实很小，三百条用例、每天八次运行、一年约八十八万行（示例值），单机 sqlite 完全够用，没必要一上来就上大数据栈。

python — 结果落库与按用例查询
import sqlite3
from datetime import datetime, timezone

DDL = """
CREATE TABLE IF NOT EXISTS results (
    run_id      TEXT NOT NULL,
    commit_sha  TEXT,
    case_id     TEXT NOT NULL,
    status      TEXT NOT NULL,
    category    TEXT,
    duration_ms INTEGER,
    created_at  TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_case ON results (case_id, created_at);
"""


def connect(path="reports/history.db"):
    conn = sqlite3.connect(path)
    conn.executescript(DDL)
    return conn


def save_run(conn, run_id, commit_sha, records):
    now = datetime.now(timezone.utc).isoformat(timespec="seconds")
    conn.executemany(
        "INSERT INTO results VALUES (?, ?, ?, ?, ?, ?, ?)",
        [(run_id, commit_sha, item["id"], item["status"],
          item.get("category"), int(item["duration_ms"]), now)
         for item in records],
    )
    conn.commit()


def recent(conn, case_id, limit=20):
    rows = conn.execute(
        "SELECT status, category, created_at FROM results "
        "WHERE case_id = ? ORDER BY created_at DESC LIMIT ?",
        (case_id, limit),
    ).fetchall()
    return rows

落库要在测试结束后做，而且不能因为它失败而让构建失败：写库是观测手段，不是被测对象。表要定期清理或按月分表，否则两年后查询变慢，而这时当初写库的人多半已经不在项目里了。

报告与 CI 的绑定：artifact、PR 评论、消息推送

报告躺在构建机的临时目录里，等于没有。三条通道各管一段：artifact 保证完整报告可下载、可归档；PR 评论保证改动相关的人第一时间看到结论；消息推送保证值班人不用盯着流水线。

artifact 的关键是 if: always()。测试失败时不生成报告，是最常见的自伤：恰恰是失败的那一次，大家最需要点进去看现场。保留期按追溯需求定，三十天是常见起点，发版节点的那份另行归档。

PR 评论要克制，只放三样：通过率与失败数、分类计数、报告链接。更重要的是更新而不是新增——同一个 PR 每次推送都发一条新评论，三个提交之后评论区就没人看了。

yaml — 上传报告并更新 PR 评论
      - name: Upload report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: web-report-${{ github.run_number }}
          path: |
            reports/allure-report
            reports/junit.xml
          retention-days: 30

      - name: Upsert PR comment
        if: always() && github.event_name == 'pull_request'
        uses: actions/github-script@v7
        with:
          script: |
            const body = [
              '## Web 自动化结果',
              `通过率 ${process.env.PASS_RATE}`,
              `失败 ${process.env.FAILED} 条，跳过 ${process.env.SKIPPED} 条`,
              `报告：${process.env.REPORT_URL}`,
            ].join('\n')
            const { data: list } = await github.rest.issues.listComments({
              ...context.repo,
              issue_number: context.issue.number,
            })
            const old = list.find(c => c.body.startsWith('## Web 自动化结果'))
            if (old) {
              await github.rest.issues.updateComment({
                ...context.repo, comment_id: old.id, body,
              })
            } else {
              await github.rest.issues.createComment({
                ...context.repo, issue_number: context.issue.number, body,
              })
            }

消息推送遵守三行原则：结论、计数、链接。把二十条用例名全贴进群消息是最常见的错误，刷屏之后没人会点链接。通知还要分级：PR 阶段只留评论，主干与夜间构建发群消息，发版前才需要邮件或文档归档。通知越廉价，阅读率越低，最后全被静音，等于没接。

链接可达性也常被忽略。内网 Jenkins 的报告对外包打不开，云上 artifact 要登录还有过期时间。常见做法是每个迭代把最后一份报告同步到对象存储的固定路径，并在用例管理平台挂上链接，半年后追查问题还能翻到现场。

别把报告做成日志堆

最没用的东西是原始日志。贴三千行和没贴效果一样，因为没人会读。只保留失败前后若干行、错误级别与关键业务日志，并在附件名里写清过滤条件；判断标准是这段日志能不能回答一个具体问题。

第二没用的是没有上下文的截图。一张不知道属于哪条用例、哪一步的图，只能证明当时屏幕上有点东西。截图要挂在步骤下，文件名带用例标识与序号，必要时附视口尺寸——在 1280 宽度下正常、在 375 宽度下错位的问题非常常见。

第三是只给通过率不给分类。95% 单独出现时，读者只能选择相信或不信；加上「其中 3 条环境问题、2 条脚本问题、1 条支付主流程回归」，它才成为判断依据。

还要分清报告与缺陷系统的边界。报告回答「发生了什么、现场什么样」，缺陷单回答「谁来修、什么时候修、修完怎么验证」。互相链接，各司其职，别把工单状态塞进报告，也别把截图堆进工单。

上线前检查清单

下面这张表适合放进团队文档，每次改报告结构时过一遍。大部分问题不是技术难题，而是遗漏，清单的价值就是把遗漏变成可见项。

检查项合格标准
字段完整性口径、分类、耗时、环境版本、现场链接五项齐全
失败证据每条失败至少一张截图加堆栈，trace 按需保留
分类质量四类计数齐全，待确认占比低于 5%
趋势连续性history 已传入，连续两次运行能看到两个点
历史可查精简结果已落库，能按用例查最近二十次
分发渠道artifact、PR 评论、群消息各就各位，链接可达
体积常见网络下能打开，示例目标 100 MB 以内

最容易自欺的一条是趋势：本地跑得通、CI 也生成了报告，就以为趋势在工作，其实 history 每次都被当成新目录覆盖。验收方法很土但有效——连续跑两次，确认趋势页有两个点；再点一条失败用例，看它过去十次记录是否都在。

最后给一个判断标准：如果一份失败报告需要写它的人亲自解释才能看懂，它就不合格。合格的报告应该让一个不熟悉该项目的人，三分钟内说清失败发生在哪一步、当时页面是什么状态、有没有可复现的路径。
