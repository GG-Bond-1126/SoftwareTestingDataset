App 自动化 12 个坑与解法

坑总是以同样的方式重复出现

我们团队 6 个人维护 480 条 App 自动化用例，跑在 4 台真机加 2 台模拟器上。我统计过 2025 年上半年全部 1 873 次失败，其中 62% 集中在 12 类问题上。也就是说，把下面这 12 条吃透，能直接消掉一大半的红色。

这 12 条有个共同特征：它们都不是框架本身的 bug，而是使用方式与真实设备环境之间的错位。框架文档里往往一句话带过，但在真机上会以完全不同的形态出现。下面每条都按症状、原因、解法三段写，症状尽量用报错原文，方便你对照自己的日志。

分类方法很土：每周把失败用例的截图和日志翻一遍，根因相同的合并成一条并编号。两个月后自然收敛到 12 类。这件事值得做，因为它把「又挂了」变成了「第 5 类，权限弹窗」，处理动作立刻明确，新人也能照着清单自查。

定位类：元素为什么就是找不到

坑 1：元素找不到，重跑一次又好了

症状：偶发 NoSuchElementException，单独重跑必过，全量跑挂的概率大约 30%。原因：find_element 是立即返回的，页面还在转场动画或等接口，元素自然不存在。另一种情况是列表项 id 每次启动都变，形如 item_1837，昨天写的定位今天就失效。

解法：禁止在用例里直接调用 find_element，统一走等待封装；定位优先级固定为 content-desc 大于可见文案大于稳定资源 id，动态 id 只做正则或父级约束，绝不硬编码。等待要等到可点击而不是仅存在，否则会点到被遮挡的透明层上。

python — 统一等待封装
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.support.ui import WebDriverWait

DEFAULT_TIMEOUT = 12


def wait_clickable(driver, locator, timeout=DEFAULT_TIMEOUT):
    return WebDriverWait(driver, timeout, poll_frequency=0.25).until(
        EC.element_to_be_clickable(locator),
        message=f"元素在 {timeout}s 内不可点击: {locator}",
    )


def wait_visible(driver, locator, timeout=DEFAULT_TIMEOUT):
    return WebDriverWait(driver, timeout, poll_frequency=0.25).until(
        EC.visibility_of_element_located(locator),
        message=f"元素在 {timeout}s 内不可见: {locator}",
    )

坑 2：Toast 抓不到，断言永远失败

症状：手动能看到「登录成功」的 Toast，脚本里 page_source 里搜不到，等断言执行时它已经消失了。原因：Toast 是系统窗口，不在当前 Activity 的视图树里；Android 的短 Toast 只显示约 2 秒，长 Toast 约 3.5 秒，而一次 page_source 调用在低端机上就要 300ms 以上。

解法：UiAutomator2 驱动可以把 Toast 节点带进 XML，但必须高频轮询才抓得住。更稳的方案是双通道：轮询 XML 拿文案，同时用 logcat 抓系统日志兜底。不要等操作结束后才开始找，要在点击之前就把轮询挂起来。

python — Toast 轮询断言
import time


def wait_toast(driver, text: str, timeout: float = 5.0) -> bool:
    deadline = time.time() + timeout
    while time.time() < deadline:
        if text in driver.page_source:
            return True
        time.sleep(0.1)
    raise AssertionError(f"Toast 未出现: {text}")


# 用法：先并发启动轮询，再触发操作，避免错过 2 秒窗口
toast_seen = wait_toast(driver, "登录成功", timeout=5)

坑 3：WebView 里的元素一律定位失败

症状：原生页面正常，一切到 H5 详情页就报找不到元素，截图里明明有。原因：会话还停在 NATIVE_APP 上下文，此时只能看到 WebView 容器这一个节点，H5 内部的 DOM 完全不可见。解法：切换到 WEBVIEW_ 开头的上下文再定位，切换后要等 DOM 就绪。细节包括调试开关、上下文等待和 JS 执行，单独写了一篇，这里只提醒一条：切回原生要在 finally 里做，否则后续用例会莫名失败。

交互类：点得到，但点不对

坑 4：软键盘遮挡输入框与按钮

症状：click 报 element not visible，或者点击落在了键盘的数字键上。原因：页面没有配置 windowSoftInputMode 为 adjustResize，键盘直接把底部按钮盖住，而元素坐标仍然是键盘弹出前的值。解法：输入完成后先收起键盘再点下一步；用 driver.hide_keyboard()，iOS 上它经常失效，退而求其次按一次返回键，注意按返回键可能触发页面退出，要在断言里确认当前页面没被关掉。

坑 5：权限弹窗让整批用例连锁失败

症状：新装的包第一次启动弹出相机、定位权限，脚本卡在那里，后面所有用例全超时。原因：权限弹窗属于系统包 com.android.permissioncontroller，不在被测 App 的视图树里，App 内部的定位策略完全找不到。解法：优先在安装时预授予，同时关掉动画。Android 11 之后的位置权限有「仅本次允许」，预授予只能拿到粗略定位，涉及精确定位的用例要单独处理弹窗，不能指望一次配置解决所有版本。

bash + python — 权限预授予
# 安装时直接授予运行时权限
adb install -r -g app-staging-5.8.2.apk

# 已安装的包补授权限
adb shell pm grant com.demo.app android.permission.CAMERA
adb shell pm grant com.demo.app android.permission.ACCESS_FINE_LOCATION
adb shell appops set com.demo.app android:coarse_location allow

# 关闭动画，减少等待类抖动
adb shell settings put global window_animation_scale 0
adb shell settings put global transition_animation_scale 0
adb shell settings put global animator_duration_scale 0

坑 6：换一台手机，坐标全偏

症状：在 1080×2400 上写死的 tap(540, 2100)，到 720×1600 的机器上点到了别处。原因：绝对坐标和设备分辨率绑定，而 App 的布局可能是百分比或自适应。解法：能用元素定位就不用坐标。确实需要按坐标（比如画布、签名板、地图）时，按 get_window_size 的比例换算，并且把比例写进配置而不是散落在用例里。

环境与驱动类：代码没改，环境变了

坑 7：系统一升级，驱动就起不来

症状：设备升到 Android 14 后，会话创建报 instrumentation 进程启动失败，或者 UiAutomator 服务反复崩溃。原因：新系统收紧了前台服务类型、后台 Activity 启动和隐式广播；targetSdk 34 的应用必须声明前台服务类型，驱动侧的 server 也需要对应版本才能适配新的权限模型。解法：设备池锁定系统镜像版本，升级走灰度，先在一台机器上跑冒烟；Appium 驱动与 uiautomator2 server 一起升级，不要只升一个。

坑 8：客户端和驱动版本对不上

症状：昨天还好好的，今天启动就报 server 安装失败或命令不支持。原因：Appium-Python-Client、Appium 主程序、uiautomator2 驱动三者版本各自演进，客户端发的命令在新驱动里改名或废弃。解法：三者在 requirements.txt 与 package.json 里全部锁版本；升级前先看驱动的 changelog，跑一遍最小会话验证，再合并到主干。

坑 9：并行跑两台设备就端口冲突

症状：单设备正常，起第二个会话时报端口被占用或设备连到了错误的会话。原因：uiautomator2 的 systemPort 默认都是 8200，两个会话抢同一个端口；MJPEG 端口也可能撞。解法：按设备序号分配端口，把配置集中在一个工厂函数里，不要在每个测试文件里手写 capabilities。

python — 按序号分配端口
from appium.options.android import UiAutomator2Options


def android_options(udid: str, index: int) -> UiAutomator2Options:
    opts = UiAutomator2Options()
    opts.platform_name = "Android"
    opts.udid = udid
    opts.system_port = 8200 + index
    opts.mjpeg_server_port = 9100 + index
    opts.auto_grant_permissions = True
    opts.new_command_timeout = 120
    return opts

工程类：单跑能过，全量就挂

坑 10：用例之间互相污染状态

症状：按文件顺序跑全挂，单独指定某条用例就过。原因：上一条用例留下了登录态、购物车商品、弹过一次的引导页，或者改了系统设置没还原。解法：用例必须能独立执行。会话层面用 no_reset = False 保证每条用例从干净状态开始；数据层面用独立测试账号和唯一业务单号；进入页面尽量用 deep link，跳过前置流程，减少对状态的依赖。另一个有效手段是把初始状态写成可执行的 setup，而不是写在注释里靠人记：需要登录就调登录接口拿 token 注入，需要购物车有商品就调加购接口，速度比点 UI 快十倍。

坑 11：CI 上设备跑到一半掉线

症状：本地稳定，CI 上随机出现 adb devices 显示 offline，或者会话超时。原因：USB 口供电不稳、线材接触不良、宿主机 USB 自动休眠、容器里 udev 规则缺失，还有模拟器自身偶发崩溃。解法：每条用例开始前做一次健康检查，发现 offline 就 adb reconnect offline 并重试一次；设备序列号写进报告；宿主机禁用 USB 休眠；长期方案是接云设备池，把硬件问题外包出去。

断言类：看起来对，其实在误报

坑 12：图片断言天天误报

症状：同一页面在本地通过，CI 上必挂，肉眼完全看不出差别。原因：像素级对比对字体抗锯齿、系统时间、状态栏图标、广告位轮播都极度敏感，换一台机器渲染就差几个像素。解法：只在结构稳定的页面做视觉断言；对比前裁掉状态栏与动态区域；用差异像素占比而不是完全相等，阈值控制在 0.3% 到 1% 之间，并用连续 10 次运行校准。

python — 带阈值的图片差异
from PIL import Image, ImageChops


def diff_ratio(expected_path, actual_path, tolerance=12, ignore_boxes=None):
    expected = Image.open(expected_path).convert("RGB")
    actual = Image.open(actual_path).convert("RGB")
    if expected.size != actual.size:
        actual = actual.resize(expected.size)

    diff = ImageChops.difference(expected, actual).convert("L")
    for box in ignore_boxes or []:
        diff.paste(0, box)

    pixels = list(diff.getdata())
    bad = sum(1 for value in pixels if value > tolerance)
    return bad / len(pixels)


ratio = diff_ratio("baseline/home.png", "artifacts/home.png",
                   tolerance=12, ignore_boxes=[(0, 0, 1080, 120)])
assert ratio < 0.003, f"视觉差异过大: {ratio:.4f}"

一套可复用的排查顺序

遇到失败不要先改脚本，按下面顺序看一遍，八成能直接定位。

  1. 看截图：当前到底停在哪个页面，有没有弹窗、键盘、加载中。
  2. 看 UI 层级：目标元素是否真的在 XML 里，属性值是否和定位器一致。
  3. 看上下文：如果是 H5，确认当前上下文是不是还在原生。
  4. 看设备状态：adb devices 是否 online，屏幕是否熄灭、是否锁屏。
  5. 看日志：logcat 里搜包名与 FATAL，崩溃往往只在这里留痕。
  6. 最后才怀疑代码：单独重跑这条用例，再全量重跑一次，区分偶发与稳定失败。

这个顺序的价值在于成本从低到高：看截图和层级是秒级，重跑一次是分钟级，改代码可能是小时级。先做便宜的检查，能省下大量无效修改，也能少走很多弯路，把时间留给真正需要判断的问题。

不要用 time.sleep 掩盖问题。加了三秒睡眠后用例通过了，并不代表问题消失，只是把偶发变成了更慢的偶发。所有等待都应该有明确条件。

这 12 条没有一条是奇技淫巧，全是把边界条件想在前面。真正拉开自动化质量差距的，往往不是会不会写定位，而是有没有把设备、系统、网络这些外部变量当成测试对象来管理。最后补一句：以上所有解法都要落进代码模板与代码评审清单，停留在文档里的经验，三个月后一定退回到原来的写法。
