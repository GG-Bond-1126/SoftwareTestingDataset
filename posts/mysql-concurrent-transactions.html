项目进阶：并发测试 + 数据一致性

python
import mysql.connector, threading

def deduct(uid, qty):
    c = mysql.connector.connect(host="localhost", user="root", password="test123", database="testdb")
    cur = c.cursor()
    cur.execute("UPDATE products SET stock=stock-%s WHERE product_id=1 AND stock>=%s", (qty, qty))
    c.commit(); cur.close(); c.close()

threads = [threading.Thread(target=deduct, args=(i, 2)) for i in range(10)]
[t.start() for t in threads]
[t.join() for t in threads]

# 验证库存非负
c = mysql.connector.connect(host="localhost", user="root", password="test123", database="testdb")
cur = c.cursor()
cur.execute("SELECT stock FROM products WHERE product_id=1")
assert cur.fetchone()[0] >= 0
print("并发测试通过 ✓")

并发写场景：库存、余额、秒杀

凡是「读出来 → 算一下 → 写回去」这种三段式逻辑，只要有两个执行体同时做，就可能出现「丢失更新」：两个请求都读到库存 100，都算出 99，都写回 99，实际扣了两次，库存却只少了 1。余额转账、秒杀抢单，全是这个模式。

先造一个最朴素的「不安全」版本，看问题长什么样：

setup.sql
CREATE TABLE stock (
  sku_id INT PRIMARY KEY,
  qty INT NOT NULL,
  version INT NOT NULL DEFAULT 0
);

INSERT INTO stock (sku_id, qty) VALUES (1, 100);

不安全写法：读改不是一步

bad.sql — 典型的「先查后改」两步走
-- 第 1 步：查出当前库存（读到 100）
SELECT qty FROM stock WHERE sku_id = 1;
-- 第 2 步：应用层算出 100 - 1 = 99，再写回
UPDATE stock SET qty = 99 WHERE sku_id = 1;
-- 两个请求同时走到第 1 步，都读到 100，都算出 99，都写 99 → 实际扣了 2 次，库存只减 1

隔离级别对并发结果的影响

MySQL InnoDB 默认隔离级别是 REPEATABLE READ（可重复读），但要注意：隔离级别解决的是「读」的问题（脏读/不可重复读/幻读），并不天然解决「并发写覆盖」这种更新丢失问题——并发写覆盖要靠锁，跟隔离级别是两套机制。

隔离级别能避免什么并发写覆盖问题还在吗
READ UNCOMMITTED基本不防什么在
READ COMMITTED脏读在
REPEATABLE READ（InnoDB 默认）脏读、不可重复读，基本防幻读在——更新丢失要靠锁解决
SERIALIZABLE额外加了隐式锁，读写都要排队天然避免，但代价是性能大幅下降

换句话说：测试并发扣库存这类问题，不能指望「把隔离级别调高就万事大吉」，得明确业务用的是哪种锁方案，再针对性验证。

两种锁方案，效果差在哪

悲观锁：SELECT ... FOR UPDATE

pesimistic.sql
START TRANSACTION;
-- 把这一行锁住，别的会话想同时 UPDATE 这行得排队等锁
SELECT qty FROM stock WHERE sku_id = 1 FOR UPDATE;
-- 应用层拿到 qty，算出 qty - 1
UPDATE stock SET qty = qty - 1 WHERE sku_id = 1;  -- 更稳妥的是直接写这个原子表达式，少一次应用层计算
COMMIT;

特点：行会被锁住，后到的请求要等前一个提交才能继续，天然串行化，不会丢失更新。代价是并发上不去、锁持有时间越长，排队越长。

乐观锁：版本号校验

optimistic.sql
-- 第 1 步：不带锁，普通读
SELECT qty, version FROM stock WHERE sku_id = 1;
-- 第 2 步：更新时带上"我读到的版本号"作为前提条件
UPDATE stock
SET qty = qty - 1, version = version + 1
WHERE sku_id = 1 AND version = 读到的那个版本号;
-- 如果两个请求同时走到第 2 步，只有一个的 version 条件还成立，另一个的 UPDATE 影响行数是 0，
-- 业务层检测到"影响行数 = 0"就该重试整个流程

特点：不加锁，读的时候不排队，但写的时候靠版本号「抢」，抢输了要整个流程重试。适合写冲突不频繁的场景；冲突很频繁时（比如爆款秒杀）重试会扎堆，反而不如悲观锁干脆。

Python 脚本：多线程并发扣库存，两种方案各跑一遍

test_concurrent_stock.py
import threading
import time
import pymysql

CONN = dict(host="127.0.0.1", port=3306, user="test_user",
            password="test_pwd", database="shop")

def reset_stock(qty=100):
    conn = pymysql.connect(**CONN)
    with conn.cursor() as cur:
        cur.execute("DELETE FROM stock WHERE sku_id = 1")
        cur.execute("INSERT INTO stock (sku_id, qty, version) VALUES (1, %s, 0)", (qty,))
    conn.commit()
    conn.close()

def final_qty():
    conn = pymysql.connect(**CONN)
    with conn.cursor() as cur:
        cur.execute("SELECT qty FROM stock WHERE sku_id = 1")
        v = cur.fetchone()[0]
    conn.close()
    return v

def deduct_pessimistic():
    """悲观锁：FOR UPDATE 串行化"""
    conn = pymysql.connect(**CONN)
    with conn.cursor() as cur:
        cur.execute("START TRANSACTION")
        cur.execute("SELECT qty FROM stock WHERE sku_id = 1 FOR UPDATE")
        cur.execute("UPDATE stock SET qty = qty - 1 WHERE sku_id = 1")
        conn.commit()
    conn.close()

def deduct_optimistic():
    """乐观锁：版本号校验，抢输就重试整个流程"""
    for _ in range(50):  # 最多重试 50 次
        conn = pymysql.connect(**CONN)
        try:
            with conn.cursor() as cur:
                cur.execute("SELECT qty, version FROM stock WHERE sku_id = 1")
                qty, ver = cur.fetchone()
                if qty <= 0:
                    return
                affected = cur.execute(
                    "UPDATE stock SET qty = qty - 1, version = version + 1 WHERE sku_id = 1 AND version = %s",
                    (ver,))
                conn.commit()
                if affected == 1:
                    return  # 抢到了，结束
        finally:
            conn.close()
        time.sleep(0.01)  # 抢输了，稍等再重试

def run_case(name, worker, n=30, initial=100):
    reset_stock(initial)
    threads = [threading.Thread(target=worker) for _ in range(n)]
    for t in threads: t.start()
    for t in threads: t.join()
    left = final_qty()
    print(f"[{name}] 初始 {initial}，{n} 个并发请求，最终库存 = {left}")
    return left

def main():
    # 两种方案各跑一遍，最终库存都应等于 initial - n（在库存充足的前提下）
    run_case("悲观锁", deduct_pessimistic)
    run_case("乐观锁", deduct_optimistic)

if __name__ == "__main__":
    main()

跑完看两个结论：① 两种方案最终库存都应该是 initial - 30，任何一个对不上，说明实现有漏；② 再对照「不安全写法」（先查后改、不加锁不带版本号）跑一遍，大概率会看到库存比预期扣得少（丢更新），这就是要证明「锁确实起作用了」的对照组。

两个绕不开的坑：死锁和锁等待超时

死锁：两个事务互相等对方先放锁。常见于按不同顺序更新多行（A 先锁 1 再锁 2，B 先锁 2 再锁 1）。测试并发时，故意制造「反向操作顺序」的对照组，观察是否触发 1213 Deadlock found 报错，以及业务层有没有做好「捕获后重试」。

锁等待超时：InnoDB 有一个参数 innodb_lock_wait_timeout（默认 50 秒），等锁超过这个时长会直接报错而不是无限等。压测时把并发拉高，要专门验证「等锁超时的请求」是不是被正确捕获、给用户返回了合理的失败提示（而不是 500 或者干脆卡死）。
