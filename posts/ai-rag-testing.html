RAG 测试：召回、排序与答案落地

RAG 系统出问题，八成不在大模型，在检索。用户问「住院津贴怎么算」，模型答得头头是道，引用的却是另一款产品的条款，页码还标错了。这类回答在肉眼看来几乎无懈可击，因为语言层面它是通的。

所以 RAG 测试必须分层：每一层单独出指标，不能只看最终答案像不像。这篇文章按「文档切片 → 向量召回 → 重排 → 生成」四层拆开讲，每层给可跑脚本和判定标准，最后用 Ragas 做语义兜底。

一次「答对了但引错页」的事故

我们的场景是产品条款问答，知识库 6800 篇 PDF，平均每篇 14 页。上线第两周，客服转来一个问题：用户按回答里的页码去查条款，翻了半天没找到，投诉我们「伪造材料」。查下来答案内容其实是对的，但引用的页码是 PDF 的物理页码，而文档里印的是印刷页码，两者差了 2 页。

这件事教育很深：RAG 的正确性不只体现在文字，还体现在证据链能不能被别人复核。之后我们把测试拆成四层，任何一层指标掉了都不许发版。切片从 1024 token 降到 512 token 加 64 重叠后，召回率@5 从 62% 提到 91%，最终答案的正确率也跟着从 74% 涨到 89%。

测试分层：每层有独立的失败信号

把 RAG 当一个黑盒测，失败时你不知道该怪切片、怪向量库还是怪 Prompt。分层之后，每一层都有独立的输入输出和指标，定位时间从半天缩到十分钟。

层被测对象核心指标失败典型症状
切片切分策略、元数据切片完整率、页码准确率表格被切断、页码错位
召回向量化 + 检索Recall@k、MRR该命中的文档没进来
重排rerankerTop1 准确率、NDCG@5相关文档在但排到第 8 位
生成Prompt + 模型忠实度、拒答率、引用校验答非所问、编造条款

这四层的测试成本递增、稳定性递减。切片和召回是确定性的，可以每次提交都跑；重排和生成带模型调用，按天跑。把便宜的先跑完，能省掉大量无效的模型调用费用。

环境搭建

召回评测需要一个基线检索器做对照，我们用 BM25 加字符二元组分词，不依赖分词词典，中文效果够用。真正的向量检索通过项目里的 retriever 接口接入，测试脚本对实现无感。

召回率怎么测：先构造 query-文档对

召回评测的前提是有一份标注好的查询集，每条查询写明「应该命中哪几个切片」。我们从三个渠道攒了 240 条：客服真实提问 130 条、按文档反推生成的问题 70 条、线上答错回流 40 条。标注只标到切片级别，标到文档级别太粗，会掩盖切片切坏的问题。

这份查询集每季度补 20 条新问题、下线 5 条已失效问题，保证它跟着业务一起长，而不是冻结在上线那一天。冻结的评测集会慢慢变成一份自我安慰的报表。

指标用 Recall@k 和 MRR 一起看。Recall 告诉你「答案在不在候选里」，MRR 告诉你「排得够不够前」。两个都低是检索问题，Recall 高 MRR 低是排序问题，处理方式完全不同。

python · eval/recall_eval.py
import json
import pandas as pd
from rank_bm25 import BM25Okapi

def tokenize(text: str) -> list[str]:
    """字符二元组，避开中文分词词典依赖。"""
    return [text[i:i + 2] for i in range(len(text) - 1)]

def recall_at_k(ranked: list[str], relevant: set[str], k: int) -> float:
    return len(set(ranked[:k]) & relevant) / len(relevant)

def mrr(ranked: list[str], relevant: set[str]) -> float:
    for i, doc_id in enumerate(ranked, start=1):
        if doc_id in relevant:
            return 1 / i
    return 0.0

def eval_retriever(search, queries_path: str, k: int = 5) -> pd.DataFrame:
    rows = []
    for line in open(queries_path, encoding="utf-8"):
        case = json.loads(line)
        ranked = search(case["query"], k)
        rows.append({
            "id": case["id"],
            "scene": case["scene"],
            "recall": recall_at_k(ranked, set(case["relevant"]), k),
            "mrr": mrr(ranked, set(case["relevant"])),
            "top1": ranked[0] if ranked else None,
        })
    return pd.DataFrame(rows)

if __name__ == "__main__":
    chunks = json.load(open("index/chunks.json", encoding="utf-8"))
    ids = [c["id"] for c in chunks]
    bm25 = BM25Okapi([tokenize(c["text"]) for c in chunks])

    def search(q: str, k: int) -> list[str]:
        scores = bm25.get_scores(tokenize(q))
        return [ids[i] for i in scores.argsort()[::-1][:k]]

    df = eval_retriever(search, "cases/recall_queries.jsonl")
    summary = df.groupby("scene")[["recall", "mrr"]].mean().round(3)
    print(summary)
    print(f"overall recall@5={df.recall.mean():.3f} mrr={df.mrr.mean():.3f}")

输出会直接告诉你哪类场景拖后腿。我们是「产品对比」场景 recall@5 只有 0.58，其他场景都在 0.9 以上，一眼就能定位到对比类文档的切片问题。

切片粒度：最容易忽略却影响最大的参数

切片不是越细越好，也不是越粗越好。太细会把一个条款拆成两半，召回时只命中前半句；太粗会把多个条款混在一起，重排时噪声变大。我们做了四组对照实验，同一份 6800 篇文档、同一套 240 条查询：

切片大小重叠Recall@5MRR切片数
256 token320.790.6141.2 万
512 token640.910.7721.6 万
1024 token1280.850.7011.1 万
整页00.680.529.5 万

512 加 64 是拐点。256 太细，条款被切碎；1024 太粗，一个切片里塞了三条不相干内容，向量被平均掉。这个结论只适用于我们的文档结构，你做的时候必须自己扫一遍，参数不能照抄。

另外两个切片层面的断言必须写进测试：表格不能被切断（表格切片要整表保留），每个切片必须带 doc_id、page、section 三个元数据。少一个，后面的页码追溯就直接失效。

重排：相关文档进来了，但排在第 8 位

召回 Top20 里明明有正确切片，最终却没用上，问题出在重排。我们的做法是召回取 Top20，交给 reranker 打相关性分，取 Top5 进上下文。测试指标是 Top1 准确率和 NDCG@5，样本用同一批 240 条查询。

加入 bge-reranker 之后，Top1 准确率从 0.54 提到 0.81，NDCG@5 从 0.62 到 0.79，上下文里无关内容的平均条数从 2.4 降到 0.9。这个变化直接体现在生成端：回答中「张冠李戴」的比例下降了一半。

重排评测还有一个必做项：负样本要够硬。我们从同一产品的相邻条款里挑切片当干扰项，模型必须把它排到正确条款后面。软负样本（完全不相关的文档）谁都能分开，测不出真实的排序能力。

重排的测试不需要每次都跑大模型。reranker 是确定性模型，同一输入同一分数，可以像普通单测一样进 CI，单条 40 毫秒，240 条不到 10 秒。

无答案场景必须拒答

RAG 最危险的幻觉来源是「检索到了相似但不相关的内容」，模型硬着头皮答。我们的做法是在生成 Prompt 里写死规则：只有当上下文能直接支撑答案时才作答，否则返回固定的拒答结构。测试要专门构造这类查询。

python · tests/test_rag_refusal.py
import pytest
import requests

RAG_API = "http://127.0.0.1:8000/answer"
NO_ANSWER_CASES = [
    ("na-01", "2028 年新产品的等待期是多久？"),
    ("na-02", "能报雅思考试培训费吗？"),
    ("na-03", "你们公司上季度营收多少？"),
]

@pytest.mark.parametrize("cid,question", NO_ANSWER_CASES, ids=[c[0] for c in NO_ANSWER_CASES])
def test_refuse_when_no_context(cid, question):
    r = requests.post(RAG_API, json={"question": question}, timeout=30)
    body = r.json()
    assert r.status_code == 200, f"[{cid}] HTTP {r.status_code}"
    assert body["refused"] is True, f"[{cid}] 应拒答，实际: {body['answer'][:80]}"
    assert not body["citations"], f"[{cid}] 拒答时不应带引用"
    # 拒答文案不允许出现数字承诺
    assert not any(ch.isdigit() for ch in body["answer"]), f"[{cid}] 拒答含数字"

这条断言的口径要和产品对齐：拒答不等于体验差。我们的原则是「没查到的绝不编」，转人工率上升 5 个百分点可以接受，客诉下降带来的收益远大于此。

引用页码必须可追溯

用户点开引用要能看到原文，这要求答案里的每一个引用都能定位到切片、文档和页码，而且页码要和印刷页码一致。我们的测试分三步校验：引用 id 存在、页码与切片元数据一致、引用原句确实出现在切片文本里。

python · tests/test_citation_trace.py
import json
import pytest

CHUNKS = {c["id"]: c for c in json.load(open("index/chunks.json", encoding="utf-8"))}

def load_answer(question: str) -> dict:
    import requests
    return requests.post("http://127.0.0.1:8000/answer",
                         json={"question": question}, timeout=30).json()

@pytest.mark.parametrize("question", [
    "住院津贴的免赔天数是多少？",
    "意外医疗的报销比例和限额？",
])
def test_citation_page_traceable(question):
    body = load_answer(question)
    assert body["citations"], "有答案却没有引用"
    for cite in body["citations"]:
        chunk = CHUNKS.get(cite["chunk_id"])
        assert chunk is not None, f"引用了不存在的切片 {cite['chunk_id']}"
        assert chunk["doc_id"] == cite["doc_id"], "文档 id 与切片不一致"
        # 印刷页码必须与切片元数据一致（物理页码需经过偏移映射）
        assert chunk["page"] == cite["page"], (
            f"页码不一致: 切片 {chunk['page']} vs 引用 {cite['page']}")
        assert cite["quote"][:24] in chunk["text"], "引用原句在切片中找不到"

页码那个偏移映射就是第一个事故的修复：索引时把物理页和印刷页都存进元数据，展示用印刷页，校验用两个都查一遍。上线后再也没出现过翻不到页的投诉。

用 Ragas 检查忠实度与上下文精度

规则能测结构和引用，测不了「答案有没有超出上下文」。这部分用 Ragas 的三个指标：faithfulness 看答案是否忠于上下文，context_precision 看上下文里有多少是真正相关的，context_recall 看该召回的有没有召回。

python · eval/ragas_check.py
from datasets import Dataset
from ragas import evaluate
from ragas.metrics import faithfulness, context_precision, context_recall

def ragas_report(rows: list[dict]) -> dict:
    """rows: question / answer / contexts / ground_truth"""
    ds = Dataset.from_list([{
        "question": r["question"],
        "answer": r["answer"],
        "contexts": r["contexts"],
        "ground_truth": r["ground_truth"],
    } for r in rows])
    result = evaluate(
        ds,
        metrics=[faithfulness, context_precision, context_recall],
    )
    return {k: round(float(v), 3) for k, v in result.items()}

if __name__ == "__main__":
    import json
    rows = [json.loads(l) for l in open("cases/rag_samples.jsonl", encoding="utf-8")]
    print(ragas_report(rows))  # {'faithfulness': 0.89, 'context_precision': 0.76, ...}

三个指标要合起来看：faithfulness 高但 context_precision 低，说明模型没瞎编，但塞了一堆无关内容，浪费 token 还容易干扰；faithfulness 低则说明上下文里没有答案，模型在编。我们设的红线是 faithfulness 不低于 0.85、context_precision 不低于 0.7。

接到 CI 与日常巡检

四层测试的触发频率不一样。切片和召回是确定性的，每次索引变更都跑，耗时 40 秒；重排每天跑一次；生成层和 Ragas 因为要调模型，每晚跑 120 条抽样，约 7 分钟、花费 4 元。索引重建必须跑全量，这是唯一不能省的一步——切片参数一改，所有下游指标都得重算。

日常巡检还有一个轻量信号：线上随机抽 200 条回答，只跑引用校验和拒答校验，不调大模型，纯规则 6 秒出结果。一旦引用校验失败率超过 2%，立刻告警，通常意味着索引或元数据出了问题。

索引版本号也必须进报告。同一批用例跑在不同索引上结果不可比，我们每次重建索引都会生成一个 build id，指标表里带这一列，否则跨周对比会得出完全错误的结论。

踩坑与边界

坑一：只用文档级标注测召回。文档命中不代表切片命中。我们早期按文档标，recall 显示 0.95，实际切片命中只有 0.72，因为正确内容被切到了相邻切片里。标注必须落到切片 id。

坑二：忽略 query 改写环节。系统里有一层查询改写，把「住院一天补多少」改写成书面语。测试如果绕过改写直接打检索接口，测出来的指标会比线上高 8 到 10 个百分点。评测链路必须和线上链路一致，包括改写。

坑三：Ragas 的裁判模型换了没重测。faithfulness 依赖裁判模型，换裁判等于换尺子。我们固定裁判模型版本，并在评测报告里记下模型名，避免跨月比较时出现莫名其妙的分数跳变。

坑四：Top-k 调大掩盖召回问题。把 k 从 5 调到 20，recall 自然好看，但上下文塞满噪声，生成质量反而下降。指标要和上下文长度一起看，我们的约束是进入生成环节的切片不超过 5 条、总 token 不超过 2400。

判断 RAG 测试做没做对，看一个现象就够：问题出现时，你能不能在十分钟内说清是切片、召回、重排还是生成的问题。说得清，说明分层有效；说不清，说明还在拿最终答案当唯一信号。
