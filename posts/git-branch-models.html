Git 分支模型：Feature、Release、Hotfix 怎么选

环境搭建

terminal
# 安装 Git
# 配置用户
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
# 验证
git --version
terminal — 初始化仓库
mkdir my-project && cd my-project
git init
echo "hello" > test.py
git add .
git commit -m "初始提交"

基础应用：分支操作

terminal
# 创建 + 切换分支
git checkout -b dev
git commit -m "dev 修改" --allow-empty
git checkout main
git merge dev

# 查看日志
git log --oneline --graph

项目进阶：Feature 分支 + MR 流程

terminal
# Feature 分支
git checkout -b feature/login
git commit -m "feat: 用户登录" --allow-empty

# 提 MR（在 GitHub/GitLab 上）
# 评审通过后合并
git checkout main
git pull origin main
git merge --squash feature/login
git commit -m "feat: 用户登录"
git push origin main
git branch -d feature/login

三种主流分支模型对比

先搞清楚：分支模型解决的核心问题是「代码从开发到上线怎么走」。测试工程师不是定策略的人，但必须看懂策略，否则测试环境和代码版本会对不上。

Git Flow（适合有定期发布节奏的项目）

分支结构示意
main（生产）
  └── release/1.2（发布准备，只修 Bug 不加功能）
       └── hotfix/1.1.1（紧急修复）

develop（开发主干）
  ├── feature/user-login（功能分支）
  ├── feature/pay-flow（功能分支）
  └── feature/report-export（功能分支）
  • main：永远对应线上版本，只接受 release 或 hotfix 的合并；
  • develop：开发主干，所有 feature 从这里切出、合并回这里；
  • feature/*：一个功能一条分支，开发完提 MR 合回 develop；
  • release/*：从 develop 切出，只允许修 Bug，测完合回 main 和 develop；
  • hotfix/*：线上紧急 Bug，从 main 切出，修完合回 main 和 develop。

测试视角：测功能在 develop，测发布在 release，测热修在 hotfix。千万别在 release 分支上加新功能，那是开发的事。

GitHub Flow（适合持续部署的项目）

分支结构示意
main（生产）
  ├── feature/login（功能分支，短期存在）
  ├── feature/dashboard（功能分支）
  └── fix/typo（小修复分支）
  • 没有 develop 和 release，所有分支直接从 main 切出；
  • 合并到 main 后立即部署，没有「发布窗口」概念；
  • 分支寿命尽量短，一两天内就该合并。

测试视角：测在 main 的「上一版」和 feature 分支上，合并到 main 后做一轮回归即可。

简化模型（小团队、项目少）

只有一条 main，所有改动直接提交到 main，用 tag 标记版本。测试就是直接测 main + 看 tag。

分支命名规范

好的命名规范让「一条分支名」就能告诉你这条分支在干嘛。推荐格式：

命名规范
# 格式：类型/简短描述（用短横线连接）
feature/user-login       # 新功能
feature/report-export    # 新功能
fix/login-timeout        # Bug 修复
hotfix/pay-overflow      # 热修复（Git Flow）
release/1.2.0            # 发布分支（Git Flow）
test/e2e-regression      # 测试专用分支
  • 全小写，单词用 - 连接，不用下划线；
  • 描述尽量短，不超过 5 个单词；
  • 测试专用分支（比如跑 UI 自动化的）用 test/ 前缀，避免和开发分支混在一起。

测试环境映射表

这是测试工程师最该记住的一张表。把「分支」和「环境」一一对应，测试时就知道该拉哪个分支：

测试环境映射（Git Flow 示例）
# 环境 | 对应分支 | 部署时机 | 测试重点
开发环境 | feature/* | 开发自测 | 功能是否可跑通
测试环境 | develop | 每次合并后 | 回归 + 新功能验收
预发环境 | release/* | 发版前 | 发布回归 + 性能验证
生产环境 | main | 发布后 | 冒烟 + 热修验证

最常见的错误：在预发环境（release 分支）测新功能。release 分支不应该有新功能，如果 release 上出现新功能，说明开发把 feature 直接合进 release 了，这是流程违规。

案例：一次完整的功能测试 + 发布流程

假设你用 Git Flow，负责测试「用户登录」功能：

terminal — 完整流程
# 1. 开发完成，feature 分支提 MR 合入 develop
# 2. 你拉 develop，开始测试
git checkout develop
git pull

# 3. 跑回归 + 新功能测试
python -m pytest tests/ -v

# 4. 测试通过，开发切 release 分支
git checkout -b release/1.2 develop

# 5. 你在 release 上做发布回归
python -m pytest tests/smoke/ -v

# 6. 发布，release 合入 main，打 tag
git checkout main
git merge release/1.2
git tag -a v1.2.0 -m "Release v1.2.0"
git push --tags

# 7. 线上冒烟
python -m pytest tests/smoke/ --env=production

走完这一遍，你就完整体验了「功能开发 → 测试 → 发布 → 线上验证」的全流程。测试工程师在每一步都知道自己在哪个分支、该跑哪些用例。

记住一句话：分支是代码的「时间线」，测试环境是代码的「舞台」。搞清楚每个分支对应哪个舞台，测试就不会迷路。
