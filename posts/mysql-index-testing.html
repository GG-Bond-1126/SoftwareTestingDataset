接口突然变慢？教你用 EXPLAIN 看 SQL 有没有走索引

环境搭建

terminal
# 启动 MySQL（Docker）
docker run -d --name test-mysql -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=test123 -e MYSQL_DATABASE=testdb mysql:8.0

# 连接验证
mysql -h localhost -u root -ptest123 testdb

# 创建测试表
CREATE TABLE users (id INT PRIMARY KEY AUTO_INCREMENT, name VARCHAR(100), email VARCHAR(200) UNIQUE);

基础应用：第一个 SQL 验证

python
import mysql.connector

conn = mysql.connector.connect(host="localhost", port=3306, user="root", password="test123", database="testdb")
cur = conn.cursor()
cur.execute("INSERT INTO users (name, email) VALUES (%s, %s)", ("测试", "t@e.com"))
conn.commit()
cur.execute("SELECT * FROM users WHERE name = %s", ("测试",))
assert cur.fetchone() is not None
print("基础验证通过 ✓")
cur.close(); conn.close()

项目进阶：并发测试 + 数据一致性

python
import mysql.connector, threading

def deduct(uid, qty):
    c = mysql.connector.connect(host="localhost", user="root", password="test123", database="testdb")
    cur = c.cursor()
    cur.execute("UPDATE products SET stock=stock-%s WHERE product_id=1 AND stock>=%s", (qty, qty))
    c.commit(); cur.close(); c.close()

threads = [threading.Thread(target=deduct, args=(i, 2)) for i in range(10)]
[t.start() for t in threads]
[t.join() for t in threads]

# 验证库存非负
c = mysql.connector.connect(host="localhost", user="root", password="test123", database="testdb")
cur = c.cursor()
cur.execute("SELECT stock FROM products WHERE product_id=1")
assert cur.fetchone()[0] >= 0
print("并发测试通过 ✓")

什么是索引，为什么测试要懂

索引可以理解成数据库的「目录页」：没有它，查一条记录要从第一行扫到最后一行（全表扫描）；有它，数据库能直接「跳」到目标位置。测试工程师不一定要会设计索引，但必须会判断一条 SQL 有没有真正用上索引——这是定位「接口变慢」和「性能回归」最快的抓手。

EXPLAIN 输出的关键字段，先看这几个

对任何一条 SELECT，前面加个 EXPLAIN 就能看执行计划：

explain1.sql
EXPLAIN SELECT * FROM orders WHERE user_id = 1;

重点看 4 列：

字段看什么危险信号
type访问类型，从好到差大致是 const > ref > range > index > ALL出现 ALL 意味着全表扫描
key实际用到的索引名，NULL 表示「没用到任何索引」大表查询时 key 为 NULL，基本可以确认全表扫描
rows估算要扫描多少行rows 接近表总行数，且数据量还很大，说明没被有效过滤
Extra额外动作出现 Using filesort（排序靠临时空间）、Using temporary（建了临时表），往往意味着 SQL 还能优化

判断「有没有走索引」最快的两步：看 key 是否为 NULL，看 type 是不是 ALL。两个都命中，就是全表扫描，基本可以认定这条 SQL 是当前慢的元凶（前提是表本身够大）。

4 种高频「索引失效」场景

① 大表查询未走索引（最常见）

对 user_id 没建任何索引，EXPLAIN ... WHERE user_id = 1 直接看到 type=ALL, key=NULL, rows≈表总行数。修复就是加索引，属于「送分题」，但测试要先能发现它，而不是等上线后接口超时才反应过来。

② 复合索引顺序用错

建了复合索引 (a, b, c)，按「最左前缀」原则，查询条件必须从 a 开始连续匹配才有效：

explain2.sql
EXPLAIN SELECT * FROM t WHERE a = 1 AND c = 3;
-- 跳过了 b，只能用到索引的 a 这一层，c 无法在索引里直接定位，往往退化成"索引扫完再过滤"

③ 在索引列上套函数，索引直接失效

explain3.sql
-- created_at 上有索引，下面这条 SQL 里套了 YEAR()，索引就用不上了
EXPLAIN SELECT * FROM orders WHERE YEAR(created_at) = 2026;
-- 修复：改成范围写法，让索引能用上
EXPLAIN SELECT * FROM orders
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';

④ 隐式类型转换

列是 varchar，查询时传的是数字，MySQL 会悄悄把整列都转成数字再比，索引也废了：

explain4.sql
EXPLAIN SELECT * FROM users WHERE phone = 13800000000;   -- phone 是 varchar，索引失效
EXPLAIN SELECT * FROM users WHERE phone = '13800000000'; -- 加引号，类型匹配，索引正常命中

Python 脚本：批量跑 EXPLAIN 并标记全表扫描

把「上线前抓一遍核心 SQL 的索引情况」做成自动化脚本，跑完直接告诉你哪些 SQL 有风险：

audit_explain.py
import pymysql

# 待审计的 SQL 列表（生产环境里通常来自慢查询日志或核心接口梳理）
SQL_LIST = [
    ("用户按 id 查订单", "SELECT * FROM orders WHERE user_id = 1"),
    ("按年统计订单",     "SELECT COUNT(*) FROM orders WHERE YEAR(created_at) = 2026"),
    ("手机号查用户",     "SELECT * FROM users WHERE phone = 13800000000"),
]

def main():
    conn = pymysql.connect(host="127.0.0.1", port=3306,
                           user="test_user", password="test_pwd",
                           database="shop", charset="utf8mb4")
    with conn.cursor() as cur:
        for label, sql in SQL_LIST:
            cur.execute(f"EXPLAIN {sql}")
            row = cur.fetchone()
            # EXPLAIN 返回是位置型结果，按列名取值更稳妥：
            cur.execute(f"EXPLAIN {sql}")
            desc = cur.description
            row_dict = dict(zip([d[0] for d in desc], row))
            type_ = row_dict.get("type")
            key = row_dict.get("key")
            rows = row_dict.get("rows")
            flagged = (type_ == "ALL") or (key is None)
            mark = "❌ 未走索引（全表扫描风险）" if flagged else "✅ 命中索引"
            print(f"[{label}] type={type_} key={key} rows={rows}  {mark}")
            if flagged:
                print(f"   建议：确认 {sql.split('FROM')[-1].strip().split('WHERE')[0]} 相关列是否缺索引，或 SQL 写法是否触发失效")

if __name__ == "__main__":
    main()

rows 是数据库的估算值，不是精确行数，别拿它当「必须小于某个数」的硬性标准；判断「走没走索引」以 type + key 为主，rows 只作辅助参考。

把这份 Checklist 固化进每次上线前的性能冒烟流程：核心接口对应的 SQL 全量跑一遍 EXPLAIN，有 ALL/NULL 的就先找开发确认是「已知问题」还是「新引入的问题」，别把隐患带上线。
