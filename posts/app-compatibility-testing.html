APP 兼容性测试：系统版本 / 分辨率 / 厂商 ROM

谁需要这篇，它解决什么问题

如果你接手一个在线跑了两三年的 App，老板问「我们到底支持哪些机型」，而你手上只有发布说明里一句 Android 8 以上，这篇就是写给你的。兼容性测试的两个极端很常见：只在自己的开发机上点两下就发版，或者列一张两千个组合的矩阵然后没人执行。前者把风险转给用户，后者把工作量转给测试自己。

兼容性缺陷往往只在某个厂商的某个 ROM 版本上出现，开发本地复现不了，日志里也没有堆栈，唯一证据是用户截图。所以核心不是多测几台，而是用有限设备覆盖住会出问题的那部分用户。下面按可执行路线展开：划边界、剪矩阵、拆版本变更、看屏幕与语言、查厂商 ROM、补资源耗尽场景，最后给取证模板和检查清单。

先定支持边界：最低版本不是拍脑袋

最低版本由三个输入决定。第一是后台真实的版本分布，不是第三方统计站的全球数据，同一个 App 在不同城市的分布可能差出两个大版本。第二是技术依赖：targetSdk 要求、三方 SDK 的下限、想用的新 API。第三是支持成本：多一个大版本就多一行回归，长尾机型的适配工时往往高于它带来的收入。

算笔账。假设 Android 9 及以下只占活跃用户 2.4%（示例值），而为了它每次发版多跑一轮老系统回归、多维护一套分支，成本约占总测试工时 15%。把 minSdk 提到 10，让商店直接过滤，比让用户装上再闪退体面。边界要写进发布说明、商店描述和客服话术，三处口径一致，每季度用后台数据复核一次。

兼容性矩阵：用用户占比乘风险剪裁

系统版本、厂商、分辨率做笛卡尔积，8 乘 50 乘 5 就是两千个组合。这个数字只能证明全量测试不可行，真正能做的是给候选设备打分，按预算取头部。

评分用「用户占比的平方根乘风险系数」。开平方是为了压住头部机型的垄断，避免占比 30% 的机型挤掉全部长尾，而长尾里往往藏着最脏的 ROM 问题。风险系数由业务和测试共同评估，支付、登录、推送给高值。矩阵强制保留最低和最新版本各一台，同一厂商同一大版本只留一台。

预算控制在十到十五台真机，其余用云测补。上线后把崩溃和客诉机型反填进来，保留两成机动名额。矩阵要随版本分布、大促和新 ROM 重算。

取舍是自建还是云测。自建随时调试、能刷机能抓完整日志，但采购维护贵、机型更新慢；云测机型全、按分钟计费，但调试受限、私有包上传要走合规。常见组合是核心十台自建，长尾用云。

python — 按占比与风险挑选机型
import csv
from dataclasses import dataclass


@dataclass
class Device:
    model: str
    vendor: str
    os_version: str
    share: float   # 后台活跃用户占比，示例值
    risk: float    # 业务风险系数 1.0 到 3.0，人工评估


def score(device: Device) -> float:
    # 开平方压住头部机型，避免占比 30% 的机型挤掉全部长尾
    return device.share ** 0.5 * device.risk


def pick(devices, budget=12, must_have=("Android 15", "iOS 18")):
    chosen = [d for d in devices if d.os_version in must_have]
    for device in sorted(devices, key=score, reverse=True):
        if len(chosen) >= budget:
            break
        if device in chosen:
            continue
        same_branch = any(
            c.vendor == device.vendor
            and c.os_version.split(".")[0] == device.os_version.split(".")[0]
            for c in chosen
        )
        if same_branch:
            continue
        chosen.append(device)
    return chosen


with open("device_share.csv", encoding="utf-8") as fp:
    pool = [
        Device(row["model"], row["vendor"], row["os_version"],
               float(row["share"]), float(row["risk"]))
        for row in csv.DictReader(fp)
    ]

for item in pick(pool):
    print(f"{item.vendor:8} {item.model:16} {item.os_version:9} {score(item):.2f}")

Android 版本行为变更：四个最容易翻车的开关

Android 的兼容问题八成集中在 targetSdk 与设备版本的交叉点。targetSdk 决定按哪套规则运行，设备版本决定系统提供什么能力。设备升级是被动的，targetSdk 被商店推着抬，两条线一交叉就出现只在某个区间复现的问题。

版本关键行为变更最典型的失败表现
Android 10分区存储可临时豁免、后台定位拆成独立权限公共目录读写失败、后台定位被拒
Android 11分区存储强制、一次性权限与权限自动重置老路径迁移失败、撤销权限后功能静默
Android 12模糊定位、蓝牙新权限、PendingIntent 可变性精确定位降级、蓝牙扫描拿不到结果
Android 13通知运行时权限、细分媒体权限通知不弹、相册只能看到部分图片
Android 14前台服务类型强制、部分照片访问前台服务启动被拒、选图范围异常
Android 15edge-to-edge 强制、前台服务超时状态栏遮挡内容、后台任务被中断

分区存储是典型一课。Android 10 引入，targetSdk 29 可临时豁免；11 起强制，豁免失效。表现不是崩溃，而是读写公共目录抛 EACCES，或写进去的图库看不到。后台定位在 10 拆成独立权限，12 又分精确与模糊，只给模糊时功能静默降级。通知在 13 变成运行时权限，不申请就永远不弹。前台服务类型在 14 强制声明，少写一个 type 直接抛 MissingForegroundServiceTypeException。

每个涉及权限的版本至少覆盖三条路径：首次拒绝、使用中撤销、自动重置后再次进入。只测首次安装是最常见的漏测。

shell — 权限与前台服务验证
# 设备系统版本与包的 targetSdk
adb shell getprop ro.build.version.sdk
adb shell dumpsys package com.demo.app | grep -E "targetSdk|versionName"

# 查看运行时权限的当前状态
adb shell dumpsys package com.demo.app | grep -A3 "runtime permissions"

# 撤销通知权限，模拟用户手动关闭
adb shell pm revoke com.demo.app android.permission.POST_NOTIFICATIONS

# 模拟系统把长期未使用的应用置为不活跃并重置权限（Android 11+）
adb shell am set-inactive com.demo.app true

# 前台服务被拒时，ActivityManager 会留下明确日志
adb logcat -d -s ActivityManager:W | grep -i "foreground service"

iOS：版本能力差异与机型安全区

iOS 差异集中在系统入口和隐私弹窗。iOS 14 的 ATT 弹窗只出现一次，拒绝后无法再唤起；16 起读剪贴板会弹系统提示，自动识别口令变得尴尬；17 要求隐私清单，缺失在开发期不报错，只在提审被拒。

机型适配的核心是几何。4.7 寸没有刘海，安全区更窄；灵动岛顶部多一块不可用区域；iPad 上可能以分屏、侧拉或台前调度出现，窗口尺寸随时变化。用安全区约束而不是写死状态栏高度。

一台小屏、一台主流、一台 iPad 能覆盖绝大多数几何问题；版本差异用模拟器补，但相机、定位、通知、生物识别必须真机。

屏幕与形态：分辨率、DPI、异形屏、折叠屏、平板

布局用 dp 不用像素。360dp 宽的布局在 1080p 和 1440p 上都能铺满，真正决定形态的是最小宽度和密度。密度决定 1dp 对应多少像素，也决定切图取哪一档；高分屏图标发糊，多半是只放了一套低密度图。

异形屏看三处：刘海挖孔、状态栏高度、底部手势条。全屏播放、地图、扫码页最容易被挡。折叠屏的展开不是旋转，而是配置变更，Activity 可能重建，滚动位置和输入内容会丢。平板分屏同理，窗口跨过 sw600dp，布局要自动切换。

不用逐机型手点，把长列表、表单、底部导航、弹窗、键盘、横屏视频各过一遍，在最小宽度、最大宽度、大字体三种条件下各看一次。

shell — 屏幕、密度与形态切换
# 当前窗口与密度
adb shell wm size
adb shell wm density

# 模拟平板或折叠屏展开后的窗口（示例值，按目标机型调整）
adb shell wm size 1768x2208
adb shell wm density 320

# 观察窗口变化是否触发 Activity 重建
adb logcat -c
adb shell wm size 2208x1840
adb logcat -d | grep -E "onConfigurationChanged|com.demo.app"

# 还原，避免影响后续用例
adb shell wm size reset
adb shell wm density reset

大字体、暗黑模式与多语言

大字体最容易被忽略。调到 1.3 甚至 2.0 倍后，标题截断、按钮换行撑高、底部导航挤在一起。根因多是固定 dp 高度或写死宽高。测试要从系统设置改，不是 App 内开关。

暗黑模式两类问题：颜色硬编码；图片与 WebView 没有深色版本，被厂商强制深色反转成黑底黑字。force dark 会反转未适配的自绘控件，不崩溃，只让用户截图投诉。

多语言与 RTL 是另一维。德语俄语词长是中文两三倍，按钮最先撑破；阿拉伯语要整体镜像，箭头、进度条、轮播方向都要翻；泰语行高更高，固定行高会裁字。日期货币格式走系统本地化。

镜像方式有取舍：系统自动镜像成本低，但自定义绘制不会翻转；手工两套布局精确，但每次改 UI 都要改两遍。

shell — 字体、深色与 RTL 开关
# 系统字体放大到 1.3 倍，模拟设置里的字体大小
adb shell settings put system font_scale 1.3

# 切换深色模式
adb shell cmd uimode night yes

# 强制 RTL 布局，验证镜像是否正确
adb shell settings put global debug.force_rtl 1

# 检查当前语言与地区
adb shell getprop persist.sys.locale

厂商 ROM：四个高危差异点

厂商 ROM 改的不是 API 而是行为。第一类保活与自启动：华为、小米、OPPO、vivo 各有启动管理，默认限制关联启动和后台驻留，推送通道被清后消息要等下次打开。第二类后台限制：除系统级的后台启动 Activity 限制，厂商还拦截后台弹窗、限制后台定位，前台服务有时要用户手动确认。

第三类权限弹窗二次确认，原生授权一次就结束，ROM 可能再弹自家确认框，或把通知、悬浮窗、自启动收进权限管理页。拒绝后不再弹，功能静默失效。第四类深色实现差异，强制深色会把 WebView 和自绘控件一起反转。

还有两个高频点：手势导航的侧滑返回区与横滑抽屉冲突；分屏小窗下 Activity 重建导致白屏。这两类问题在原生系统不一定复现，必须上对应品牌真机。取证先拿设备指纹：型号、ROM 版本、构建指纹、API 级别。

shell — ROM 指纹与后台受限验证
# 设备指纹：判断具体是哪家 ROM
adb shell getprop ro.product.model
adb shell getprop ro.build.version.release
adb shell getprop ro.build.fingerprint
adb shell getprop ro.miui.ui.version.name    # 小米
adb shell getprop ro.build.version.emui      # 华为

# 打入受限待机分组，近似模拟厂商省电策略
adb shell am set-standby-bucket com.demo.app restricted

# 观察进程是否还活着、推送连接是否还在
adb shell dumpsys activity processes | grep com.demo.app
adb logcat -d -t 50 -s PushService:V

低内存与低存储：不是慢，是崩

低内存的典型表现不是慢，而是回来就没了。用户填了一半地址，切去微信再回来，页面被重建，输入全丢；或切回时白屏几秒。根因是后台进程被回收而没做状态恢复，大图列表和多路视频会加速这个过程。

测试手段三个：开发者选项的不保留活动；低内存模拟器或低配真机；反复切前后台并同时开大应用。观察 onTrimMemory 的级别和恢复后的状态。

低存储是另一条线。剩余几百兆（示例值）时，下载、解压、数据库写入、拍照保存会集中失败。升级尤其危险，下载加解压需要接近两倍临时空间，空间不足会升级失败甚至留下损坏的数据库。实现必须给出可读提示和恢复路径。

shell — 低内存与低存储模拟
# 不保留活动：每次离开页面即销毁，暴露状态恢复问题
adb shell settings put global always_finish_activities 1

# 关注 TOTAL 与 Java Heap，确认是否存在大图常驻
adb shell dumpsys meminfo com.demo.app

# 主动回收后台进程，再切回前台看恢复情况
adb shell am kill com.demo.app

# 低存储：先看剩余空间，再用模拟器磁盘配额压到临界值
adb shell df -h /data

# 记得还原，否则后续用例都会被销毁页面
adb shell settings put global always_finish_activities 0

兼容性缺陷的取证与归档

兼容缺陷最贵的不是修，是复现。开发在自己手机上跑十次都正常，因为没有那台设备、那个 ROM、那个权限状态。取证第一原则：任何一项都不能靠回忆补。型号、ROM、构建指纹、API、屏幕与密度、字体缩放、深色、语言、网络，是基础字段。

第二原则记第一次出现，当前版本只能说明问题还在，首次出现的构建号才能定位是哪次改动引入的。第三原则附件齐全：截图、录屏、logcat、最小步骤，并写清复现率。

归档按机型与 ROM 建目录，附件用用例名加时间命名，缺陷单放链接。半年后回看，能快速判断是机型特例还是普遍回归。

常见坑与排查

现象：CI 上一条版本判断用例直接报 TypeError: '>=' not supported between instances of 'str' and 'int'。原因：capabilities 里的 platformVersion 是字符串，直接和数字比较。解法：先切分取主版本再转 int，不要用字符串比大小，字典序里 9 是大于 10 的。

现象：功能在测试机上全部正常，上线后低端机大量白屏。原因：测试设备全是 12GB 内存的旗舰，低端 3GB 机型加载大图时 OOM。解法：矩阵里至少保留一台低配机，或用低内存模拟器跑主流程。

现象：权限功能在部分用户那里完全不工作，日志无异常。原因：Android 11 的权限自动重置，加上二次拒绝后系统不再弹窗，代码没有检查 shouldShowRequestPermissionRationale。解法：所有权限点都要有拒绝后引导去设置的兜底路径。

现象：某品牌手机上自绘的图表变成黑底黑字。原因：ROM 的强制深色对未适配控件做了颜色反转。解法：在主题里声明不跟随强制深色，或给自绘控件显式指定颜色。另一类高频问题是折叠屏展开后页面错位、输入内容丢失，原因是没有处理配置变更导致 Activity 重建，解法是声明 configChanges 并手动适配，或用 ViewModel 保存状态。

上线前检查清单

把兼容性验证压缩成一张表放进发版流程，任意一项不通过就不进灰度。它保证不了零缺陷，但能保证每次发版都清楚风险落在哪里。

检查项通过标准覆盖范围
最低版本安装启动冷启动无崩溃，首屏可交互最低支持版本
权限全路径首次拒绝、撤销、自动重置后均有兜底Android 10 及以上
通知可达申请权限后能收到，通道未被默认关闭Android 13 及以上
后台任务前台服务类型声明完整，后台不被静默清理Android 12 到 15
屏幕形态小屏、大屏、折叠、分屏布局均可用全部机型
字体与深色1.3 到 2.0 倍字体不截断，深色可读全部机型
语言与 RTL长词不撑破，镜像方向正确目标语言
厂商 ROM保活、权限、深色、手势四项通过华为、小米、OPPO、vivo
低资源低内存可恢复，低存储有明确提示低配机与模拟器
取证归档每个失败都带设备指纹与附件全部用例

表格每一项都对应一个可复现的失败场景；有人以用户少为由要求跳过时，回到矩阵看占比和风险分，而不是凭感觉放过。
