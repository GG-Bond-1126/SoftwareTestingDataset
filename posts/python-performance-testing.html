Python 做性能测试：压测脚本、结果收集与报告

先说结论：慢在哪，比怎么加速更重要

一套九百条的接口回归，串行跑四十二分钟（示例值）。第一反应通常是上 xdist 开八个 worker，结果压到十一分钟，看起来很成功。但一周后开始出现随机失败：同一账号并发登录被踢、库存扣减用例互相抢数据、报告里的附件串了台。加速省下的半小时，被排查 flaky 的时间又还了回去。

这篇写给已经嫌自己用例慢、正准备动手优化的测试工程师。核心主张只有一条：先把耗时拆开测量，再决定加并发还是砍开销。多数团队的用例慢，六成时间花在重复登录和固定的等待上，而不是被测服务响应慢。

一个可以立刻用的判断：如果单条用例的耗时里，被测接口本身的响应时间占比不到三成，那么优化脚本自身的收益远大于加机器，也远大于加并发。反之，如果接口本身就占七成，脚本再怎么改也只是把边角磨平。

四种开销：启动、登录、等待、IO 阻塞

启动开销包括解释器启动、导包、pytest 收集、fixture 初始化。导包是常被低估的一项，一个看似无害的重量级依赖导入就要几百毫秒（示例值），在几十个 worker 里各付一次就是分钟级。测量方法是让解释器报告导入耗时，按累计时间排序，通常能一眼看到几个意料之外的包。

登录开销的形态更隐蔽：很多用例在每条 test 里调一次登录拿 token，单次两百毫秒（示例值），乘以九百就是三分钟，而这些 token 往往还能复用。把它提到 session 级 fixture，或者用一份预生成的有效 token，是最划算的改动之一，风险是 token 过期时间要留足余量。

等待与 IO 阻塞要分开看。固定的 time.sleep 是纯浪费，应该换成条件轮询；而真正在等网络的时间，单线程下就是干等，这部分才是并发能救的。判断方法很简单：把 sleep 全部注释掉跑一遍，如果总耗时只降了一点，说明瓶颈在 IO 或被测服务，不在等待策略。

先测量：perf_counter 与 cProfile 的边界

计时用 time.perf_counter()，不要用 time.time()。前者是单调时钟，不受系统时间校准影响；后者在校时的瞬间可能倒退，用它算出负的耗时不是没发生过。精度上 perf_counter 在主流平台上足够到微秒级，压测和用例计时都够用。

分段计时比总耗时有用得多：把一条用例拆成准备、请求、断言三段分别记录，跑完看分布，才知道该优化哪一段。注意把结果写进日志而不是直接打印，否则并行执行时多个 worker 的输出会交错，读起来毫无意义。

cProfile 的边界要说清：它按函数调用统计，适合找「哪个函数被调了几十万次」，不适合找「哪个请求慢了三秒」。后者是一次性 IO 等待，剖析结果里只会显示一个占比很高的读取调用，看不出是网络还是服务端。而且剖析本身有开销，会把整体拖慢一到三倍（示例值），结论只能看相对排名，不能看绝对耗时。

python — 分段计时
import time
from contextlib import contextmanager

@contextmanager
def timed(label, sink):
    start = time.perf_counter()
    try:
        yield
    finally:
        sink.append((label, round((time.perf_counter() - start) * 1000, 1)))


def test_checkout(api, stage_log):
    stages = []
    with timed("prepare", stages):
        cart = api.post("/api/cart", json={"sku": "SKU-A", "qty": 1}).json()
    with timed("submit", stages):
        order = api.post("/api/orders", json={"cart_id": cart["id"]}).json()
    with timed("assert", stages):
        assert order["status"] == "created"
    stage_log.extend(stages)   # 由 fixture 统一落盘，避免并发打印交错

并行化前提：用例必须无共享状态

xdist 的工作方式是把用例分给多个 worker 进程，每个进程独立启动、独立收集、独立执行。这意味着任何跨用例共享的东西，包括全局变量、模块级缓存、固定账号、固定文件名，都会从「串行时恰好没问题」变成「并发时随机出问题」。

判断一条用例能不能并行，问三个问题：它写的数据有没有别人读？它用的账号有没有并发限制？它落盘的文件名是否唯一？三个都是否，才能安全并行。有一个是是，就得先改造：数据加唯一前缀、账号按 worker 分配、文件名带 worker 标识。

代价也要说清：改造成无状态会让用例变长、准备数据变慢，有些场景下为了并行做的改造比串行还慢。我的经验是，只有用例数乘以单条耗时足够大、且能改造成无状态时才值得上 xdist，否则先做上一节的减开销更实在。

python — 账号与数据按 worker 隔离
import os
import uuid

import pytest

WORKER = os.environ.get("PYTEST_XDIST_WORKER", "gw0")

@pytest.fixture
def account(account_pool):
    # 每个 worker 使用自己的一段账号，避免并发登录互相踢下线
    return account_pool[WORKER]

@pytest.fixture
def order_no():
    # 订单号带 worker 前缀，日志和清理都能定位到来源
    return f"AT-{WORKER}-{uuid.uuid4().hex[:8]}"

pytest-xdist 的三种典型翻车

第一种是同一账号并发。现象是登录接口返回 401，或者上一个会话被踢，日志里能看到同一账号的 token 交替失效。原因是服务端对单账号的会话数有限制，串行执行时永远只有一个会话，并发时才会出现两个以上，这个限制在压测里也一样成立。

第二种是同一份数据竞争：两条用例都去改同一个订单的状态，A 断言已支付的时候 B 已经改成了退款，报错信息里期望值和实际值都合法，只是时机不对。这种失败最难查，因为它无法稳定复现，本地跑十次可能一次都不挂。

第三种是落盘文件与报告目录冲突。所有 worker 默认写同一个工作目录，附件、截图、临时数据库同名覆盖，最后报告里的证据张冠李戴。解法有两个：用分组参数把有资源竞争的用例绑到同一个 worker 保证串行，或者给每个 worker 一个独立临时目录。另外 -n auto 不等于最优，worker 数超过物理核数后收益迅速衰减，本机一般取核数或核数减一。

python — 用分组标记把竞争用例串行化
import pytest

@pytest.mark.xdist_group("inventory")
def test_deduct_stock(api, order_no):
    resp = api.post("/api/stock/deduct", json={"order_no": order_no, "qty": 1})
    assert resp.status_code == 200

@pytest.mark.xdist_group("inventory")
def test_restore_stock(api, order_no):
    api.post("/api/stock/deduct", json={"order_no": order_no, "qty": 1})
    resp = api.post("/api/stock/restore", json={"order_no": order_no})
    assert resp.status_code == 200

并发模型取舍：线程、进程与 asyncio

GIL 决定了纯 Python 字节码同一时刻只有一个线程在执行，所以多线程不会让 CPU 密集的代码变快。但测试脚本里的等待绝大多数是网络 IO，线程在等套接字时会释放 GIL，因此「多线程做 HTTP 并发」是成立的，这也是线程池在压测脚本里最常见的原因。

多进程绕开 GIL，适合真正吃 CPU 的场景：生成百万级测试数据、对大文件做解析与校验、批量做签名计算。代价是进程启动和参数序列化的开销，进程间传大对象会明显变慢；在 Windows 上还要注意启动方式，不能依赖 fork 的隐式继承语义。

asyncio 适合「并发量很大、单个请求很轻」的场景，比如一次发两千个请求验证限流。它的优势是单线程内可以挂起上万个协程，内存占用远低于线程；代价是整个调用链都要异步，中间一旦出现同步阻塞调用，整个事件循环就被卡住，并发度立刻退化成一。这也是为什么异步压测要用支持异步的客户端，而不是普通同步库。

模型适合的负载优势代价
ThreadPoolExecutor几十到几百并发、以等网络为主改动最小，同步代码直接复用受 GIL 限制，CPU 密集无收益
ProcessPoolExecutor数据生成、大文件解析等 CPU 密集任务真正并行，绕开 GIL启动与序列化开销大
asyncio上千并发、单请求很轻单线程挂起上万协程，内存低全链路必须异步，一处阻塞全盘退化

连接池与 Session 复用：量级差别的来源

直接调顶层请求函数时，每次都会新建一个会话，走一次完整的 TCP 握手；HTTPS 还要加 TLS 握手。在同一台机器、同一个域名下，单次握手的成本在几十毫秒量级（示例值，跨机房更高），一千次请求就是几十秒的纯开销，与你测的接口毫无关系。

复用会话省掉的正是这部分。写压测脚本时这个差别不是百分比，而是倍数关系：对同一个服务打一千次请求，新建连接和会话复用的总耗时可能差一倍以上（示例值，取决于网络往返时间和服务的长连接配置）。所以「脚本慢」有时根本不是代码逻辑问题。

但复用有前提和风险：会话对象不是线程安全的，多线程共享一个会话在高并发下会出现连接状态错乱，正确做法是每个线程一个会话；另外复用的连接可能被服务端提前关闭，客户端会抛连接中断错误，这时应该开启适配器层的重试而不是简单重跑整条用例。

python — 带连接池与重试的会话
import threading

import requests
from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry


def build_session(pool_size=50, retries=3):
    session = requests.Session()
    retry = Retry(
        total=retries,
        backoff_factor=0.2,
        status_forcelist=(502, 503, 504),
        allowed_methods=frozenset(["GET", "POST"]),
    )
    adapter = HTTPAdapter(
        pool_connections=pool_size,
        pool_maxsize=pool_size,
        max_retries=retry,
    )
    session.mount("https://", adapter)
    session.mount("http://", adapter)
    return session


local = threading.local()

def get_session():
    # 每个线程各自持有一个会话，绝不跨线程共享
    if not hasattr(local, "session"):
        local.session = build_session()
    return local.session

测试数据：预生成与运行时生成

运行时生成数据的诱惑是每次都新鲜、不会互相干扰，但代价是准备时间进了每条用例的耗时。如果准备一个用户需要调三个接口、耗时四百毫秒（示例值），而验证只需要一百毫秒，那这条用例八成的时间花在了造数据上，优化脚本等于优化造数据。

预生成的做法是跑批前一次性生成若干份数据写到文件或数据库，用例按 worker 编号从中领取。好处是准备时间被摊薄、数据量可控；坏处是数据有生命周期，库存被扣完、优惠券过期、账号被风控，一周后这份数据就失效了，需要定期重建并留出重建脚本。

落地时通常是混合方案：账号、商品这类基础数据预生成并按 worker 分片；订单、支付这类需要状态流转的数据运行时生成，因为它们的价值恰恰在于状态变化。判断标准是这份数据在一次执行中会被改几次，改得越多越该现造。

python — 预生成并按 worker 分片领取
import json
import pathlib


def generate_users(path, total=2000):
    """一次性造好账号池，写成 JSONL。"""
    path = pathlib.Path(path)
    with path.open("w", encoding="utf-8") as fp:
        for i in range(total):
            row = {"user_id": f"U{i:06d}", "phone": f"139{i:08d}"}
            fp.write(json.dumps(row, ensure_ascii=False) + "\n")


def load_shard(path, worker_index, worker_count):
    """第 worker_index 个 worker 领取自己那一段，互不重叠。"""
    users = [json.loads(line) for line in open(path, encoding="utf-8")]
    return users[worker_index::worker_count]

结果缓存与幂等：能缓存的与绝不能缓存的

有一类接口天然可以缓存：查字典、查配置、查城市列表，数据一天不变一次。把它们的结果在 session 级 fixture 里缓存，能省掉大量重复请求；风险是当你在测的正是这个接口时，缓存会让用例永远断言到旧数据，于是「缓存导致漏检」这种事故就发生了，而且很难在评审里看出来。

判断能不能缓存看两点：这份数据是不是被测对象；这份数据在一次执行中是否允许变化。任意一条为真就不能缓存。只有既不是被测对象、执行期间又不变的数据才值得缓存，比如一份用于参数化的商品 ID 列表。

幂等的价值体现在重试上。用例失败重跑是常态，如果用例本身不幂等，重复下单会累加库存，重跑一次就污染一次数据，最后大家都不信这套回归了。造数据的接口最好带唯一业务号，让重复调用返回同一个结果，这样重跑才是安全的；反过来，验证幂等本身也是一条独立用例，不要和普通业务用例混在一起。

快与独立性：该不该为速度牺牲隔离

这是本主题唯一的价值判断。共享一份登录态能把启动时间从三十秒压到三秒（示例值），但代价是一条用例改了登录用户的资料，后面的用例全部受影响，失败原因指向一个和它完全无关的地方。省下的二十七秒，换来的是每次排查多花二十分钟。

我的原则是只共享只读的东西：token、基础配置、只读的商品列表；绝不共享会被写的东西：用户资料、库存、订单。违反这条原则换来的速度，最终都会以 flaky 的形式还回来，而且还款的时候通常是在发版前夜。

还有一个反向的坑：为了独立性把每条用例都做成端到端全流程，注册、登录、下单、支付、退款走一遍，单条四十秒，九百条就是十小时。正确做法是把验证点拆细，用状态预置替代流程重走——预置数据是准备动作，不是验证内容，两者不该混在同一条用例里。

耗时基线与回退防护

优化做完如果不留基线，三个月后一定回退。原因很朴素：有人在 fixture 里加了一句固定等待，有人引入了一个重量级依赖，单条多两百毫秒谁也不会注意，但乘以九百就是三分钟，而且没有任何一次提交看起来是错的。

基线的做法是每次流水线记录总耗时和历史对比，超过阈值就提醒而不是直接失败。机器负载会波动，直接卡死会天天误报，团队很快就会把告警静音。阈值取最近十次的中位数加两成，这个系数在我们的环境里误报可以接受（示例值），换环境需要重新标定。

慢用例排行比总耗时更有行动价值。总耗时涨了百分之五，没人知道从哪下手；而「这条用例从零点八秒变成了十二秒」可以直接定位到某次提交。把排行贴进周报，比任何优化倡议都管用，因为它把抽象的「变慢了」变成了具体的一条记录。

python — 耗时基线与阈值判断
import json
import pathlib
import statistics

BASELINE = pathlib.Path("perf/baseline.json")


def check_duration(current_total_s, tolerance=0.2):
    payload = json.loads(BASELINE.read_text(encoding="utf-8"))
    history = payload.setdefault("totals", [])
    median = statistics.median(history[-10:]) if history else current_total_s
    limit = median * (1 + tolerance)
    status = "OK" if current_total_s <= limit else "SLOW"
    print(f"本次 {current_total_s:.1f}s / 中位数 {median:.1f}s / 上限 {limit:.1f}s → {status}")

    history.append(round(current_total_s, 1))
    BASELINE.write_text(json.dumps(payload, indent=2), encoding="utf-8")
    return status

常见坑与上线前检查清单

坑一：-n auto 在容器里读到的是宿主机核数，实际可用 CPU 更少，结果开了一堆 worker 互相抢，总耗时反而变长。坑二：把并行参数和「只跑上次失败」一起用，失败集合在每个 worker 里各算一遍，等于跑了八倍。坑三：在 worker 里启动本地服务并绑固定端口，第二个 worker 直接报端口被占用。

坑四：用非单调时钟计时，偶发算出负数。坑五：把性能断言写死成绝对毫秒，在负载波动的流水线上必然 flaky，应该改成相对基线比较，或者只做趋势观察不打红。坑六：压测脚本和功能用例混在同一个进程里跑，压测的高并发把功能用例的连接池耗光，两边互相拖累。

上线前至少核对四件事：并发是否真的带来线性收益，画一张 worker 数与总耗时的曲线，通常在核数附近出现拐点；随机失败率是否上升，对比串行与并行的失败集合差集；报告与附件是否还能对上号；数据是否会被重跑污染。四项都过了，再谈把并行开关设为默认。

检查项通过标准
是否先测量再优化有分段耗时数据，热点有结论
用例是否无共享状态数据带前缀、账号按 worker 分、文件名唯一
并发模型是否匹配负载IO 为主用线程或协程，CPU 为主用进程
会话是否复用且线程安全每线程一个会话，连接池大小有依据
重跑是否安全造数据接口幂等，重跑不累加副作用
是否有耗时基线总耗时与慢用例排行入库，超阈值有提醒
