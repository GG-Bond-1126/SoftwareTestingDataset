Python 列表、字典与 JSON：测试数据的三种形态

先分清三种形态，再谈写法

有一类问题几乎每个测试团队都遇到过：用例里写死了三份订单数据，改一个字段要改三个地方；接口返回的嵌套 JSON 一层层下标取下来，某天上游删了一个可选字段，两百条用例同时报 KeyError；把响应存成基线文件做对比，第二天 diff 出几百行，仔细看只是 key 顺序变了、中文变成了 \u 转义。这些都不是语法问题，而是没分清列表、字典、JSON 各自该负责什么。

这篇写给已经能写 pytest 用例、但数据一复杂就靠复制粘贴的一线测试工程师。读完应该能判断：手上这份数据该用列表还是字典承载；跨进程传递时该序列化成什么；断言失败时该怀疑数据构造还是怀疑被测代码。

一句话概括：列表管顺序与批量，字典管按键查询，JSON 管跨语言传输与落盘。三者随时可以互转，但每一次转换都有代价，代价的大小决定了你该在哪一层停手。

三段旅程：内存结构、查询索引、传输落盘

同一条订单，在测试代码的不同阶段会以三种面貌出现。刚从接口拿到时是一段字符串，属于传输形态；json.loads 之后变成字典和列表的组合，属于内存形态；你把它按业务主键重建成字典，它才成为查询索引。分清这三种形态的价值在于：你随时知道自己手上是什么，也就知道下一步哪些操作便宜、哪些操作昂贵。

字典的按键取值是哈希查找，平均 O(1)，一千条数据里找一条和十条里找一条几乎没有差别；列表按值查找是线性扫描，in 会随规模变慢，一万条以上放进循环就能明显感觉到。所以凡是「按 ID 找记录」的断言，都应该先把列表转成以 ID 为键的字典，再做查询，而不是在循环里反复判断存在性。

传输形态不关心查询效率，只关心体积与兼容性。JSON 的键必须是字符串，值只能落在有限的几种类型里，因此 Python 的 set、datetime、Decimal 都要先降级成列表、字符串、浮点数才能序列化。很多人第一次写 json.dumps 报 TypeError: Object of type datetime is not JSON serializable，根因就是把内存形态直接扔给了传输层。

形态典型载体强项代价
内存结构list / dict可迭代、可修改、可直接断言占内存，跨进程必须序列化
查询索引以业务主键为键的 dict按键取 O(1)键必须唯一，重复会被静默覆盖
传输落盘JSON 字符串或文件跨语言、可 diff、可归档类型受限，需要处理编码与转义
python — 同一条数据的三种形态
import json
from decimal import Decimal

raw = '{"order_id": "ORD-001", "amount": 99.99, "status": "paid"}'

# 传输形态：还没解析的字符串
print(type(raw))                    # <class 'str'>

# 内存形态：字典
order = json.loads(raw)
print(type(order))                  # <class 'dict'>

# 查询索引：以业务主键为键重建
by_id = {item["order_id"]: item for item in [order]}
print(by_id["ORD-001"]["amount"])   # 99.99

# 回到传输形态：Decimal 不能直接序列化
order["amount"] = Decimal("99.99")
try:
    json.dumps(order)
except TypeError as exc:
    print(exc)   # Object of type Decimal is not JSON serializable

列表与推导式：用例参数化的骨架

场景很具体：一个下单接口要覆盖 5 种商品、3 种优惠券、2 种支付方式，手写三十条用例不现实，但全排列的三十种组合里有一半业务上不成立，比如 C20 券只能用于指定品类。这时列表推导式不是炫技，而是唯一能把「组合规则」和「用例数据」写在同一个地方的手段。

写法上建议把数据构造和执行彻底分开：先算出用例列表，再交给 parametrize。这样组合规则写错时，你可以在几十毫秒内打印出这份列表核对，而不用等 pytest 收集完、跑起来才逐条看用例 ID 反推。

代价要说清：推导式里塞三层 for 加两个 if，可读性会迅速下降到没人敢改。我的经验线是超过两层循环、或者超过六十行，就该改成显式循环加 append，或者抽成 build_cases() 函数并给它补两三条断言。测试代码同样要被维护，可读性比省三行更重要。

python — 组合规则与参数化
import pytest

SKUS = ["SKU-A", "SKU-B", "SKU-C"]
COUPONS = [None, "C10", "C20"]
PAY_METHODS = ["balance", "card"]

# 组合规则集中在一处：C20 只适用于 SKU-A
CASES = [
    (sku, coupon, pay)
    for sku in SKUS
    for coupon in COUPONS
    for pay in PAY_METHODS
    if coupon != "C20" or sku == "SKU-A"
]

@pytest.mark.parametrize(
    "sku,coupon,pay",
    CASES,
    ids=[f"{sku}-{coupon}-{pay}" for sku, coupon, pay in CASES],
)
def test_create_order(api, sku, coupon, pay):
    body = {"sku": sku, "coupon": coupon, "pay_method": pay}
    resp = api.post("/api/orders", json=body)
    assert resp.status_code == 201

不要省略 ids。默认的用例 ID 是 sku0-coupon0-pay0，跑失败时你根本不知道是哪组参数；显式给 ID 之后，-k 能按商品或券直接筛，报告里也能一眼看出失败的是哪一类组合。

字典：把响应变成可查询的索引

断言列表型响应时，最常见的写法是 assert len(resp['items']) == 3，这个断言几乎不携带信息，它只能说明数量对。真正要验证的是这三条记录分别是哪三条、关键字段值对不对。做法是先建索引，再比对投影出来的字段。

字典推导在这里干两件事：把列表转成以业务主键为键的字典，让后续取值变成 O(1)；把关注字段投影出来，让断言只比较业务关心的部分。第二点常被忽略，接口多返回一个 updated_at 就让整份断言失败，这种脆弱断言是回归阶段最大的噪音来源。

但字典有个硬限制：键必须唯一。列表里出现两条同 ID 记录时，无论是分页边界重复还是上游 join 放大，字典推导都会静默地只保留后一条，长度从三变成二。如果你的断言正好没检查数量，一个数据重复的缺陷就被放过去了。所以建索引之后必须补一句数量断言。

python — 建索引并校验主键唯一
def index_by(rows, key):
    """把列表建成字典，同时校验主键唯一。"""
    index = {}
    for row in rows:
        value = row[key]
        if value in index:
            raise AssertionError(f"主键重复：{key}={value}")
        index[value] = row
    return index


resp = api.get("/api/orders?page=1&size=50").json()
rows = resp["data"]["list"]
by_id = index_by(rows, "order_id")
assert len(by_id) == len(rows)

# 只投影业务关心的字段，避免 updated_at 之类的噪音
actual = {oid: (r["status"], r["amount"]) for oid, r in by_id.items()}
expected = {"ORD-001": ("paid", 99.99), "ORD-002": ("pending", 199.98)}
assert actual == expected

嵌套取值：链式 get 的安全写法与代价

线上最典型的失败长这样：KeyError: 'address'，堆栈指向 data['user']['address']['city']。这不是代码写错，而是上游把一个可选字段从响应里摘掉了，而断言的写法假定它一定存在。

链式 get 能解决报错，但解决不了信息量问题：某一层缺失时它返回默认值，随后的断言只告诉你 None != 上海，看不出是第几层缺的。我的做法是写一个几行的取值助手，缺哪层就把完整路径和当前层的键打出来，排查时不用再回去读代码。

反过来说，不是所有取值都该用 get。对协议约定必须存在的字段，比如 code、data、业务主键，就该用下标，让它 KeyError，因为缺了就是接口违约，早崩比晚崩好。判断标准只有一条：这个字段缺失时，是上游 bug 还是合法状态。前者用下标，后者用 get 加默认值。

python — 带路径信息的取值助手
MISSING = object()

def pick(payload, path, default=MISSING):
    """按 a.b.c 逐层取值，缺失时抛出带路径的错误或返回默认值。"""
    current = payload
    for key in path.split("."):
        if not isinstance(current, dict) or key not in current:
            if default is not MISSING:
                return default
            here = list(current) if isinstance(current, dict) else type(current).__name__
            raise KeyError(f"响应缺少字段 {path}，断在 {key}，当前层：{here}")
        current = current[key]
    return current


assert pick(resp, "code") == 200
city = pick(resp, "data.user.address.city", default=None)

json.load 与 json.loads：字符串与文件的岔路口

两个函数的区别只有一处，但用错一次就要排查一阵：loads 收字符串，s 代表 string；load 收文件对象。反过来用，报错分别是 AttributeError: 'str' object has no attribute 'read' 和 TypeError: the JSON object must be str, bytes or bytearray, not TextIOWrapper，看到哪个就知道方向反了。

除了入口不同，两者的参数完全一致，都支持 object_hook、parse_float 这类钩子。真正需要区分的是另一组：dump 写文件，dumps 返回字符串。序列化到磁盘时如果想让人读得懂，一定加 ensure_ascii=False，否则文件里全是转义序列，基线 diff 完全没法看。

还有一个容易踩的点：resp.json() 内部就是解析响应体，但它会先看 Content-Type 猜编码。如果服务端返回 text/html 而内容是 JSON，会抛 JSONDecodeError: Expecting value: line 1 column 1。这时候自己按 UTF-8 解码再解析，反而更可靠，代价是要多写一行。

python — 四个入口别用反
import json
import pathlib

BASELINE = pathlib.Path("baselines/order.json")

# 文件 → 对象（load，不是 loads）
with BASELINE.open(encoding="utf-8") as fp:
    expected = json.load(fp)

# 对象 → 文件（dump，不是 dumps）
BASELINE.parent.mkdir(parents=True, exist_ok=True)
with BASELINE.open("w", encoding="utf-8") as fp:
    json.dump(expected, fp, ensure_ascii=False, indent=2, sort_keys=True)

# 字符串 → 对象 / 对象 → 字符串
text = '{"code": 200, "msg": "成功"}'
data = json.loads(text)
print(json.dumps(data, ensure_ascii=False))

# 服务端 Content-Type 不可信时，自己解码再解析
payload = json.loads(resp.content.decode("utf-8"))

编码与中文：ensure_ascii 改的到底是什么

很多人以为中文被转义成 \u6210\u529f 是编码问题，其实不是。JSON 规范里转义写法和直接写中文都合法，Python 只是默认选了 ASCII 安全的那种，好处是任何老编辑器、任何终端都不会乱码。设成 ensure_ascii=False 才会输出真正的中文，代价是文件必须以 UTF-8 保存，读的时候也必须按 UTF-8 打开。

在 Windows 上这是最常见的翻车点。open 不带参数时按系统默认编码处理，中文环境里往往不是 UTF-8，写进去的中文在别人机器上打开就是乱码，报错是 UnicodeDecodeError: 'utf-8' codec can't decode byte 0xb3 in position 0。所有涉及文件的读写都应该显式写 encoding='utf-8'，这是唯一跨平台稳定的写法。

取舍在于用途：给人看的基线文件用可读中文加 UTF-8，diff 时能看清哪个中文字段变了；要经过老旧系统、或者只给机器比的中间文件，保持默认转义更保险，代价是人眼几乎没法读。两边成本都不高，关键是团队内统一，而不是一半人一种写法。

去重、分组与排序：断言比对的三件工具

列表型响应的比对，八成麻烦来自三件事：顺序不稳定、有重复、需要按分组核对。顺序不稳定最常见，数据库没写 order by，两次查询返回顺序不同，assert actual == expected 就随机失败。这时不是数据错，是断言写法错。

去重用 set，但要记住它会丢掉顺序和重复次数：两条完全相同的记录会合成一条，于是「重复插入」这种缺陷反而被测试自己掩盖了。要保留重复就先用 Counter 统计次数，或者用 dict.fromkeys 做保序去重。分组用 defaultdict(list)，比手写判断加初始化少三行，也不容易写错。

排序方面，sorted 的 key 可以返回元组，实现先按第一个字段、相同再按第二个字段。两个坑必须记住：字段可能为 None 时，混合类型比较会抛 TypeError: '<' not supported between instances of 'NoneType' and 'str'，要给它一个哨兵值；字符串排序是字典序，10 会排在 9 前面，数字型 ID 要先转成整数再排。

python — 去重、分组与多字段排序
from collections import Counter, defaultdict

rows = [
    {"sku": "SKU-A", "status": "paid", "amount": 10},
    {"sku": "SKU-B", "status": "paid", "amount": 20},
    {"sku": "SKU-A", "status": "refund", "amount": 10},
    {"sku": "SKU-A", "status": "paid", "amount": 10},
]

# 保序去重：保留首次出现顺序
unique = list(dict.fromkeys(r["sku"] for r in rows))
print(unique)                       # ['SKU-A', 'SKU-B']

# 统计次数，防止重复记录被 set 吞掉
counts = Counter(r["sku"] for r in rows)
assert counts["SKU-A"] == 3, counts

# 分组
by_sku = defaultdict(list)
for row in rows:
    by_sku[row["sku"]].append(row["status"])

# 多字段排序：金额降序，金额相同按 sku 升序
ordered = sorted(rows, key=lambda r: (-r["amount"], r["sku"]))

深浅拷贝：改断言数据顺手改了源数据

这个坑的经典形态：conftest 里有一个基础订单 fixture，用例里想试一下金额改成零会怎样，于是直接赋值再修改，断言通过了，但下一条用例拿到的基单金额已经是零。排查时看到的现象是「单独跑通过、一起跑失败」，而且失败顺序不固定，非常费时间。

根因是赋值只绑定名字，不复制对象。要隔离有三档：list()、dict()、copy.copy() 只复制最外层，嵌套的列表和字典仍然共享；copy.deepcopy() 递归复制全部，慢但安全。测试数据一般只有几 KB，深拷贝的开销可以忽略，别为省这点时间埋雷。

但深拷贝也不是万能：文件句柄、数据库连接、线程锁这些对象不可深拷贝，典型报错是 TypeError: cannot pickle '_thread.lock' object。所以 fixture 交给用例的应该是纯数据结构，而不是带着连接的会话对象；两类东西不要塞进同一个字典里。

python — 赋值、浅拷贝与深拷贝
import copy

base_order = {"order_id": "ORD-001", "amount": 99.99,
              "items": [{"sku": "SKU-A", "qty": 2}]}

# 错误：两个名字指向同一对象
alias = base_order
alias["amount"] = 0
print(base_order["amount"])          # 0，源数据被改了

# 浅拷贝：外层独立，嵌套仍共享
shallow = copy.copy(base_order)
shallow["amount"] = 1
shallow["items"].append({"sku": "SKU-B", "qty": 1})
print(len(base_order["items"]))      # 2，嵌套被改了

# 深拷贝：完全隔离
safe = copy.deepcopy(base_order)
safe["items"].clear()
print(len(base_order["items"]))      # 2，源数据不变

类型映射：null、true、false 与 None、True、False

JSON 只有三个字面量：null、true、false，对应 Python 的 None、True、False。映射本身很直接，但断言里最常见的错是拿字符串去比，结果是 'true' != True，看起来像差一对引号，实际是类型错。

反向的问题更隐蔽：Python 的 True 序列化成 true，整数 1 序列化成 1，而在弱类型语言里两者常常相等。于是接口把布尔字段写成 0 或 1，前端不报错、后端不报错，只有做了严格类型断言的测试能发现。这类字段除值断言外，应该补一条类型断言。

还有一个坑是空值与缺失的区别：字段存在但值为 null，和字段根本不存在，业务含义经常不同，比如清空备注与不改备注。区分方法是用 is None 判断值、用 in 判断存在，不要都用 get 一把梭，否则两种情况会被抹平成同一个结果。

python — 字面量映射与类型断言
import json

raw = '{"is_vip": true, "balance": null, "tags": []}'
data = json.loads(raw)

assert data["is_vip"] is True       # 不要写成等于字符串 true
assert data["balance"] is None      # 字段存在但为空
assert "balance" in data
assert data["tags"] == []

# 反向：Python → JSON
print(json.dumps({"ok": True, "none": None, "n": 1}))
# {"ok": true, "none": null, "n": 1}

# 防止 0/1 混进布尔字段
assert isinstance(data["is_vip"], bool), f"is_vip 类型错误：{type(data['is_vip'])}"

大 JSON：增量处理与内存上限

全量响应几百 MB 时，json.load 会把整个文档读进内存再构造对象，峰值内存通常是文件大小的五到十倍（示例值，取决于嵌套深度和字符串平均长度）。在 8 GB 的构建机上解析一份 300 MB 的导出文件很容易被系统杀掉，现象是进程直接消失，日志里没有任何 Python 异常。

处理思路分两层。如果文件是每行一个对象的 JSONL，逐行解析即可，内存只跟单行大小相关，改动成本最低；如果是标准的大数组，就要用流式解析器按事件遍历，只把需要的字段投影出来、其余丢弃。代价是代码复杂度和速度都会变差，流式解析比内置模块慢一个数量级属于正常（示例值）。

还有一条更省事的路线：先问清楚这份数据是不是必须在测试进程里解析。如果只是核对统计结果，交给数据库或命令行工具更合适；只有必须写断言、必须留痕的场景，才值得为它写流式解析。判断标准是数据规模和复用次数，一次性的临时文件不值得配上百行代码。

python — 逐行处理大文件
import json

matched = 0
with open("orders.jsonl", encoding="utf-8") as fp:
    for lineno, line in enumerate(fp, start=1):
        line = line.strip()
        if not line:
            continue
        try:
            row = json.loads(line)
        except json.JSONDecodeError as exc:
            raise AssertionError(f"第 {lineno} 行不是合法 JSON：{exc}") from exc
        if row.get("status") == "paid" and row.get("amount") > 100:
            matched += 1
print(f"命中 {matched} 条")

常见坑、取舍与上线前检查清单

坑一：金额用 == 比较。99.99 这类浮点数跨语言、跨数据库都会在最后一位上有差异，正确做法是判断差值小于一分钱，或者统一转成整数分再比。坑二：把响应对象直接当基线缓存，对象里带连接和编码状态，序列化必然失败，正确做法是先取 JSON 再落盘。

坑三：参数化时用字典当 ID，pytest 会把整个字典拼进用例名，方括号和逗号让 -k 筛选几乎不可用，正确做法是显式给 ids。坑四：JSON 数字解析后整数是整数、带小数点的是浮点，1 == 1.0 在 Python 里成立，看起来没问题，但落盘后一个带小数点一个不带，基线 diff 会长期抖动。

取舍总结：能用纯字典和列表表达的就别引入 DataFrame，后者适合批量数值计算，不适合逐条断言；能用内置 json 就别上第三方加速库，后者快但返回字节串，团队里第一次见要愣几秒；跨进程传数据用 JSON 不用 pickle，pickle 又快又省事，但反序列化即执行代码，拿外部文件在 CI 上解开是明确的安全风险。
