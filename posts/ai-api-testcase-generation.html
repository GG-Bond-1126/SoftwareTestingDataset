AI 生成接口测试用例：从接口文档到可执行用例

先把边界划清：接口用例与业务用例

这篇文章只讲一条线：接口（契约）测试用例。它按接口契约组织，回答的是「传什么参数，命中哪条校验，返回什么字段和状态码」。字段必填、类型、长度、枚举、分页、幂等键、4xx 与 5xx 的区分，都是接口用例的断言对象。一句话边界：接口用例按字段、参数、状态码、边界组织，业务用例按用户场景组织。

业务测试用例是另一条线。它按用户场景和业务规则组织，回答的是「谁，在什么条件下，从哪个页面进入，做了什么，最终看到什么结果」。一个下单场景、一条退款规则、一次权限变更，都属于那条线。那条线另有一篇单独讲，本文不展开，也不在示例里出现任何页面断言。

混在一起生成，是很多团队第一个踩的坑。写接口用例时让模型顺手从页面入口开始点，结果用例既不像接口用例，也不能直接进接口自动化；写业务用例时让它断言 code=200 与 data.orderId，又被前端改版拖死。两类用例的输入材料、评审人、执行方式、失败定位全都不同，应该分开生成、分开维护。

维度接口测试用例业务（功能）用例
组织维度接口契约与参数组合用户场景与业务规则
输入材料OpenAPI 文档、字段约束、错误码表需求点、业务规则、页面流程、数据字典
断言对象响应字段、类型、错误码、幂等性页面文案、状态变化、消息、单据状态
执行方式接口自动化人工执行或 UI 自动化

归属 skillapi-testcase-generationbusiness-case-generation

一个实用判断标准：如果这条用例必须知道 URL、参数名、状态码或字段类型才能执行，它属于接口用例；如果它换一套前端实现仍然成立，它属于业务用例。按这条标准分流，两类用例的边界基本不会打架。

这个 skill 管什么、不管什么

这个 skill 只做一件事：把已经定稿的接口文档，转成能直接落进接口自动化的用例。输入是文档，输出是用例表，中间不产代码。它依赖的上下文只有三类：用户提供的接口文档原文、当前会话上下文、本 skill「输入」一节列出的文件。除此之外，它不自由发挥。

它管的内容是契约层：路径与 HTTP 方法、请求参数（必填、类型、长度、枚举、默认值）、响应体关键字段、状态码映射、鉴权要求、幂等与并发约束。它不管的内容也很明确：不写 Python 脚本、不写框架选型、不设计用例目录规范、不做压测与安全渗透。管与不管的边界如果守不住，输出的用例就会变成「半成品脚本」，接口自动化团队接不住，纯手工团队又用不上。

这个 skill 的第一条硬性约束是：只依据引用文档与当前上下文输出，禁止编造字段名、状态码、参数名；信息不足的部分必须进入「待确认清单」，不许拿经验值补上。后面每个环节都建立在这条约束上。

上下文怎么给：九类材料，各有粒度

接口用例的质量，八成取决于喂进去的上下文。喂少了，模型会编字段；喂多了，它抓不住重点。我的经验是九类材料，缺一类就会在某一类用例上系统性失守。粒度比数量重要：把整份 OpenAPI 文件扔进去，模型分不清哪段是本次要覆盖的；把每个字段的校验都贴进去，又和业务规则串味。下面这张表是我们实际使用的给法。

材料给什么粒度缺失后果
接口文档路径、方法、请求参数、响应体、状态码映射只贴本次范围的接口，一个模块一批参数与状态码全靠编
字段表字段名、类型、必填、长度、枚举、默认值原表粘贴，不改写措辞边界与异常全漏
错误码表状态码、错误码、含义、触发条件只贴与本次规则相关的条目异常分支写不出断言
鉴权说明token 获取、请求头字段、角色权限矩阵原表粘贴越权用例无法落地
环境信息测试环境地址、账号角色、可写数据范围脱敏后给前置数据写不出具体值
请求样例一份真实可复现的请求与响应脱敏后原样粘贴请求体结构靠猜
业务约束金额精度、库存扣减、幂等键位置与接口相关的规则一行一条幂等与并发用例缺失
历史用例编号、标题、入参摘要只给这三列，不贴全文重复造用例，颗粒度不一致
历史缺陷根因分类、发生次数、触发场景归到根因，不复述单个缺陷同类问题继续漏

接口文档：只喂本次范围，一次一个模块

OpenAPI 或 Swagger 文件通常很大。我们只贴本次要覆盖的接口段落，一个模块一批，20 到 40 个接口是试下来最稳的批次大小。每个接口带上路径、方法、请求参数、响应体、状态码映射，缺一样就得让模型补一样。跨模块混喂，字段名和状态码会串味，编号也会乱。

字段表与错误码表：原文粘贴，不改写

字段表原样粘贴，字段名、类型、必填、长度、枚举、默认值一个不少。错误码表只贴与本次规则相关的条目，贴多了模型会把不相干的错误码也编进断言。这两份材料的原文措辞是 skill 的唯一断言依据，改写一个字，就可能让模型误判。

鉴权说明与请求样例：越权用例的前提

鉴权说明写清 token 怎么拿、请求头字段叫什么、每个角色的权限矩阵。没有它，越权用例就写不出「用哪个角色的 token 去调哪个接口」。请求样例给一份真实可复现的请求与响应，脱敏后原样粘贴，模型才能照着搭请求体，而不是按通用模板编一个。

九类材料都要带版本号与生效日期。skill 只依据这些上下文和引用文档输出，材料里没写清的东西，一律进待确认清单，不补不猜。

历史文档怎么挂：目录、清单与冲突裁决

历史文档不是越多越好。旧版接口文档、已废弃字段、三年前的缺陷单一起塞给模型，它会认真地把已经下线的字段和旧状态码写进用例，而且写得很顺。要做的是三件事：固定目录、维护清单、标清废弃。

目录约定

目录按模块和版本两级切分，当前生效版本单独一层，废弃版本整套挪走。这样引用路径本身就带版本信息，不需要再靠文件名猜。

引用方式：只认清单里的路径

skill 不自由搜索目录。输入里给一份明确的引用清单，每条写「用途 + 路径 + 章节」，模型只允许读清单里的内容。我们实际给的形式大概是这样：

  • 接口文档：docs/openapi/order/v1.4/openapi.yaml 的 POST /orders 与 GET /orders/{id} 两节。
  • 历史用例：docs/cases/order/v1.4/api-cases.md 的编号与标题列。
  • 历史缺陷：docs/defects/2026-H1-order-api.md 的根因汇总表。
  • 参数校验：docs/code/order-param-validation.md 的字段校验片段。

代码里的参数校验逻辑是接口用例的重要补充。文档里常漏写边界和枚举，代码里却写得明明白白。我们让开发把 @NotNull、@Size、枚举校验这类注解摘录成一份 code/ 目录下的文档，skill 只引用这份摘录，不直接读源码，避免把实现细节当断言依据。

过时文档怎么标记

三个动作同时做：把文件挪进 deprecated/；在文件首行加 STATUS: DEPRECATED 和 SUPERSEDED-BY: v1.4；在 DEPRECATED.md 里登记。只做其中一个都不够。清单里只保留生效版本，引用清单一律不给旧路径。

冲突以哪份为准

我给的优先级是：当前生效版本的接口文档，高于最新评审通过的字段表与错误码表，高于代码参数校验摘录，高于旧版文档与旧用例。前三层仍有冲突时，不自行取舍，而是并列写进待确认清单，由接口负责人裁决。接口用例写错的代价，远高于多问一句。

冲突场景处理方式
接口文档与字段表不一致以字段表为准并标注，同时列入待确认清单
代码校验与文档不一致不按代码改文档，列为缺陷候选并进待确认
历史用例与当前文档不一致以当前文档为准，旧用例标记失效
新旧版本状态码冲突并列两种说法，不选，交接口负责人

提示词骨架：把输入槽位和护栏写死

这是我给接口用例 skill 用的提示词骨架。它不追求让模型更聪明，只做三件事：固定输入槽位、固定输出列、固定不知道时的出口。槽位对应上一节的九类材料，出口对应待确认清单。护栏里最重要的一条是：字段名、状态码、参数名只允许取自引用文档，编一个都不行。

prompt — 接口用例生成
角色：你是一名有 8 年后端接口测试经验的测试工程师。

任务：依据下方引用材料，为指定模块的接口生成可执行的接口测试用例。

一、输入（只允许使用以下内容，不要补充材料里没有的字段或状态码）
1. 模块：{{module}}
2. 接口文档：{{openapi_doc}}（路径、方法、请求参数、响应体、状态码映射）
3. 字段表：{{field_table}}
4. 错误码表：{{error_code_table}}
5. 鉴权说明：{{auth_notes}}
6. 环境信息：{{env_info}}
7. 请求样例：{{request_samples}}
8. 历史用例编号与标题：{{history_cases}}
9. 历史缺陷根因与次数：{{defect_root_causes}}
10. 引用清单：{{reference_index}}（文件路径 + 章节）

二、输出格式（Markdown 表格，列固定，顺序不可调整）
用例编号 | 接口 | 方法 | 前置条件 | 请求参数 | 预期状态码 | 预期响应断言 | 异常分支 | 关联需求

三、写作要求
1. 每条用例必须绑定一个接口路径和一个文档来源。
2. 预期状态码只取文档状态码映射表里的取值，不自行编造。
3. 预期响应断言至少写一个响应体关键字段的取值或类型，不只写状态码。
4. 请求参数必须是具体值；金额、时间、状态要写清构造方式。
5. 等价类与边界值：有取值范围的字段写最小、最小减一、最大、最大加一。
6. 异常分支至少覆盖：缺字段、类型错误、非法枚举、越权、重复提交、下游超时。
7. 同一接口、同一入参组合、同一预期视为重复，只保留一条。
8. 不写自动化脚本、不写框架选型、不写用例目录规范。

四、不知道怎么办
1. 材料没写清的字段名、状态码、参数名，不要猜，全部进入「待确认清单」。
2. 基于经验补出的内容用「推断：」开头，并标置信度（高 / 中 / 低）。
3. 文档与代码不一致的，并列两种说法，不自行取舍。

五、输出结尾必须包含
## 待确认清单
| 序号 | 缺失或不确定的内容 | 影响 | 需要谁提供 |
没有待确认项时写「无」，不许省略这一节。

这套骨架里真正起作用的是第四节。模型在缺信息时的默认行为是补一个看起来合理的状态码，补得越顺越难发现。给它一个明确出口，它才会把不确定的部分留下来，而不是替你决定。skill 只依据引用文档和上下文输出，这一条靠第四节落实。

输出规范：一条接口用例的九个字段

字段不是越多越好，但下面九个我一个都不建议省。省掉任何一个，评审或执行时都会有人来问。字段顺序也固定下来，导入用例库时可以按列直接映射。

方法HTTP 方法，与文档一致POST

请求参数具体值，不用形容词amount=99.00；couponId=空

请求参数：写具体值，禁用形容词

接口用例的请求参数必须能直接填进工具里跑。金额写 99.00，不写「有效金额」；时间写清构造方式，不写「合理时间」。四个禁用词和业务用例一致：有效、合法、正常、合理。

预期响应断言：不止状态码

只断言状态码的用例是不合格的。状态码只说明请求被接受还是拒绝，说明不了业务对不对。每条用例的断言点分三层：状态码、响应体字段、数据副作用（数据库记录或下游服务状态）。至少有一个响应体关键字段的断言，这条用例才算能落地。

异常分支：写明触发条件，不写「异常情况」

异常分支要写清触发的校验条件或资源状态：是字段缺失，还是类型错误，还是越权，还是重复提交。只写「异常情况」四个字，执行时没人知道要造什么数据。skill 只依据引用文档里的错误码表和校验规则来写异常分支，文档里没有的分支，进待确认清单。

等价类、边界值与异常权限并发怎么列全

接口用例最容易漏的三块，正好是等价类、边界值、异常权限并发。让模型列全的办法不是多问一句「还有吗」，而是把方法写死，逐条点名。

等价类：合法与非法各一半

对每个有取值范围的字段，合法取值和非法取值都要列。例如订单金额 amount 是 0 到 100000 的整数，合法等价类取一个正常值，非法等价类取负数、超上限、小数、字符串四种。很多人只列合法值，非法值留到执行时临场想。

边界值：上下界与越界一格

边界取四个点：最小、最小减一、最大、最大加一。例如字段长度上限 50，边界用例写 50、49、51、0。这四个点缺一个，就越界或临界那条漏测。这条规则直接写进 skill 的执行步骤，模型不会自己想起来。

异常、权限、并发：三类各点名

异常分支点名六种：缺字段、类型错误、非法枚举、越权、重复提交、下游超时。权限单独点：需要登录态的接口写清角色，越权用例至少一条，注明用哪个角色的 token。并发单独点：写操作接口至少一条重复提交或幂等用例，写明幂等键位置和预期只成功一次。三类都点名之后，skill 才不会把「异常」理解成「参数不对」一种。

判定方法是覆盖统计：每个接口至少覆盖正常、参数异常、鉴权失败三类；有取值范围的字段必须有边界四个点；写操作接口必须有幂等用例。任一为 0，说明这一批上下文或历史文档没给全，回退补料，而不是让模型硬凑。

人工复核与落地到用例库

生成只是中间产物。我们的流程是：AI 出稿，测试同学按字段自检，接口负责人评审，导入用例库，下一版本再把本次用例回填成历史材料，形成闭环。每一步都有明确的拒绝条件，避免看起来差不多就放过去。

  1. 自检看三样：有没有编造的状态码，有没有形容词式请求参数，有没有只断言状态码的用例。
  2. 评审只细看异常分支和幂等用例，正常流抽查；状态码与文档不符的整批打回。
  3. 导入前统一编号，模块内连续，避免和存量用例撞号。
  4. 下一版把本版用例的编号与标题回填到历史用例槽位，用于去重和颗粒度校准。

不要跳过评审直接入库。接口用例最大的风险不是写错，而是写得像对的。一条「预期 200，data 非空」的用例，如果当前文档已经把该接口改成 201 加 Location 头，读起来毫无破绽，跑起来才发现整条都是错的。

踩坑与边界

  • 状态码靠常识编：文档里只写了 400，用例里却断言 422，理由是「一般后端都这么返回」。处理方式是状态码只取文档映射表，文档没写就进待确认清单。
  • 只断言状态码：预期写成「返回 200 成功」，没有响应体字段断言，跑通了也证明不了业务对。处理方式是要求至少一个响应体关键字段断言。
  • 请求参数全是形容词：写「有效金额」「合法手机号」。处理方式是要求具体值，并在质量清单里禁用有效、合法、正常、合理四个词。
  • 异常用例只用不存在的 ID：所有异常都用「不存在的订单号」，不区分格式错误与资源不存在。处理方式是异常分支按校验规则点名，缺字段、类型错误、越权各写一条。
  • 旧文档污染：引用了已下线的字段和旧状态码。处理方式是只给清单里的生效路径，旧文档挪进废弃目录并标状态。
  • 前置数据写「已存在」：前置条件写「已存在订单」，执行时没人知道是哪一条。处理方式是写清需要先创建什么、用哪个角色账号、依赖哪个接口的返回值。

# 接口测试用例生成：从接口文档到可执行用例

## 硬性约束（优先级最高，与其他章节冲突时以本节为准）

1. 只能依据三类信息输出：用户提供的需求文档 / 接口文档 / 代码 / 日志原文、当前会话上下文、本 skill「输入」一节所列的文件。禁止凭想象补充业务规则、字段名、接口地址、阈值、状态码、版本号或历史数据。
2. 每条产出都要可回溯，必须标注来源：文档章节或条款、文件路径与行号、日志片段、接口字段。标不出来源的条目不得进入正式产出。
3. 信息不足时不许编造填补。缺失项一律进入「待确认清单」，逐条写清：缺什么、影响哪条结论、需要谁提供。
4. 凡是基于经验补出的内容，必须以「推断：」开头，并写明依据与置信度（高 / 中 / 低）。置信度为低的推断不能当结论用。
5. 禁止虚构引用：不编造文档条款号、版本号、链接、指标数值、报错原文。引用原文时逐字摘录并注明位置。
6. 资料互相矛盾时（文档与代码不一致、两处规则冲突）不要自行取舍，把两种说法并列，标明冲突点和需要确认的问题。
7. 输出前逐条自检：这条有来源吗？没有就移到「待确认清单」。自检不通过不许输出。

## 待确认清单（输出必带）

无论信息是否充足，输出末尾都保留这一节；没有待确认项时写「无」，不许省略该节。每行格式：

| 序号 | 缺失或不确定的内容 | 影响 | 需要谁提供 |

## 适用场景

- 接口文档已定稿，需要把契约转成能直接执行的接口级用例。
- 服务改造或版本升级，需要按新旧文档差异补回归用例。
- 前后端联调前，需要一批不依赖页面的接口冒烟用例。
- 业务用例已覆盖用户场景，但契约层边界（必填、类型、长度、枚举、状态码）大量缺失。
- 历史接口缺陷反复出现，需要按接口维度做一次系统性补测。

以下情况不要用：

- 接口文档还停留在口头约定，字段与状态码都没写清，先补文档再生成。
- 目的是压测、稳定性或安全渗透，应使用对应专项 skill。
- 目的是验证页面渲染与交互，应使用 UI 自动化相关 skill。
- 接口还没有测试环境与可用账号，生成出来也无法执行。

## 输入

必需：

1. 接口文档：OpenAPI 3.0 / Swagger 2.0 文件，或接口管理平台导出的 Markdown，至少包含路径、方法、请求参数、响应体、状态码映射表。
2. 鉴权说明：token 获取方式、请求头字段名、角色清单与权限矩阵。
3. 环境信息：测试环境地址、可用测试账号的角色说明、可写入的测试数据范围。
4. 范围清单：本次要覆盖的接口列表或模块名，一次只喂一个模块。
5. 业务约束：与接口相关的业务规则，例如金额精度、库存扣减方式、幂等键位置。

建议补充：

6. 旧版接口文档与废弃字段、下线接口清单，用于识别字段增删与行为变更。
7. 历史接口缺陷，至少含接口路径、缺陷现象、根因分类、发生次数。
8. 代码里的参数校验逻辑，用于补齐文档没写清的边界与枚举。
9. 上下游依赖清单：被测接口依赖的服务、数据库表、消息主题。

输入缺失时：把缺失项写进「待确认清单」，并在用例表里把相关字段标为未确认，不要用猜测值替代。缺鉴权说明时不要生成鉴权类用例，改为在待确认清单里要。

## 上下文与历史文档规范

### 本次任务需要的材料

| 材料 | 截取哪一部分 | 贴入方式 | 全文还是摘要 |
| --- | --- | --- | --- |
| OpenAPI 文档 | 本次模块的路径、方法、参数、响应体、状态码映射 | 只贴本次范围涉及的接口 | 只贴相关段落 |
| 字段表 | 字段名、类型、必填、长度、取值范围、枚举 | 原表粘贴，不改写措辞 | 全文 |
| 错误码表 | 状态码、错误码、含义、触发条件 | 只贴与本次规则相关的条目 | 只贴相关段落 |
| 鉴权说明 | token 获取、请求头字段、角色权限矩阵 | 原表粘贴 | 全文 |
| 请求样例 | 一份真实可复现的请求与响应 | 脱敏后原样粘贴 | 全文 |
| 历史缺陷 | 近半年同接口缺陷的根因分类与次数 | 一行一条，附严重级别 | 摘要 |
| 历史用例库 | 同接口的编号、标题、入参摘要 | 只要这三列，用于去重 | 摘要 |

执行要求：

1. 一次只喂一个模块的接口清单，禁止把整份 OpenAPI 文件一次性贴入。
2. 历史用例超过 300 条时先按接口路径粗筛，只贴筛后的 50 条，避免上下文被稀释。
3. 缺陷描述只保留根因与次数，去掉复现步骤，防止模型复述单个缺陷。
4. 环境地址与账号必须脱敏后再贴入，生产地址一律不进入输入。

### 历史文档目录约定

```text
docs/
  openapi/
    order/v1.4/openapi.yaml
  cases/
    order/v1.4/api-cases.md
  defects/
    2026-H1/order-api.md
  deprecated/
    DEPRECATED.md
```

1. 接口文档路径为 `docs/openapi/{模块}/v{版本}/openapi.yaml`，版本号与上线版本一致。
2. 用例库路径为 `docs/cases/{模块}/v{版本}/api-cases.md`，只保留编号、标题、入参摘要三列。
3. 停止维护的接口文档移入 `deprecated/`，不参与断言与去重。

### 引用与冲突

1. 每条用例必须写关联接口与文档来源，引用格式为文件路径加章节，例如 `docs/openapi/order/v1.4/openapi.yaml` 的 POST /orders 一节。
2. 历史用例只用于去重和颗粒度校准，引用时写《接口用例库》v1.4 #API-ORD-014。
3. 同一接口在两个版本中描述不同时，以当前生效版本为准，旧版写进去重记录的合并来源。
4. 文档与代码行为不一致时，不按代码改文档，列为缺陷候选并进入待确认清单。
5. 无法判断哪一版有效时，两条都保留并写入待确认清单，不自行删除。

## 执行步骤

1. 确定基线版本：以当前生效版本为唯一断言依据，旧版文档只用于识别变更。
2. 拆接口清单，按模块分组。每个接口先登记：方法、路径、鉴权要求、依赖数据、历史缺陷次数。
3. 逐接口列契约检查项：必填字段、字段类型、长度与取值范围、枚举取值、默认值、状态码映射、响应体关键字段。
4. 套设计方法：等价类（合法与非法取值）、边界值（长度与数值的上下界及越界一格）、异常（缺字段、类型错误、非法枚举、越权、重复提交、下游超时）、状态迁移（订单、支付、退款类接口）、并发与幂等。
5. 每条用例补前置数据：需要先创建什么资源、用哪个角色的账号、依赖哪个接口的返回值。
6. 断言点分三层：状态码、响应体字段、数据副作用。只断言状态码的用例视为不合格。
7. 用历史缺陷做反向检查：同一根因必须至少对应一条用例，并在备注里注明对应缺陷编号。
8. 标注无法确认的字段与场景，进入待确认清单，不要用推断值填满。
9. 去重：同一接口、同一入参组合、同一预期视为重复。正常流与异常流不合并。
10. 输出前做敏感信息检查：确认用例表里没有真实手机号、身份证号、token、生产地址。

## 输出格式

先给一段总体说明：覆盖接口数、用例总数、按场景类型（正常 / 参数异常 / 鉴权 / 幂等 / 状态迁移 / 依赖）的分布、未覆盖接口及原因。

然后输出用例表，列固定为：

| 用例编号 | 接口 | 方法 | 前置条件 | 请求参数 | 预期状态码 | 预期响应断言 | 异常分支 | 关联需求 |

用例编号规则：API-模块缩写-三位序号，例如 API-ORD-014。

字段要求：

1. 用例编号：API-模块缩写-三位序号，模块内连续不跳号。
2. 接口：路径加模块名，例如 POST /v1/orders。
3. 方法：GET / POST / PUT / DELETE 等 HTTP 方法。
4. 前置条件：需要先创建的资源、使用的角色账号、依赖接口的返回值。
5. 请求参数：具体值，禁止出现「有效」「合法」「正常」这类形容词，金额与时间写清构造方式。
6. 预期状态码：取值全部来自文档的状态码映射表，不自行编造。
7. 预期响应断言：至少一个响应体关键字段的取值或类型，不止写状态码。
8. 异常分支：写明触发的校验条件或资源状态，例如缺字段、越权、重复提交、下游超时。
9. 关联需求：需求编号或接口文档章节，例如 REQ-ORD-014 / openapi.yaml POST /orders。

表格之后输出三节：

1. 覆盖说明：按接口统计用例条数，列出没有用例的接口与原因。
2. 版本差异：新旧文档的字段增删、类型变化、状态码变化，逐条标注以哪一版为准。
3. 待确认清单：按硬性约束保留该节，没有条目时写「无」。

不要输出自动化脚本、框架选型与目录规范，这些由使用方决定。

## 质量检查清单

- 每个接口至少覆盖正常请求、参数异常、鉴权失败三类场景。
- 状态码取值全部来自文档的状态码映射表，没有自行编造 200 / 400 / 500。
- 必填字段缺失、类型错误、超长、越界各至少一条用例。
- 断言点不止状态码，至少包含一个响应体关键字段。
- 写操作接口有一条重复提交或幂等用例，并写明幂等键位置。
- 需要登录态的接口写清角色，越权用例至少一条，且注明用哪个角色的 token。
- 依赖上下游的接口标注依赖项，并说明依赖不可用时的预期表现。
- 每条用例都有前置数据描述，没有「使用已有数据」这种模糊表述。
- 版本冲突已列出，且每处冲突都明确了以哪一版为准或标记为待确认。
- 输出里没有真实账号、真实 token、生产地址等敏感信息。
- 待确认清单存在，且与正文一致。

## 反例

- 把接口用例写成业务场景，「用户下单成功」这种粒度，看不到请求体和断言。
- 预期结果只写「返回成功」，不写状态码和响应字段。
- 所有异常用例都用不存在的 ID，不区分格式错误与资源不存在。
- 文档里只写了 400，用例里却断言 422，理由是「一般后端都这么返回」。
- 新旧文档字段冲突时自己选一个，不告诉任何人。
- 直接拿生产环境地址和真实账号跑用例，把 token 明文贴进对话。
- 只生成本次改动的接口，忽视被改动接口的上下游调用方。
- 用例表里所有前置数据都写「已存在订单」，执行时没人知道是哪一条。
