测试工程师的 Git 第一课：从 clone 到 push 不迷路

环境搭建

terminal
# 安装 Git
# 配置用户
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
# 验证
git --version
terminal — 初始化仓库
mkdir my-project && cd my-project
git init
echo "hello" > test.py
git add .
git commit -m "初始提交"

基础应用：分支操作

terminal
# 创建 + 切换分支
git checkout -b dev
git commit -m "dev 修改" --allow-empty
git checkout main
git merge dev

# 查看日志
git log --oneline --graph

项目进阶：Feature 分支 + MR 流程

terminal
# Feature 分支
git checkout -b feature/login
git commit -m "feat: 用户登录" --allow-empty

# 提 MR（在 GitHub/GitLab 上）
# 评审通过后合并
git checkout main
git pull origin main
git merge --squash feature/login
git commit -m "feat: 用户登录"
git push origin main
git branch -d feature/login

什么是 Git，为什么测试工程师必须懂

Git 是一个分布式版本控制系统：它把你每一份改动（代码、测试脚本、配置、文档）都记成一条带时间戳的「快照」（commit），并且能在任意两个快照之间做对比、回退、分叉。测试工程师和开发用同一套仓库协作，所以你「跑脚本」这件事本身就依赖 Git：

  • 脚本是开发提交上来的，你得先 clone / pull 拿到最新；
  • 你改了一条用例、加了一个断言，得 add / commit / push 让别人看到；
  • 线上出 Bug，要 diff / log 找到是哪一次改动引入的。

换句话说，不是「会跑脚本」就够了——你得知道脚本从哪来、改了什么、怎么合回去。下面 8 条命令就是测试工程师 90% 场景里会反复用的。

开始之前先装好 Git 并配置身份，否则 commit 会报错：

terminal — 一次性配置（只需执行一遍）
# 检查是否已安装
git --version

# 配置你的名字和邮箱（会写进每条 commit，请务必用公司邮箱）
git config --global user.name "GG Bond"
git config --global user.email "ggbond@example.com"

8 条核心命令：clone / status / add / commit / pull / push / log / diff

按「从拿到仓库到交回改动」的完整生命周期排列。每条先说「下一步该干嘛」，再给测试场景。

① clone —— 把整个仓库拉到本地

下一步该干嘛：进入目录（cd 仓库名），再 git status 确认工作区干净。

terminal
# 克隆测试仓库到当前目录
git clone https://git.example.com/qa/test-scripts.git
cd test-scripts
  • 场景 A：第一天入职，clone 团队的测试用例仓库；
  • 场景 B：clone 时加 --depth 1 只拉最新一层，仓库很大时省时间；
  • 场景 C：clone 下来发现子模块是空的，需要 git submodule update --init（见第 7 篇）。

② status —— 看工作区现在是什么状态

下一步该干嘛：看到 modified / untracked 就决定要 add 哪些文件，或 checkout 还原误改。

terminal
git status            # 查看：哪些文件改了、哪些没跟踪、当前在哪个分支
git status -sb        # 简短版：一行显示分支 + 改动清单
  • 场景 A：改完脚本先看 status，确认只改了目标文件，没误碰配置；
  • 场景 B：看到 Your branch is behind，说明远端有新提交，该 pull 了。

③ add —— 把改动放进暂存区

下一步该干嘛：再 git status 确认「待提交」列表，然后 commit。

terminal
git add test_login.py        # 只暂存这一个文件（推荐，改动可控）
git add .                    # 暂存当前目录所有改动（注意：别把临时文件加进去）
git add -p                   # 交互式逐块暂存，适合一个文件里只想提交一部分改动
  • 场景 A：修了一条用例只 add 那一个文件，避免把调试用的临时打印带进仓库；
  • 场景 B：add -p 把一个文件里「修 Bug」和「加日志」两段改动拆成两次提交。

④ commit —— 把暂存区写成一条历史

下一步该干嘛：提交完立即 push（如果是在特性分支上），或 log 确认刚写进去的内容。

terminal
# 普通提交，信息要写清"做了什么 + 为什么"
git commit -m "fix: 登录用例超时从 5s 改为 10s，修复偶发失败"

# 写多条信息时用 -m 多次
git commit -m "refactor: 抽出公共登录方法" -m "影响：login / register 两个用例"

# 提交时顺带暂存改动（省掉单独的 add）
git commit -am "docs: 补充数据清理说明"
  • 场景 A：提交信息带上「影响范围」，开发合并时一眼看懂改了什么；
  • 场景 B：用 git commit --amend 修正刚提交的信息或补漏的文件（仅限还没 push 的提交）。

⑤ pull —— 拉取远端最新并合并到本地

下一步该干嘛：合并完看 status 确认干净，再重新跑一遍脚本，因为「最新」可能改了依赖。

terminal
git pull                 # 等价于 fetch + merge
git pull --rebase        # 等价于 fetch + rebase，历史更干净（见第 3 篇）
  • 场景 A：每天早上开工先 pull，保证跑的是最新脚本；
  • 场景 B：开发刚推了新代码，你 pull 后再跑回归，避免拿旧版本测出假 Bug。

⑥ push —— 把本地提交推上远端

下一步该干嘛：推送后在 GitLab/GitHub 上发一个 Merge Request / Pull Request，等评审。

terminal
git push                 # 推送当前分支（首次需 git push -u origin main）
git push -u origin feature/login-fix   # 首次推送并建立跟踪关系
git push --force-with-lease   # 危险：强制覆盖远端（仅当你 rebase 自己的分支时用）
  • 场景 A：特性分支开发完，push 后发 MR 让开发和另一个测试一起看；
  • 场景 B：千万别对 main 用 force push，会抹掉别人的提交（见「常见新手错误」）。

⑦ log —— 看历史，回溯改动

下一步该干嘛：找到可疑提交后，用 show 或 diff 看它具体改了什么。

terminal
git log --oneline -10    # 最近 10 条，一行一条
git log --author=GG --oneline   # 只看自己提交的
git log -p -3            # 最近 3 条并展开改动内容
git show 8f3a2c1         # 看某一条 commit 的完整 diff
  • 场景 A：某条用例突然挂了，log -p 看是哪个提交改了它的断言；
  • 场景 B：配合 git blame 定位「这一行是谁哪次改的」。

⑧ diff —— 看改动内容

下一步该干嘛：看完 diff 决定是保留改动（add）还是还原（checkout -- 文件）。

terminal
git diff                 # 工作区 vs 暂存区（改了还没 add 的）
git diff --staged        # 暂存区 vs 上次提交（add 了还没 commit 的）
git diff HEAD            # 工作区 + 暂存区 vs 上次提交（所有未提交改动）
git diff main..feature   # 两个分支之间的差异（评审前自查常用）
  • 场景 A：发 MR 前 diff main..feature 自查一遍，确认没把调试代码带进去；
  • 场景 B：跑脚本前 diff 看远端到底改了什么，心里有数再执行。

常见新手错误：force push、忘记 add、提交到错误分支

  • 对公共分支 force push：会把别人已拉取的提交抹掉，导致协作事故。main / master / release 一律禁止 force push，只在没人共用的特性分支上谨慎使用，且优先 --force-with-lease。
  • 忘记 add：只改了文件却直接 commit，结果是「提交了个空提交」或漏交。养成习惯：commit 前先 status 看暂存区。
  • 提交到错误分支：在 main 上直接改完提交。万一发生，git reset --soft HEAD~1 退回这条提交（改动还在工作区），再切正确分支重做。

三条铁律：① 公共分支绝不 force push；② commit 前必看 git status；③ 动手改代码前先确认自己在哪个分支（git branch）。这三条能避开新手 80% 的事故。

案例：从零 clone 一个测试仓库并跑通第一条脚本

把上面 8 条串起来走一遍。假设团队仓库地址是 https://git.example.com/qa/test-scripts.git：

terminal — 完整走一遍
# 1. clone 到本地
git clone https://git.example.com/qa/test-scripts.git
cd test-scripts

# 2. 确认工作区干净、在 main 分支
git status

# 3. 拉一次最新，保证脚本是新的
git pull

# 4. 看一眼最近提交，了解仓库大概有什么
git log --oneline -10

# 5. 跑第一条脚本（按仓库 README 的方式，这里示例）
python -m pytest tests/test_login.py -v

# 6. 你改了一条断言，提交并推送
git status                       # 确认只改了 test_login.py
git add tests/test_login.py
git commit -m "fix: 登录断言改为校验 status=200 而非 2xx"
git push -u origin main

走完这一遍，你已经完成了一个测试工程师最基础、最完整的工作循环：拿脚本 → 跑脚本 → 改脚本 → 交回脚本。剩下要练的，只是把这个循环做得更稳、更快。

把这条命令表打印出来贴工位：clone / status / add / commit / pull / push / log / diff。每个命令旁边记一句「我下一步要干嘛」，两周后你会发现 Git 对你来说已经不再陌生了。
