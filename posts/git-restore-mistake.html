Git 误操作急救：撤销提交、还原文件、找回删除

环境搭建

terminal
# 安装 Git
# 配置用户
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
# 验证
git --version
terminal — 初始化仓库
mkdir my-project && cd my-project
git init
echo "hello" > test.py
git add .
git commit -m "初始提交"

基础应用：分支操作

terminal
# 创建 + 切换分支
git checkout -b dev
git commit -m "dev 修改" --allow-empty
git checkout main
git merge dev

# 查看日志
git log --oneline --graph

项目进阶：Feature 分支 + MR 流程

terminal
# Feature 分支
git checkout -b feature/login
git commit -m "feat: 用户登录" --allow-empty

# 提 MR（在 GitHub/GitLab 上）
# 评审通过后合并
git checkout main
git pull origin main
git merge --squash feature/login
git commit -m "feat: 用户登录"
git push origin main
git branch -d feature/login

先记住一条核心原则

Git 不会真的删除东西。所有「删除」操作在 Git 眼里都是「移动引用」，历史还在。只要知道怎么「把引用移回去」，任何东西都能找回来。

场景一：误提交（提交了不该提交的东西）

刚 git commit 完发现「不该提交那个文件」或「提交信息写错了」，但还没 push。

方法 A：撤销提交，保留改动

terminal
# 撤销最近一次提交，改动保留在工作区
git reset HEAD~1

# 重新整理后提交
git add 该加的文件
git commit -m "正确的提交信息"

为什么用 reset 而不是 revert？reset 是「回到过去」（改写历史），适合还没 push 的提交。revert 是「加一条反向提交」（不改历史），适合已经 push 的。

方法 B：撤销提交并丢弃改动

terminal
# 撤销最近一次提交，改动直接丢弃
git reset --hard HEAD~1

--hard 是危险的，改动直接没了。99% 的场景用 reset HEAD~1（不加 --hard）就够了。

场景二：误删除文件

情况 A：删除了还没 add 的文件（工作区删除）

terminal
# 从仓库恢复（文件还在仓库历史里）
git checkout -- 文件名.py

# 或者用新命令（Git 2.23+）
git restore 文件名.py

为什么能恢复？因为文件还在仓库历史里（你之前 commit 过），checkout -- 就是「把仓库里的版本放回工作区」。

情况 B：误提交了删除（commit 了 rm 操作）

terminal
# 撤销那次"删除"提交，文件回来了
git reset --hard HEAD~1   # 回到删除前的提交

# 或者用 revert（不改历史，加一条"恢复文件"提交）
git revert HEAD   # 撤销最近一次提交
git commit -m "fix: 恢复误删的文件"

如果这条提交已经 push 了，用 revert 而不是 reset（reset 会改历史，别人拉下来会乱）。

情况 C：彻底误删（从仓库里删了、提交了、push 了）

terminal
# 用 log 找到删除文件的那条提交
git log --diff-filter=D --name-only -- 文件名.py
# 假设找到 commit abc123

# 从那条提交恢复文件
git show abc123:文件名.py > 文件名.py
git add 文件名.py
git commit -m "fix: 恢复误删的文件"
git push

场景三：误 reset / 误 rebase

误 reset（回退了好几格）

terminal — 找回「被 reset 掉的」提交
# reset 之后，被"丢"的提交还在 reflog 里
git reflog
# 输出示例：
# 1a2b3c4 HEAD@{0}: reset: moving to HEAD~2
# def4567 HEAD@{1}: commit: 我写的那条
# 890abc1 HEAD@{2}: commit: 再前一条

# 找到被 reset 掉的提交（def4567），切回去
git reset --hard def4567

# 或者开一条新分支保留（更安全的做法）
git branch recovery def4567
git checkout recovery

误 rebase

terminal — 找回「被 rebase 改掉的」提交
# rebase 改写了历史，原提交也在 reflog 里
git reflog
# 找到 rebase 前的提交
git reset --hard ORIG_HEAD   # rebase 前自动保存的位置

ORIG_HEAD 是 Git 在 rebase、merge、reset 等操作前自动保存的「上一次 HEAD 位置」，99% 的误操作急救都靠它。

场景四：误 force push

对公共分支做了 force push，抹掉了别人的提交。

terminal — 紧急修复
# 1. 先确认抹掉了哪些提交
git reflog

# 2. 找到被抹掉的提交 ID（比如 999888）
# 3. 恢复那些提交
git reset --hard 999888
git push --force-with-lease origin main

# 如果不确定 999888 是什么
git show 999888
git log 999888 --oneline -5

force push 公共分支是协作事故，不是误操作。事前用 --force-with-lease（比 --force 安全，远端有别人的新提交时拒绝）能减少 80% 的事故。事后立即通知团队，让大家 git fetch 重新同步。

reflog：误操作急救的瑞士军刀

所有「找不到」的情况，reflog 都能帮你找回来。它记录了你本地 HEAD 的每一次移动：

terminal — 用 reflog 找东西
# 查看所有 HEAD 移动记录（最近 50 条）
git reflog -50

# 查找某条提交是否在 reflog 里
git log --oneline | grep "我要找的那条"

# 找到后切过去
git reset --hard 找到的提交ID
# 或者开新分支保留
git branch 安全分支 找到的提交ID

reflog 只记录「你本地」的 HEAD 移动，远端 reflog 你查不到。误操作如果发生在远端（比如别人 force push），reflog 帮不了你，需要找管理员查远端日志。

急救命令速查表

场景 → 命令
# 误提交（未 push）
git reset HEAD~1              # 撤销提交，保留改动
git reset --hard HEAD~1       # 撤销提交，丢弃改动（危险）

# 误删除（已 commit）
git checkout -- 文件名         # 从仓库恢复
git revert HEAD              # 不改历史，加一条反向提交（已 push 用这个）

# 误 reset / rebase
git reset --hard ORIG_HEAD    # 回到操作前
git reflog                    # 查操作记录

# 误 force push
git reflog                    # 找被抹掉的提交
git reset --hard 提交ID
git push --force-with-lease   # 推回去（紧急）

把这张表打印出来贴工位。误操作时最该做的不是「再敲一遍命令」，而是先 reflog 看看，确认「东西还在哪」，再决定用什么命令找回。
