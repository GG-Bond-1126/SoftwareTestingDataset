数据库测试第一关：怎么证明写入的数据没丢没脏

环境搭建

terminal
# 启动 MySQL（Docker）
docker run -d --name test-mysql -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=test123 -e MYSQL_DATABASE=testdb mysql:8.0

# 连接验证
mysql -h localhost -u root -ptest123 testdb

# 创建测试表
CREATE TABLE users (id INT PRIMARY KEY AUTO_INCREMENT, name VARCHAR(100), email VARCHAR(200) UNIQUE);

基础应用：第一个 SQL 验证

python
import mysql.connector

conn = mysql.connector.connect(host="localhost", port=3306, user="root", password="test123", database="testdb")
cur = conn.cursor()
cur.execute("INSERT INTO users (name, email) VALUES (%s, %s)", ("测试", "t@e.com"))
conn.commit()
cur.execute("SELECT * FROM users WHERE name = %s", ("测试",))
assert cur.fetchone() is not None
print("基础验证通过 ✓")
cur.close(); conn.close()

项目进阶：并发测试 + 数据一致性

python
import mysql.connector, threading

def deduct(uid, qty):
    c = mysql.connector.connect(host="localhost", user="root", password="test123", database="testdb")
    cur = c.cursor()
    cur.execute("UPDATE products SET stock=stock-%s WHERE product_id=1 AND stock>=%s", (qty, qty))
    c.commit(); cur.close(); c.close()

threads = [threading.Thread(target=deduct, args=(i, 2)) for i in range(10)]
[t.start() for t in threads]
[t.join() for t in threads]

# 验证库存非负
c = mysql.connector.connect(host="localhost", user="root", password="test123", database="testdb")
cur = c.cursor()
cur.execute("SELECT stock FROM products WHERE product_id=1")
assert cur.fetchone()[0] >= 0
print("并发测试通过 ✓")

数据完整性的 5 种约束

所谓「数据没脏」，本质是数据始终满足事先声明过的规则。MySQL 里能声明这类规则的工具就 5 种：

约束类型作用测试关注点
主键 PRIMARY KEY唯一 + 非空能不能插入重复主键、主键列能不能为 NULL
唯一约束 UNIQUE指定列不重复大小写/空格是否算重复、NULL 值是否参与唯一判断
外键 FOREIGN KEY引用列必须在被引用表存在能不能插入「孤儿记录」、删除被引用行会发生什么
CHECK 约束（MySQL 8.0.16+ 才真正生效）列值必须满足表达式超范围值能不能插进去（老版本会静默放过）
默认值 DEFAULT不传值时自动填充省略该列时，实际写入的值是不是约定的默认值

特别注意 CHECK 约束：MySQL 在 8.0.16 之前会「解析但不生效」，意味着你写了 age CHECK (age > 0)，实际负数照样能插进去。测试前先用 SHOW CREATE TABLE 表名 确认版本行为和约束是否真的在列定义里。

建一张测试用的表，把 5 种约束都用上：

setup.sql
CREATE TABLE users (
  id INT PRIMARY KEY AUTO_INCREMENT,
  email VARCHAR(128) NOT NULL UNIQUE,
  age INT CHECK (age >= 0 AND age <= 150),
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE orders (
  id INT PRIMARY KEY AUTO_INCREMENT,
  user_id INT NOT NULL,
  amount DECIMAL(10,2) NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(id)
);

5 个典型场景与对应验证 SQL

① 重复提交

同一份数据被提交两次（用户手抖、前端没做防重、消息重复投递）。验证方式：造两个并发或串行的重复 INSERT，看唯一约束是否真正拦住了第二条：

dup1.sql
INSERT INTO users (email, age) VALUES ('a@test.com', 20);
-- 再插一次完全相同的
INSERT INTO users (email, age) VALUES ('a@test.com', 20);
-- 期望：第二条报 1062 Duplicate entry，第一条保留

用 SQL 验证「库里的最终结果」：

SELECT email, COUNT(*) FROM users WHERE email = 'a@test.com' GROUP BY email HAVING COUNT(*) > 1;
-- 结果应为 0 行；有任何一行命中，说明唯一约束没生效，是严重问题

② 外键悬挂（孤儿记录）

删了用户，订单还在。正确行为应该是：外键约束让「删用户」这一步直接失败（除非显式配置了 ON DELETE 行为）。验证：

dup2.sql
INSERT INTO users (email, age) VALUES ('bob@test.com', 30);
INSERT INTO orders (user_id, amount) VALUES (2, 100);
-- 尝试删掉有订单关联的用户 2
DELETE FROM users WHERE id = 2;
-- 期望：报 1451 Cannot delete or update a parent row: foreign key constraint fails

③ 事务回滚后数据恢复

多步写库（下单扣库存、更新余额）中途失败，整个事务要能完整回滚。验证：

dup3.sql
START TRANSACTION;
INSERT INTO users (email, age) VALUES ('carol@test.com', 25);
UPDATE users SET age = 26 WHERE email = 'carol@test.com';
-- 故意制造一步失败（比如违反 CHECK）
UPDATE users SET age = 200 WHERE email = 'carol@test.com';  -- 期望报错
ROLLBACK;
-- 回滚后再查：carol 这条记录应该完全不存在
SELECT * FROM users WHERE email = 'carol@test.com';  -- 期望 0 行

④ 脏读

事务 A 读到事务 B 还没提交的数据，B 又回滚了，A 读到的就是「脏」的。验证方法：两个会话同时开事务，把其中一个隔离级别调到 READ UNCOMMITTED（默认级别下脏读本来就会被拦住，这是「验证防线有没有失守」的手段）：

dup4.sql — 会话 A
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
START TRANSACTION;
SELECT * FROM users WHERE email = 'dave@test.com';   -- 先占位读
-- （会话 B 此时插入 dave 但不提交，A 再查一次就能看到这条"未提交"的数据）
SELECT * FROM users WHERE email = 'dave@test.com';
dup4-b.sql — 会话 B
START TRANSACTION;
INSERT INTO users (email, age) VALUES ('dave@test.com', 40);
-- 不 COMMIT，直接在会话 A 里查，看能不能读到
ROLLBACK;  -- 回滚后，A 读到的这条"不存在"的数据就是脏读的典型后果

⑤ 幻读

同一事务里，两次相同条件的查询，结果行数因为别的会话在中间插数据而「变多」。InnoDB 默认 REPEATABLE READ 级别下，靠 MVCC + 间隙锁基本能防住「读」方向的幻读，但验证脚本仍建议显式构造一次确认防线有效：两次相同 SELECT 之间，让另一个会话插入一条满足条件的数据，回读两次结果应当一致。

Python 脚本：并发写入 + 唯一约束断言

用多线程模拟「两个请求同时提交同一订单」，验证唯一索引真的拦得住：

test_dup_submit.py
import threading
import pymysql

conn_conf = dict(host="127.0.0.1", port=3306, user="test_user",
                 password="test_pwd", database="shop")

success_count = 0
error_count = 0
lock = threading.Lock()

def try_insert():
    """每个线程独立连接，模拟两个并发的"下单请求"插同一笔订单"""
    global success_count, error_count
    conn = pymysql.connect(**conn_conf)
    try:
        with conn.cursor() as cur:
            # order_no 上有唯一索引（建表时加 UNIQUE）
            cur.execute("INSERT INTO orders (user_id, amount, order_no) VALUES (1, 10, 'ORD-001')")
            conn.commit()
        with lock:
            success_count += 1
    except pymysql.err.IntegrityError:
        with lock:
            error_count += 1
    finally:
        conn.close()

def main():
    threads = [threading.Thread(target=try_insert) for _ in range(10)]
    for t in threads: t.start()
    for t in threads: t.join()

    # 核心断言：10 个并发里，只有 1 个能成功，9 个报唯一冲突
    assert success_count == 1, f"期望 1 条成功，实际 {success_count}"
    assert error_count == 9, f"期望 9 条冲突，实际 {error_count}"
    print("✅ 唯一约束在并发下仍然生效")

if __name__ == "__main__":
    main()

上生产前再检查一遍

  • 关键业务字段（订单号、用户唯一标识）是否真的加了 UNIQUE 而不是「应用层去重」；
  • 外键约束是否被显式关闭（MySQL 的 foreign_key_checks 会话变量），生产库别为了「图快」关掉；
  • 回滚验证要覆盖到「多表、多语句」的事务，不是单表单语句；
  • 脏读/幻读验证建议固定用两个隔离级别对比跑一遍，而不是默认「应该没问题」。
