Python 连接数据库做测试：sqlite3 和 MySQL 实战

先分清三类用途，再决定要不要连库

这篇写给已经能独立写接口自动化、但每次被问「数据到底写进去了没有」就卡住的测试工程师。典型现场是这样的：下单接口返回 200，前端也跳到了成功页，第二天运营说订单表里没有这一单；或者参数校验接口返回 400，看起来一切正常，库里却多出一条金额为 0 的脏记录。接口层的断言覆盖不到这些，必须有人去看落库结果。

但「连数据库」本身不是目的。测试脚本连库只有三类用途，把它们分清楚之后，很多争论会自动消失。

用途典型动作读写写错的后果
造数插入前置数据、构造边界值写污染测试库，影响同库其他人
校验落库查询接口调用后的副作用只读通常只是一次误判
清理按批次删除本次造的数据写误删他人数据，影响不可撤销

三类用途的风险并不对称。校验是只读的，写错了最多得到一次错误的通过或失败；造数和清理要写库，脚本一旦指错环境，破坏是即时的。后面所有关于隔离与清理的规矩，都是为这两类写操作准备的。

直连数据库做断言的边界

接口测试要回答的是「经过 HTTP 这一层，系统行为是否符合契约」。一旦用 SQL 查出期望值再断言接口返回，两条路径就共享了同一个数据源，序列化、鉴权、状态机、缓存全被绕过。这类用例在接口改坏时依然会绿，因为它比较的其实是同一个错误。

数据库断言应该只用来验证副作用：接口承诺会写库的东西，最终有没有按约定落进去。期望值来自用例设计，而不是来自另一次查询。

python — 用 SQL 反推期望值，等于没测接口
# 反例：把库里的值查出来，再拿去断言接口返回
expected = query_one("SELECT amount FROM orders WHERE order_no = %s", order_no)
resp = client.get(f"/api/orders/{order_no}")
assert resp.json()["amount"] == expected   # 两边同源，接口错了也发现不了

# 正例：期望值来自用例设计，库只用来验证副作用
resp = client.post("/api/orders", json={"sku": "SKU-1001", "qty": 2})
assert resp.status_code == 201
order_no = resp.json()["order_no"]

row = query_one(
    "SELECT sku, qty, status FROM orders WHERE order_no = %s",
    order_no,
)
assert row is not None, "接口返回成功，但订单未落库"
assert row["sku"] == "SKU-1001"
assert row["qty"] == 2
assert row["status"] == "created"

判断标准可以压缩成一句话：把这条 SQL 删掉，用例还剩多少验证能力？如果什么都不剩，说明它已经退化成数据库测试，接口只是陪跑；如果还能验证状态码、响应结构和业务字段，那这条 SQL 才是有价值的补充。

另一条边界是不要用 SQL 去「修」数据让用例通过：下单失败后直接 UPDATE 订单状态，再断言查询接口返回已支付，这种用例永远不会失败，也就永远没有价值。

驱动选型：pymysql、psycopg2 与 sqlite3

选型只由一件事决定：被测系统用的是哪种数据库。测试脚本不该为了「统一技术栈」去装一个异构驱动再靠中间件转接，那只会让出问题时多一层排查。

驱动目标数据库占位符安装成本适用场景
pymysqlMySQL / MariaDB%s纯 Python，pip 即可接口测试校验落库
psycopg2PostgreSQL%s依赖 libpq需要服务端游标或批量导入
sqlite3SQLite? 或 :name标准库内置单元测试、本地夹具、离线复现

三者都遵循 PEP 249 定义的 DB-API 2.0，connect、cursor、execute、fetchone、commit 这一套接口基本同构，所以封装一层薄适配并不难。真正不一样的是占位符风格和游标返回类型，这两点在跨库复用代码时最容易踩。

连接池要不要上？测试脚本通常不需要：一个进程活几分钟，建连十几次的开销可以忽略。造数脚本是例外，如果要循环写几万行，每次握手的成本会明显拖慢整体，这时用 DBUtils 或 SQLAlchemy 的 QueuePool 包一层是值得的。代价是多一个依赖，池里归还的连接也可能带着旧事务快照。下面这个薄封装把参数收在一处，也顺手统一了提交与关闭。

python — 连接薄封装
import contextlib
import os

import pymysql

DB = {
    "host": os.environ["QA_DB_HOST"],
    "port": 3306,
    "user": os.environ["QA_DB_USER"],
    "password": os.environ["QA_DB_PASSWORD"],
    "database": os.environ["QA_DB_NAME"],
    "charset": "utf8mb4",
    "autocommit": False,
    "cursorclass": pymysql.cursors.DictCursor,
}


@contextlib.contextmanager
def db_cursor(commit=False):
    conn = pymysql.connect(**DB)
    try:
        with conn.cursor() as cur:
            yield cur
        if commit:
            conn.commit()
        else:
            conn.rollback()   # 只读也显式结束事务，避免长事务占着旧快照
    except Exception:
        conn.rollback()
        raise
    finally:
        conn.close()

这里有两个刻意的设计。只读查询也调用 rollback，是为了让连接尽快结束事务；在可重复读隔离级别下，一个没结束的事务会一直拿着旧快照，后续再查同一个库可能看不到别人刚提交的数据。提交用参数控制而不是让调用方随手调，是为了避免「忘了提交」和「提前提交」两种错误散落在业务代码里。

连接、游标、事务的关闭顺序

关闭顺序只有一个正确答案：先游标，后连接。游标是连接上的执行句柄，连接关掉之后再操作游标，pymysql 会抛 ProgrammingError 提示 cursor closed；SQLite 上的表现更隐蔽，可能只是静默失败，让人误以为语句没生效。

很多人对 with 的理解有偏差。sqlite3 的 with conn 只负责事务：正常退出提交，异常退出回滚，它不会关闭连接。这是官方文档里明确写着的，也是最常见的误解来源。要真正关闭连接，还得再套一层 contextlib.closing。

python — sqlite3 的事务与关闭是两件事
import contextlib
import sqlite3

# with conn 管事务，closing 管关闭，两件事必须分开写
with contextlib.closing(sqlite3.connect("qa_fixture.sqlite")) as conn:
    with conn:                       # 正常退出 commit，异常退出 rollback
        cur = conn.cursor()
        try:
            cur.execute(
                "INSERT INTO users (name, email) VALUES (?, ?)",
                ("qa_20261124_001", "qa_001@test.local"),
            )
        finally:
            cur.close()

pymysql 的 Connection 也支持上下文管理器，退出时关闭连接，但同样不替你提交。更省心的写法还是显式 try/except/finally，把提交、回滚、关闭写全。

失败模式很具体：某次用例在 with 块里断言失败，异常抛出，连接没关，fixture 也没兜住。跑掉几百条之后服务端开始报 Too many connections，后面的用例全部变成 error，报告一片红，看起来像系统崩了，实际是脚本泄漏。排查时先看测试库的 SHOW PROCESSLIST。

参数化查询：占位符不是风格问题

占位符的本质是把 SQL 文本和参数分两次发给服务端：服务端先编译语句结构，再把值填进去。值里无论出现引号、分号还是注释符，都只被当成数据。字符串拼接则相反，值先变成 SQL 文本的一部分，再一起解析，注入的空间就是这样产生的。

python — 拼接与占位符的差别
# 错误：字符串拼接，数据参与了 SQL 结构
name = "O'Brien"
sql = f"SELECT id FROM users WHERE name = '{name}'"
# 实际执行：... WHERE name = 'O'Brien'  → 1064 语法错误

# 正确：占位符，由驱动负责绑定
cur.execute("SELECT id FROM users WHERE name = %s", (name,))

# 正确：批量写入同样走绑定，不要拼成一条大 INSERT
cur.executemany(
    "INSERT INTO users (name, email) VALUES (%s, %s)",
    [("qa_001", "qa_001@test.local"), ("qa_002", "qa_002@test.local")],
)

测试代码里更常见的不是恶意攻击，而是意外：姓名里的单引号（O'Brien、D'Angelo）、备注里带反斜杠、金额字段传了 None。这些在拼接写法下都会变成语法错误或类型错误，而报错信息指向 SQL 语句本身，看着像库的问题，实际是拼串造成的。

占位符写法按驱动不同：sqlite3 用 ? 或命名占位符 :name；pymysql 和 psycopg2 都用 %s。psycopg2 有个额外注意点：SQL 文本里本身的百分号（比如 LIKE '%abc%'）要写成 %%，否则会被当成占位符，报参数数量不匹配。

查询结果为空，先别急着判失败

断言查不到数据时，第一反应不该是「功能有 bug」。测试脚本里的空结果至少对应三种完全不同的原因，修复方式也互不相同：数据根本没写进去、查询条件本身写错了、写进去了但事务没提交，或者连到了另一个库。

第一种才是真正要抓的缺陷，通常伴随接口成功但业务状态缺失。第二种最常见，条件里的枚举值大小写不一致、时间字段存的是 UTC 而查询用了本地时间、软删除的表忘了过滤 is_deleted，都会让一条本该存在的记录消失。第三种最隐蔽：被测服务和测试脚本是两个独立连接，服务端提交了，脚本的连接若处在可重复读的事务里，读到的还是旧快照。

排查顺序按成本从低到高：先确认连的是哪个库、哪张表，打印 SELECT DATABASE() 和不带条件的 COUNT(*)；逐条去掉 WHERE 条件，看哪一步结果变空；最后才怀疑被测服务。把这些中间值写进断言失败信息，别人接到报告就能自己往下查。

断言升级：从「有这条记录」到「字段值全对」

fetchone() is not None 只能证明行存在。接口把金额写成 0、把状态写成草稿，这条断言依然通过。落库校验的价值在字段级比对，但直接 SELECT * 全字段对比又走向另一个极端：自增 id、updated_at、加密后的手机号每次都不同，用例会稳定失败，最后被人加个 skip 关掉。

正确做法是白名单：只取接口契约里承诺的字段，构造一份期望字典，逐字段断言，失败信息里带上字段名。下面这个 helper 把「查不到」和「字段不对」区分成两种失败，前者说明写入缺失，后者说明业务逻辑算错了。

python — 字段级落库断言
FIELDS = ("sku", "qty", "status")


def fetch_order(cur, order_no):
    cur.execute(
        "SELECT sku, qty, status FROM orders WHERE order_no = %s",
        (order_no,),
    )
    return cur.fetchone()


def assert_order_written(cur, order_no, expected):
    row = fetch_order(cur, order_no)
    assert row is not None, f"订单 {order_no} 未落库，但接口返回了成功"
    for field in FIELDS:
        assert row[field] == expected[field], (
            f"字段 {field} 期望 {expected[field]!r}，实际 {row[field]!r}"
        )

字段多了要分级：金额、状态、关联 id 必须精确断言；创建时间只断言落在合理区间；扩展 JSON 只断言关键 key 存在。全部精确比对的维护成本会在表结构变更时集中爆发，最后没人愿意改。

隔离红线：测试库与生产库之间必须有硬边界

隔离不能靠自觉，要靠机制。三条红线：连接串里不允许出现生产库的 host 或库名；测试账号在测试库上只有增删改查权限，没有 DROP 和 GRANT；脚本启动时做一次环境自检，发现库名、host 或数据量符合生产特征就直接退出，而不是弹个确认框等人点。

最典型的事故是配置复制：把 staging 的配置文件复制一份改名叫 prod，只改了 host 忘了改库名，或者反过来。清理脚本随后按标记删除，而生产数据恰好也有同样的标记前缀，一次运行就删掉真实数据。

python — 启动时的目标库自检
import os
import sys

ALLOWED_HOSTS = {"127.0.0.1", "mysql-test.internal"}
FORBIDDEN_HOSTS = {"mysql-prod.internal", "10.0.0.11"}
FORBIDDEN_DB = {"shop", "shop_prod"}


def assert_safe_target(host: str, database: str) -> None:
    if host in FORBIDDEN_HOSTS or database in FORBIDDEN_DB:
        sys.exit(f"拒绝执行：目标是 {host}/{database}，疑似生产库")
    if host not in ALLOWED_HOSTS:
        sys.exit(f"拒绝执行：{host} 不在测试库白名单内")


def db_target():
    host = os.environ.get("QA_DB_HOST", "")
    database = os.environ.get("QA_DB_NAME", "")
    if not host or not database:
        sys.exit("缺少 QA_DB_HOST / QA_DB_NAME，不允许使用默认值")
    assert_safe_target(host, database)
    return host, database

第三条容易被忽略：只读账号也会造成泄露。校验脚本可能把真实手机号、身份证号打进日志，而这些日志会作为附件上传到 CI。测试库的数据要么脱敏，要么全部由造数脚本生成。

清理：按造数标记删，永远不要无条件 DELETE

清理的目标是「只删自己造的，不动别人的」。三种做法各有适用面，选错一种的代价差别很大。

做法实现方式适用场景代价
标记字段删除造数写统一前缀或批次号，按前缀删共享测试库，多人并行表里需要预留可标识的字段
独立库或 schema每次运行重建整个测试库独占环境、数据量小建库耗时，无法与其他任务共享
事务回滚造数后不提交，断言完 rollback只验证读逻辑跨连接、跨服务时无效

标记法要求造数时就写好归属：统一前缀加批次号，例如 qa_20261124_001，同一批次的所有行共享前缀。清理只按这个前缀删，天然不会碰到历史数据和其他人的数据。批次号用日期加序号，出问题时能反查是哪次运行留下的，也方便先查后删。

python — 记录批次并把清理放进 finally
import pymysql
import pytest

BATCH = "qa_20261124_001"


@pytest.fixture
def seeded_order():
    prefix = f"{BATCH}_"
    conn = pymysql.connect(**DB)
    try:
        with conn.cursor() as cur:
            cur.execute(
                "INSERT INTO orders (order_no, sku, qty, status)"
                " VALUES (%s, %s, %s, %s)",
                (f"{prefix}1001", "SKU-1001", 2, "created"),
            )
        conn.commit()
        yield f"{prefix}1001"
    finally:
        # 放在 finally，断言失败也一定执行
        with conn.cursor() as cur:
            cur.execute(
                "DELETE FROM orders WHERE order_no LIKE %s",
                (f"{prefix}%",),
            )
        conn.commit()
        conn.close()

清理一定要放在 finally 或 yield 之后，不能用「用例通过才清理」的写法，否则失败用例留下的脏数据会越积越多，最后连测试库自己都跑不出稳定结果。另一条硬规矩是禁止不带 WHERE 的 DELETE 和 TRUNCATE：TRUNCATE 会隐式提交、无法回滚，在共享测试库上执行一次，就可能让正在并行跑的其他人全部失败。

常见坑与排查

症状：查询结果里中文全是问号或乱码。原因：连接没有指定字符集，服务端按默认的 latin1 返回，而表里存的是 utf8mb4。处理：连接参数里显式写 charset=utf8mb4，同时确认建库和建表的字符集，服务端排序规则不一致仍会出问题。

症状：库里明明是今天的数据，查出来的时间却差了 8 小时。原因：数据库存的是 UTC，驱动或服务端时区配置把值当成服务器本地时间处理，来回转换两次。处理：统一约定存 UTC，断言时用带时区的 datetime 比较，不要用字符串比大小。

症状：本地跑得好好的，CI 上偶发 Too many connections。原因：fixture 作用域是 function，每条用例新建一条连接，而失败路径上没有关闭；并行执行又把这个问题放大。处理：把连接提到 session 或 module 级，用完必须关闭；或者改用上下文管理器，让异常路径也走关闭逻辑。

症状：executemany 返回了，紧接着查询却是空的。原因：autocommit 关闭时没有 commit，数据只存在于当前事务里；或者复用了同一个游标，上一条语句的结果集还没读完。处理：写操作后显式 commit 再查，同时用独立的游标做校验查询，避免结果集互相干扰。

上线前检查清单

把这套脚本接进流水线之前，逐条对一遍，比事后排查便宜得多。

检查项合格标准
连接凭据来自环境变量或密钥管理，仓库里没有明文密码
目标库启动时做白名单自检，命中生产特征直接退出
SQL 写法全部使用占位符，没有 f-string 拼 SQL
资源释放游标先于连接关闭，异常路径也覆盖
事务写操作显式提交，只读查询结束事务
断言粒度核心字段精确比对，明细字段断言范围
清理按批次前缀删除，无无条件 DELETE 与 TRUNCATE
失败信息包含库名、表名、查询条件与字段期望值

最后给一个判断标准：如果落库断言失败时，报告里只有一句 assert None is not None，那它离可用还很远；合格的失败信息应让人不打开代码就知道查哪张表、什么条件、期望与实际各是什么。
