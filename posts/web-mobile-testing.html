移动端 Web 测试：响应式 + PWA

移动端 Web 的问题不在「屏幕小」

把桌面页面缩到 375 像素宽，只是把问题放大了，并没有制造新问题。真正让 H5 在手机上出事的，是四件桌面端不存在的事：视口是可变且会被缩放和键盘改写的，输入靠手指而不是鼠标指针，页面经常处在弱网和省电状态，还有一个介于网页和原生之间的 PWA 外壳。这四件事各自都能让一条在 Chrome 桌面端全绿的用例，在 iPhone 上稳定失败。

所以移动端 Web 的验收不能只做「换个窗口尺寸截图」。合理的拆分是三层：渲染层看布局与视口，交互层看触摸、手势、键盘，运行层看网络、缓存、离线与安装。三层用的工具不同，能在模拟器上做的只有第一层和部分第二层，剩下的必须上真机。本文按这个顺序展开，每个结论都给出可复现的验证方法。

三个视口：先搞清你在测哪一层

移动浏览器里有三套宽度。布局视口是 CSS 布局参照的宽度，由 meta viewport 决定；视觉视口是用户实际看到的窗口，随双指缩放与软键盘变化；理想视口是设备物理宽度除以像素比。绝大多数「手机上像桌面缩小版」的故障，根因是页面没声明 viewport，浏览器退回默认的 980 像素布局视口再整体缩放。

标准声明是三段：width=device-width 让布局视口等于设备宽度，initial-scale=1 禁止初始缩放，viewport-fit=cover 让页面延伸到刘海区域，否则安全区填充无从谈起。要特别注意 user-scalable=no 这种写法，它会让低视力用户无法放大页面，属于无障碍问题，很多团队在评审时才发现。

排查时不要靠肉眼判断。用下面的脚本把三套宽度、缩放比例、页面偏移一次打出来，能立刻区分是布局视口错了、还是用户缩放了、还是键盘顶起了视觉视口。这组数字也是提缺陷时最有说服力的证据，比一张截图管用得多。

javascript — 一次打全视口状态
const meta = document.querySelector('meta[name="viewport"]');
const vv = window.visualViewport;
console.table({
  metaContent: meta ? meta.content : '(缺失)',
  layoutWidth: document.documentElement.clientWidth,
  visualWidth: vv ? Math.round(vv.width) : null,
  visualHeight: vv ? Math.round(vv.height) : null,
  scale: vv ? vv.scale.toFixed(2) : null,
  offsetTop: vv ? Math.round(vv.offsetTop) : null,
  dpr: window.devicePixelRatio,
  horizontalScroll:
    document.documentElement.scrollWidth > document.documentElement.clientWidth,
});

断点验证：模拟器与真机怎么分工

断点测试的核心不是拖窗口，而是验证「断点两侧布局是否按设计切换，以及有没有横向溢出」。常见断点是 320、375、414、768、1024、1280，边界值要各测一次（767 与 768 是两套布局）。只测中间值，最容易漏掉卡在临界宽度上的溢出。

模拟器的价值是快和可重复：视口、像素比、触摸能力都能精确设定，适合进 CI 每次提交跑。局限也明确：它用的是桌面内核，字体回退、软键盘、动量滚动、iOS 安全区都与真机不同。真机真实但不可并行、不稳定，适合发版前抽检。经验值是模拟器覆盖八成布局问题，真机专门抓剩下那些最贵的。

验证横向溢出不要只判断 scrollWidth，那个数字会告诉你「有溢出」，但不会告诉你是谁溢出的。把越界元素列出来，缺陷单里直接带上元素与所在宽度，开发几乎不用复现就能定位，通常是一个写死宽度的卡片或一段不会换行的长英文串。

python — 按断点扫溢出元素
import pytest
from playwright.sync_api import sync_playwright

BREAKPOINTS = [320, 360, 375, 414, 768, 1024, 1280]
URL = "https://staging.example.com/"


@pytest.mark.parametrize("width", BREAKPOINTS)
def test_no_horizontal_overflow(width):
    with sync_playwright() as p:
        browser = p.chromium.launch()
        ctx = browser.new_context(
            viewport={"width": width, "height": 800},
            has_touch=width < 768,
            is_mobile=width < 768,
            device_scale_factor=3,
        )
        page = ctx.new_page()
        page.goto(URL, wait_until="networkidle")

        offenders = page.evaluate("""() => {
            const docW = document.documentElement.clientWidth;
            return [...document.querySelectorAll('body *')]
                .filter(el => el.getBoundingClientRect().right > docW + 1)
                .slice(0, 10)
                .map(el => el.tagName + '.' + (el.className || ''));
        }""")

        assert not offenders, f"{width}px 下溢出元素: {offenders}"
        browser.close()

触摸事件：300 毫秒延迟与手势冲突

三百毫秒点击延迟的来历是双击缩放。早期浏览器在收到 touchend 后要等一段时间，确认用户不是要双击放大，才派发 click。声明了 width=device-width 的现代浏览器已经不再等待，但内嵌 WebView、iframe 里没带 viewport 的页面、以及部分老版本安卓仍然存在这段延迟，表现为按钮「点了半天没反应」。

解法不是到处绑 touchstart，那会破坏键盘与无障碍语义，还会让滚动误触发点击。正确做法是给可点击元素加 touch-action: manipulation，明确告诉浏览器这块区域不需要双击缩放；或者在滚动容器上设 overscroll-behavior: contain，阻止滚动穿透。判断有没有修好，用 Event Timing 接口看 click 的处理耗时，比秒表可靠。

手势冲突是另一个高频问题：轮播图左滑与页面横滑打架，下拉刷新与列表滚动抢事件。根因通常是 touchmove 里无条件 preventDefault，或组件没声明 touch-action，浏览器只能按默认逻辑猜。测试要覆盖「从卡片中间滑」和「从屏幕边缘滑」两种起点，边缘手势常被系统接管，模拟器测不出来。

python — 检查 touch-action 与慢点击
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch()
    ctx = browser.new_context(**p.devices["iPhone 13"])
    page = ctx.new_page()
    page.goto("https://staging.example.com/")

    page.tap(".buy-btn")

    # 没声明 touch-action 的可点区域，在老 WebView 里会有 300ms 延迟风险
    risky = page.evaluate("""() => [...document.querySelectorAll('button, .card, .carousel')]
        .filter(el => getComputedStyle(el).touchAction === 'auto')
        .map(el => el.className)
        .slice(0, 10)""")
    print("待确认区域:", risky)

    slow = page.evaluate("""() => performance.getEntriesByType('event')
        .filter(e => e.name === 'click' && e.duration > 100)
        .map(e => Math.round(e.duration))""")
    print("超过 100ms 的点击:", slow)
    browser.close()

五类布局 Bug：成因与验证方式

横向滚动条排第一。成因多是写死的宽度、100vw 叠加滚动条、长单词或长链接不换行、以及绝对定位元素超出父容器。验证方式就是上一节的越界元素扫描，比手动拖动可靠。第二是键盘顶起：输入框获得焦点后软键盘弹出，安卓会压缩视口，iOS 则把整个页面往上推，底部固定按钮就跑到键盘后面去了。

第三是 position: fixed 的错位。iOS 在键盘弹出、页面惯性滚动时对 fixed 元素的重绘时机与安卓不同，表现为底部工具栏漂在半空或遮住输入框。第四是安全区：iPhone 的底部横条与刘海会压住内容，必须用 env(safe-area-inset-bottom) 给固定栏补内边距，并且 meta 里带上 viewport-fit=cover，两者缺一不可。第五是动态视口单位：手机浏览器地址栏收起会改变可视高度，用 100vh 做全屏的页面会被裁掉一截，应改用 100dvh 或 100svh。

这五类问题的共同点是「桌面端完全正常」。验收要有硬性规则：任何含输入框或底部操作栏的页面，必须在真机上走一遍「聚焦、输入、收起键盘、继续点击」的完整链路，截静态图发现不了。

python — 底部固定栏遮挡自检
layout = page.evaluate("""() => {
    const bar = document.querySelector('.submit-bar');
    const rect = bar.getBoundingClientRect();
    const bodyPad = parseFloat(getComputedStyle(document.body).paddingBottom) || 0;
    return {
        barHeight: Math.round(rect.height),
        bodyPadding: Math.round(bodyPad),
        position: getComputedStyle(bar).position,
        bottomGap: Math.round(window.innerHeight - rect.bottom),
        coveredByBar: bodyPad + 1 < rect.height,
    };
}""")
assert layout["position"] == "fixed"
assert not layout["coveredByBar"], f"固定栏可能压住正文: {layout}"

PWA 的五个检查项

PWA 不是框架，是一组能力的组合。验收按五项确认：manifest 可解析且字段完整、Service Worker 注册并激活、离线时有可用页面、安装入口按平台预期出现、新版本发布后有更新提示。任何一项缺失，用户看到的就是「和普通网页没区别」。

manifest 的关键字段是 name、short_name、start_url、display 和图标；图标至少要有 192 与 512 两个尺寸，缺 512 在部分安卓机型上不出现安装横幅。缓存策略要分类型：静态资源 cache-first，接口 network-first 或 stale-while-revalidate，绝不能把登录态接口缓存成永不过期，否则换账号后会看到别人的数据。

更新是 PWA 最容易翻车的地方。默认的 Service Worker 会一直用旧的缓存，用户刷新十次还是旧页面。必须显式处理 skipWaiting 与 controllerchange，并在界面上给出「有新版本，点击刷新」的提示。测试方法是：发布新构建后不清理缓存直接访问，观察是否出现更新提示、点击后内容是否真的换了。iOS Safari 直到较近的版本才支持安装后的 Web Push，且没有安装提示事件，这块要单列验收。

python — manifest、SW 与离线三联检
with sync_playwright() as p:
    browser = p.chromium.launch()
    ctx = browser.new_context(**p.devices["Pixel 7"])
    page = ctx.new_page()
    page.goto("https://staging.example.com/")

    manifest = page.evaluate("""async () => {
        const link = document.querySelector('link[rel=manifest]');
        if (!link) return null;
        const res = await fetch(link.href);
        return res.ok ? await res.json() : null;
    }""")
    assert manifest and manifest.get("start_url"), "manifest 缺失或不可解析"
    sizes = {icon.get("sizes") for icon in manifest.get("icons", [])}
    assert {"192x192", "512x512"} <= sizes, f"图标尺寸不足: {sizes}"

    active = page.evaluate("""async () => {
        const reg = await navigator.serviceWorker.getRegistration();
        return Boolean(reg && reg.active);
    }""")
    assert active, "Service Worker 未激活"

    ctx.set_offline(True)
    page.reload()
    assert page.locator(".offline-banner").is_visible()
    ctx.set_offline(False)
    browser.close()

弱网、省电与低端机

弱网不是「慢一点」，而是会暴露一串只在特定时序下出现的问题：请求超时阈值设得太短导致重试风暴，骨架屏与真实内容打架，图片懒加载在滚动停止后才触发导致大片空白。用 CDP 把下行限制到 400 kbps、延迟 300 毫秒，接近国内地铁里的 4G 体验，跑一遍主流程，很多「偶现」问题会变成必现。

省电模式的影响更隐蔽。iOS 低电量模式会降低动画帧率、推迟定时器，安卓省电策略可能直接限制后台网络。依赖 setInterval 轮询的页面会明显变慢，依赖动画结束事件推进流程的页面可能卡住。打开省电模式走一遍支付流程，比重装十次 App 有用。

低端机的瓶颈在内存与主线程。一台 3GB 内存的安卓机打开含大量图片的长列表，很容易触发页面重载，用户看到的是「莫名其妙回到首页」。这类问题只能真机验证，模拟器有无限的 CPU 和内存，永远复现不了。

python — 弱网与首屏耗时采样
cdp = ctx.new_cdp_session(page)
cdp.send("Network.enable")
cdp.send("Network.emulateNetworkConditions", {
    "offline": False,
    "latency": 300,                              # 往返延迟 300ms
    "downloadThroughput": 400 * 1024 // 8,       # 400 kbps
    "uploadThroughput": 400 * 1024 // 8,
})

page.goto("https://staging.example.com/", wait_until="load")
lcp = page.evaluate("""() => new Promise((resolve) => {
    new PerformanceObserver((list) => {
        const last = list.getEntries().at(-1);
        resolve(Math.round(last.startTime));
    }).observe({ type: 'largest-contentful-paint', buffered: true });
})""")
print("弱网下 LCP(ms):", lcp)   # 记录趋势，不作为固定阈值

H5、原生与小程序的边界

同一个功能放在 H5 还是原生里，测试成本差一个量级。H5 的优势是发版快、跨平台、可回滚；劣势是性能受 WebView 限制、系统能力要靠桥接、离线能力弱。原生在动画、相机、蓝牙、推送这些场景无可替代。小程序则是另一套运行时，包体积、域名白名单、权限模型都由平台规定，不能简单当作「套壳 H5」来测。

边界判断有个实用办法：看这个功能是否依赖系统能力或高频交互。依赖相机、定位、蓝牙、后台推送的，放原生；以内容展示、表单、活动页为主的，放 H5；需要社交裂变、平台流量入口的，放小程序。落到测试上就是三套验收清单，不能拿 H5 的清单去覆盖小程序，否则一定会漏掉授权弹窗、分包加载与审核版本差异。

混合应用还要关注容器。WebView 的内核版本由 App 决定，不是用户浏览器版本；同一份 H5 在系统浏览器里正常，在 App 内嵌页里可能因容器禁用某些 API 而失败。提缺陷时务必写清容器版本，否则开发按 Chrome 最新版排查，方向从一开始就错了。

自动化取舍：模拟器、真机与云真机

模拟器的优势是免费、可并行、可进 CI，适合跑布局巡检、断点回归、PWA 基础检查这类确定性强的用例。它跑的是桌面内核加设备模拟，字体、滚动、键盘、系统手势都不是真的。真机的优势是真实，但设备要人管、无法大规模并行、稳定性差，适合发版前的人工抽检和疑难问题复现。云真机在两者之间：真实的设备与系统，按需租用，能进流水线，代价是费用与网络延迟。

建议按覆盖面分配：模拟器承担七成自动化用例，云真机承担两成关键链路（登录、支付、PWA 安装），剩下一成留给本地真机做探索性测试。别追求所有用例都上真机，维护成本会吞掉收益；也别只跑模拟器，那样等于没测 iOS。

还有一点必须说清：Playwright 的 WebKit 不等于 iOS Safari。它共用 WebKit 内核，但缺少 iOS 的系统级行为，安全区、滚动回弹、键盘、安装流程都不一致。要验证这些，只有真机或云真机。

yaml — 双内核布局巡检
jobs:
  mobile-web:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        project: [chromium, webkit]
    steps:
      - uses: actions/checkout@v4
      - run: pip install pytest pytest-playwright
      - run: playwright install --with-deps ${{ matrix.project }}
      - run: pytest tests/mobile_web -q
          --browser=${{ matrix.project }}
          --browser-channel=${{ matrix.project == 'chromium' && 'chrome' || '' }}
      - uses: actions/upload-artifact@v4
        if: failure()
        with:
          name: traces-${{ matrix.project }}
          path: test-results

iOS Safari 与 Android Chrome 差异清单

两家的差异不是细节，而是会改变验收结论的项。最典型的是视口高度：Safari 地址栏随滚动收起展开，100vh 在加载时按展开状态计算，底部内容会被裁；Chrome 也有同类问题，但地址栏行为不同，裁切位置不一样。全屏布局必须用动态视口单位，并在两端各测一次。

安装与推送差异更大。Chrome 支持 beforeinstallprompt，可自定义安装引导；Safari 没有这个事件，只能提示用户点分享按钮添加到主屏幕。推送方面，Safari 要求先把站点安装到主屏幕，权限模型与 Chrome 完全不同。日期选择器、聚焦缩放、橡皮筋回弹、文件上传的相机选项，各家行为也各不相同。

把这份清单固化成验收表，比记住结论更有用。每次发版按表逐项打勾，新同学也能在半小时内完成两端的基础验收。

检查点iOS SafariAndroid Chrome
安装引导无安装事件，需手动添加到主屏幕支持 beforeinstallprompt，可自定义按钮
推送通知需先安装到主屏幕，权限更严格网页可直接申请通知权限

存储限制长期未访问站点可能被清理存储配额较宽，清理策略不同

上线前检查清单

最后给一份可以直接贴进发版单的清单。它不追求穷举，只保证每次发版覆盖那些「漏掉就会线上出丑」的项。其余部分交给探索性测试，别指望表格覆盖所有边界。

  • 三个视口数值已采集，meta viewport 含 viewport-fit=cover
  • 320 到 1280 各断点无横向溢出，越界元素已记录
  • 真机上完成过「聚焦输入、弹出键盘、收起、再点击」的完整链路
  • 底部固定栏与安全区叠加正确，正文未被遮挡
  • 弱网（400 kbps / 300 ms）下主流程可完成，无重试风暴
  • PWA 五项逐条通过，更新提示在真机上验证过
  • iOS Safari 与 Android Chrome 差异清单已逐项打勾

一个常见误判：在 Chrome 设备模式里看到「iPhone 12 Pro」就以为测了 iOS。那只是把视口和像素比改成 iPhone，内核仍是 Chromium。凡是涉及安全区、软键盘、安装引导、系统手势的结论，都必须来自真机。
