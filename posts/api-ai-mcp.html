接口自动化新打法：AI IDE + MCP 从文档到可执行脚本

环境搭建

terminal
# 安装 Python 3.10+
python -m venv venv
venv\Scripts\activate
pip install pytest
pytest --version

基础应用：第一个测试用例

python
def test_basic():
    assert 1 + 1 == 2
    print("基础用例通过 ✓")

项目进阶：fixture + 参数化 + CI

python
import pytest

@pytest.fixture
def data():
    return [1, 2, 3, 4, 5]

@pytest.mark.parametrize("n, expected", [(3, 6), (5, 15)])
def test_sum(data, n, expected):
    assert sum(data[:n]) == expected

接口自动化的老问题一直没变：前期搭建慢、接口一改脚本就红、数据依赖复杂、维护成本高于新增成本。大模型出现后，很多团队第一反应是做个“测试知识库问答”，但那条路只能答疑，产不出能跑的资产。

更有效的形态是 AI IDE + MCP：模型不只回答，还能直接操作工程——读接口文档、写测试文件、调用工具执行、根据报错自我修正。

和“知识库方案”的本质区别

方案能力边界产出
知识库问答检索文档、生成文本建议一段需要人工搬运的示例代码
AI IDE + MCP读写文件、调用 API、执行命令、读取结果落地到仓库里的可运行用例与脚本

后者能形成闭环：文档解析 → 用例生成 → 脚本落地 → CI 执行 → 失败回到模型修正。核心前提只有一个：需求与接口描述必须结构化、清晰。文档写得含糊，再强的模型也只能猜。

一条可落地的链路

把流程拆成固定五步，每步都有确定性产物，避免“一把梭”导致不可控：

  1. 契约先行：OpenAPI / Protobuf 作为唯一事实来源，字段、类型、必填、错误码齐全。
  2. 用例生成：按接口 + 业务规则生成正例、异常、边界用例，输出结构化表格。
  3. 脚本生成：在既有框架里生成 pytest / Playwright 用例，复用 client 与 fixture。
  4. 执行与修正：本地跑通，失败信息回灌给模型，限制修改范围。
  5. 入 CI：按 smoke / regression 打标，接入流水线并设置门禁。

第 3 步的关键是「生成到既有框架里」。让模型另起一套目录结构和封装，短期看着整齐，长期会变成谁都不敢动的黑盒。

示例：从契约生成可维护的用例

下面这种生成结果的“形状”，比具体代码更重要：分层清晰、断言可追溯、数据自造自清。

tests/test_refund.py — AI 生成后人工校准
import pytest

@pytest.mark.regression
@pytest.mark.parametrize("case", [
    # 正例：支付后 30 分钟内可取消
    {"paid_minutes_ago": 10, "expect": "CANCELLED"},
    # 边界：刚好 30 分钟
    {"paid_minutes_ago": 30, "expect": "CANCELLED"},
    # 异常：已发货不可取消
    {"paid_minutes_ago": 31, "expect": "REJECTED", "code": "ALREADY_SHIPPED"},
])
def test_cancel_order(order_service, order_factory, case):
    order = order_factory.paid(minutes_ago=case["paid_minutes_ago"])
    resp = order_service.cancel(order["id"])
    assert resp["status"] == case["expect"]
    if "code" in case:
        assert resp["code"] == case["code"]
    assert order_service.get(order["id"])["status"] == case["expect"]

注意三个细节：边界值单独成例、错误码也做断言、状态变化通过二次查询验证。这些都是模型常常「顺手省掉」的部分，需要靠评审或 Prompt 强制要求。

必须补上的四条工程约束

  1. 生成代码必须评审：至少检查断言是否验证业务结果，而不是只看状态码 200。
  2. 数据自造自清：fixture 创建前置数据、结束后回收，禁止依赖库里现成记录。
  3. 确定性优先：字段查找、schema 校验、参数替换交给程序，模型只做语义映射——这也是字节 NL2Test 的核心原则。
  4. 限制修改范围：让模型只改指定文件，避免一次“顺手重构”把整个仓库带进 PR。

别把“生成速度”当成唯一指标。更有意义的指标是：生成用例进入 CI 的比例、脚本三个月后的存活率、以及因脚本本身问题导致的误报率。

适合先从哪里开始

优先选同时满足三个条件的模块：接口契约完整、业务规则明确、历史缺陷较多。这类模块生成质量高、收益可量化，也最容易拿到团队信任。

反过来，强依赖第三方、规则天天变、文档缺失的模块先放一放——那不是模型的问题，是输入不成立。
