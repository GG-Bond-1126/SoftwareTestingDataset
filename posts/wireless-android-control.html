不插线不 root：扫码隔空操控 Android 真机

真机自动化最琐碎的部分不是写脚本，而是让脚本能碰到手机。设备一多就是一排数据线；线松了、驱动抽风、手机息屏，半夜挂掉的用例常死在这些地方。想不插线，多数团队只能买按小时计费的云真机。外链介绍的 Droidline 换了个方向：手机装一个普通 App，扫码配对，之后由电脑用命令驱动这台真机。PC 端用 Go、手机端用 Kotlin，MIT 协议，2026 年 10 月 7 日开源，作者是韩国开发者 KnifeLemon，官网 droidline.dev，App、报错与文档均提供中英韩三语。

一、它替掉的不是 Appium，而是插线与 ADB 那一段

Appium 与 uiautomator2 跑了很多年，好用，但前提一样不少：开发者选项、USB 调试、数据线。Droidline 把这层拿掉——手机端只装普通 App，开无障碍服务和自带键盘，扫码后手机自己往外连，PC 一个端口都不用开。方向反过来，安全模型也顺了：配对决定谁能控这台手机，握手后每行通信端到端加密，隧道和中继只搬密文。断网重连从断点接着跑，执行中的命令由手机侧缓存应答，不会整条重跑。

它并不替换定位体系：定位仍按 text、id 去找，等待逻辑内置，换掉的只是「怎么连上手机」。脚本资产多的团队，迁移成本落在连接层与等待策略，用例设计本身可以搬过去。

环节传统 adb 链路扫码直连
连接前提开发者选项、USB 调试、数据线装普通 App，开无障碍与自带键盘
网络方向电脑连手机，需可达地址手机主动外连，电脑不开端口
跨网络端口映射或内网穿透同 Wi-Fi 直连，在外走隧道或中继
传输安全由隧道方案自行决定握手后端到端加密，中继只见密文
断线恢复多数情况整条脚本重跑手机侧缓存应答，重连后接着跑

表里真正改变体验的是后两行：加密决定远程控真机能否过安全评审，断点续跑决定弱网和换网时用例会不会成片失败。

二、两条命令完成配对，先用设置页跑一个最小闭环

PC 端三个平台都有发布包，手机要求 Android 9 及以上；发布包带 fakephone 模拟器，没真机也能照官方教程写第一个脚本。装好后两条命令：

bash · 首次配对
droidline serve          # 常驻服务，所有入口都连它的 8780 端口
droidline pair           # 弹出二维码，手机 App 扫码即配对

没有摄像头就点 App 里的「在此 Wi-Fi 下配对」，输入 6 位码一样能连。先用系统设置页确认通路，再写进业务脚本：

bash · 第一次触碰真机
droidline launch com.android.settings
droidline touch text "Network & internet"

Python 侧 pip install droidline，接着跑仓库自带的演示 App 登录：

python · login_demo.py
from droidline import connect

d = connect()
d.launch("dev.droidline.demo")

if d.exists("text", "Close ad"):
    d.touch("text", "Close ad")

d.input("id", "email", "knife")
d.touch("text", "Log in")
print(d.get_text("id", "greeting"))

示例先判断关闭广告弹窗再登录，值得留意：启动广告、权限弹窗、升级提示是真机上最常见的脏动作，写进流程开头比在断言里补救稳。组件记三个就够：serve 是常驻服务，pair 管配对，mcp 是给 Agent 用的适配器；inspect 能录脚本并推荐选择器，webdriver 让 Appium 客户端直接接管，按需再开。

三、一份规格生成五个入口，多端 SDK 不会各说各话

仓库根目录的 spec/commands.json 定义全部命令与三语错误文案，Python、Node.js、.NET 三个 SDK 和 MCP 工具清单都由它生成，CI 里跑一致性校验，对不上直接挂。所以 touch 在五个入口里都叫 touch，文档只维护一份。

这一点比工具本体更值得抄。多端 SDK 贵在不一致：Python 叫 tap、Node 叫 click、就描述再各写一遍，文档三份、错误文案三套，改一处要追五个仓库，最后没人敢动。把命令、参数、错误消息收敛成一份机器可读的规格，再让 CI 做门禁，改一处就全局生效。封装 MCP 工具时，同样的坑会以工具描述与参数 schema 的形式再来一次。

报错也照这个思路做。找不到元素时直接给出停在哪个页面、等了多久，形如 NOT_FOUND: Could not find text 'Log in' within 10s；配合 dump() 把屏幕拉成元素树，失败时一眼能看出是文案改了还是页面没跳过去。定位方式的取舍见 App 元素定位。

四、权限边界：把做不到的事写进 README 更值钱

手机端只用无障碍服务和自装键盘，也就是普通 App 能拿到的权限。代价 README 直接列了清单：解不开 PIN 锁，没有强停、清数据的单命令，打不开别的 App 未导出的页面。这三条恰好是测试里最常用的小动作，接入前得先确认用例有没有踩到。

还有两条上限属于路线决定的天花板，不是修一版能解决的。游戏和自绘界面拿不到元素，只能退回坐标点击加颜色判断，稳定性立刻掉一档；Android 15 起系统把一次性验证码从通知里藏起来，工具只能知道码到了，仍然得进 App 里读。

版本还在 0.1。作者在 Status 页写明，服务端与 SDK 的测试目前都是对着手机模拟器跑的，跨品牌真机验证仍在进行。这意味着它现在适合先拿自己的机器趟一遍，不适合直接压进生产回归流水线。

五、谁适合用，以及怎么小步接入

接入顺序建议这样走：一台备机跑系统设置页，确认连接与元素定位；再跑仓库自带的演示 App 登录，确认输入与读文本；第三步才是跨 App 收短信验证码的完整流程，这也是它相对插线方案真正的差异点——不需要为跳转额外准备连接配置。三步都过了再谈多机并行。

一台电脑带一排手机是另一个卖点：不同手机并行跑、每台有名字，还能给每台单独配 socks5 或 http 代理；配合 cuts_network 在飞行模式换 IP 后任务接着跑，这类需求常见于采集与造数。

不适合换的场景也说清楚：脚本资产已经稳稳跑在 App 自动化框架上、用例需要强停或清数据、依赖云真机平台做弹性扩容的团队，为了省一根线搬家并不划算。真正可迁移的是两个设计：用单一规格生成多端入口，以及手机主动外连加端到端加密的远程控制模型。
