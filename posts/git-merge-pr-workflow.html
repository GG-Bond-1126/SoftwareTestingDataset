Git 合并请求（MR/PR）流程：测试工程师的评审要点

环境搭建

terminal
# 安装 Git
# 配置用户
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
# 验证
git --version
terminal — 初始化仓库
mkdir my-project && cd my-project
git init
echo "hello" > test.py
git add .
git commit -m "初始提交"

基础应用：分支操作

terminal
# 创建 + 切换分支
git checkout -b dev
git commit -m "dev 修改" --allow-empty
git checkout main
git merge dev

# 查看日志
git log --oneline --graph

项目进阶：Feature 分支 + MR 流程

terminal
# Feature 分支
git checkout -b feature/login
git commit -m "feat: 用户登录" --allow-empty

# 提 MR（在 GitHub/GitLab 上）
# 评审通过后合并
git checkout main
git pull origin main
git merge --squash feature/login
git commit -m "feat: 用户登录"
git push origin main
git branch -d feature/login

MR/PR 的完整生命周期

不管用 GitLab（叫 MR）还是 GitHub（叫 PR），流程基本一样：

完整生命周期
# 1. 开发在 feature 分支完成功能
# 2. 开发提 MR/PR：feature → develop（或 main）
# 3. CI 自动触发：跑 lint、单测、构建
# 4. 测试评审：看 diff、确认影响范围
# 5. 测试跑回归（CI 上或本地）
# 6. 评审通过 + CI 通过 → 批准合并
# 7. 合并（squash / merge commit / rebase）
# 8. 合并后：CI 再跑一轮、部署、冒烟

测试工程师该看什么

看 diff（改动内容）

重点不是「代码写得好不好」（那是开发评审的事），而是「改动会影响哪些测试用例」：

  • 改了接口参数？→ 接口用例要更新；
  • 改了数据库表结构？→ 数据完整性测试要重新跑；
  • 改了前端页面？→ UI 用例的元素定位可能失效；
  • 改了配置？→ 不同环境的配置是否一致。

看提交信息（了解改动意图）

好的提交信息会写清「做了什么 + 为什么 + 影响范围」。如果信息模糊（比如「修 bug」），评审时追问开发「具体修了什么、影响哪些模块」。

看 CI 结果（有没有自动检查）

CI 的 lint、单测、构建结果是最基础的关卡。CI 挂了不能合，这是底线。但 CI 过了不代表「测试过了」——CI 跑的是开发写的测试，测试工程师要跑的是自己写的回归。

测试评审 Checklist

评审一个 MR 时，按这个清单过一遍：

测试评审 Checklist
# □ 改动范围是否清晰？（看 diff，改了哪些文件）
# □ 影响哪些测试模块？（接口 / UI / 性能 / 数据）
# □ 对应的测试用例是否已更新？（旧用例可能不适用了）
# □ 有没有新增测试？（改了功能但没加测试 = 风险）
# □ 配置变更是否同步到所有环境？（dev / test / prod）
# □ CI 是否通过？（lint + 单测 + 构建）
# □ 回归测试是否已跑？（在测试环境上）
# □ 有没有引入新的依赖？（新包、新服务）
# □ 数据库变更是否有迁移脚本？（改表结构必须有 migration）
# □ 性能影响是否评估过？（慢查询、内存泄漏）

评审不是「找茬」，是「把关」。看到明显问题就提出来，看到不确定的就追问，看到没问题的就点「批准」。三条原则：有疑点就追问，有阻塞就拒绝，没问题就放行。

怎么批、怎么拒

批准（Approve）

terminal / GitLab UI
# 在 GitLab/GitHub 上点"Approve"按钮
# 或者命令行（GitLab 支持）
# 直接在 UI 上操作最方便

批准后，CI 全绿 + 至少一人批准 → 合并按钮亮起。注意：开发者不能批准自己的 MR（多数平台强制）。

请求更改（Request Changes）

示例评论
# 在 MR 上评论（指定文件和行号）
# 文件：tests/test_payment.py，第 42 行
# 评论："这里改了金额上限从 10000 到 100000，
#        但对应的测试用例 test_max_amount 还是 10000，
#        需要同步更新，否则 CI 会假通过。"

# 或者全局评论（不针对某一行）
# 评论："改动影响支付模块，建议在预发环境跑一轮
#        性能回归（特别是大额支付场景）再合。"

拒绝（Reject / Close）

改动太大、方向不对、或者「这个功能不该在这个版本做」。在 MR 上写清拒绝原因，开发调整后重新提。

合并策略：squash、merge commit、rebase

合并时有三种策略，测试工程师要理解各自的「历史长相」：

三种策略对比
# 1. Squash（推荐：feature 分支多条提交压成一条）
# 合并前：feature 分支有 5 条提交
# 合并后：main 上多 1 条提交（5 条压成 1 条）
# 历史最干净，推荐用于"一个功能一条提交"的场景

# 2. Merge Commit（保留分叉历史）
# 合并前：feature 分支有 5 条提交
# 合并后：main 上多 6 条（5 条 + 1 条合并提交）
# 历史完整，能看清 feature 分支的演进

# 3. Rebase（线性历史）
# 合并前：feature 分支有 5 条提交
# 合并后：main 上直接多 5 条（没有合并提交）
# 历史最线性，但改写了 feature 分支的历史

测试工程师不选策略（那是团队规范），但要理解「合并后 main 上的提交变了几条」，方便用 git log 回溯。

案例：一次完整的 MR 评审

假设开发提了一个 MR：feature/pay-flow → develop，改了支付接口和测试：

terminal — 评审流程
# 1. 看 diff（在 GitLab/GitHub 上，或本地）
git diff develop..feature/pay-flow

# 2. 看改动文件清单
git diff --stat develop..feature/pay-flow
# app/controllers/payment.py | 45 +++++-
# tests/test_payment.py       | 12 +--
# config/settings.yaml        |  2 +-

# 3. 检查每个改动文件
# 控制器：新增了"大额支付"分支，改了什么？
# 测试：旧用例有没有同步更新？有没有新增用例？
# 配置：改了限额，测试环境配置同步了吗？

# 4. 在测试环境跑回归
python -m pytest tests/payment/ -v
# 假设 2 条失败：test_max_amount（用例没同步）+ test_refund（配置影响）

# 5. 在 MR 上评论
# "test_max_amount 失败：限额从 10000 改到 100000，
#  但断言还是 10000，请同步更新用例。
#  test_refund 失败：配置改了但测试环境没同步，
#  请在 config/test/settings.yaml 里也改一下。"

# 6. 开发改完重新 push，CI 重跑
# 7. 回归通过 → 批准 → 合并 → 部署 → 冒烟

MR 评审是测试工程师「把质量卡在最前面」的关键环节。在 diff 里发现问题比在回归里发现问题便宜 10 倍——「一条评审评论」 vs 「一个 Bug 工单」。
