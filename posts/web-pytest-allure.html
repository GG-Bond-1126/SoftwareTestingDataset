Playwright Agents + pytest + Allure：AI 规划-生成-自愈三合一

本地先跑通，报告才有意义

这篇只解决一件事：在你自己的机器上，让 planner、generator、healer 的产出能被 pytest 管起来、被 Allure 讲清楚。CI 怎么接、密钥怎么放、分片怎么切，那是流水线视角的事，这里不重复。先本地跑通的理由很实际——如果你连一次自愈有没有发生都看不见，把它搬进 CI 只会让问题更难查。

读者画像：已经在用 Playwright 加 pytest 写 E2E，报告要么没有、要么只有一行 passed。你想要的是一份能回答「这条用例按什么规格写的、卡在哪一步、失败那一秒长什么样、是不是 Agent 刚改过」的报告。这三件套配起来刚好能答。

先把期待校准一下。generator 产出的是 Playwright Test 的 TypeScript 用例，而你的存量是 pytest，所以本地这套骨架的定位是「pytest 做编排与报告，Agent 产出 spec 与参考实现」。两者不是同一个运行时，硬接只会在 conftest 里打架。

目录结构：四类产物各有各的家

Agent 工作流的混乱，九成来自产物乱放。定好四个目录就够了：specs/ 放人读的规划，tests/ 放 pytest 用例，prompts/ 放触发 Agent 的模板，reports/ 放一切可丢弃的产物（Allure 结果、trace、截图、自愈台账）。前三个进版本库，最后一个进 .gitignore。

这条边界要守死：reports/ 里的东西任何时刻删掉都不该影响下一次运行。反过来，如果某条结论只存在于 reports 里（比如「这条用例上周自愈过」），那它就该被提升成版本库里的文件——否则下次清理报告，证据就没了。

依赖与环境：包名别写错

Python 侧只需要两个包：pytest-playwright 提供 browser、context、page 这组 fixture 与浏览器管理，allure-pytest 提供报告适配器。网上大量文章把适配器写成 pytest-allure-adapter，这个包不存在，装不上的人会以为是网络问题。

Node 侧要装 Playwright Test 本体，因为 init-agents 是 Playwright CLI 的子命令。生成的定义文件属于工具产物，Playwright 升级后要重新生成，所以它该提交进仓库，跟着版本走。

pytest 作为编排层：交给 fixture，别自己 new_page

pytest-playwright 已经帮你做好了浏览器生命周期：browser 是 session 级，context 与 page 是函数级，每条用例拿到独立的 context，cookie 与存储天然隔离。自己写 sync_playwright().start() 再 new_page() 的后果是：并行时互相污染，失败时拿不到 trace，报告里所有用例共用一个浏览器实例。

要加的是三样东西：tracing、console 采集、失败时把证据挂进报告。tracing 一定要在 page 创建之前启动，并把 stop(path=...) 放在 fixture 的收尾里，这样即使用例断言失败，trace 也能正常落盘。request.node.rep_call 由下面那个 makereport 钩子写入，用它判断这次是不是真失败，避免把 teardown 阶段的报错误当成业务失败。

注意：pytest-playwright 自己也有 --tracing 选项，两者同时开会在第二次 start() 时报「Tracing is already started」。要么全交给插件，要么全交给 fixture，不要各管一半。

python — tests/conftest.py 浏览器与取证
import pathlib

import allure
import pytest
from allure_commons.types import AttachmentType

ARTIFACTS = pathlib.Path("reports/artifacts")


@pytest.hookimpl(hookwrapper=True, tryfirst=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    report = outcome.get_result()
    # 三个阶段的 report 都挂在 item 上，供 fixture 收尾时判断
    setattr(item, f"rep_{report.when}", report)


@pytest.fixture
def page(context, request):
    ARTIFACTS.mkdir(parents=True, exist_ok=True)
    context.tracing.start(screenshots=True, snapshots=True, sources=True)
    page = context.new_page()

    console = []
    page.on("console", lambda m: console.append(f"[{m.type}] {m.text}"))
    page.on("pageerror", lambda e: console.append(f"[pageerror] {e}"))

    yield page

    call_report = getattr(request.node, "rep_call", None)
    if call_report is not None and call_report.failed:
        trace = ARTIFACTS / f"{request.node.name}-trace.zip"
        context.tracing.stop(path=str(trace))
        allure.attach.file(
            str(trace), name="trace.zip", attachment_type=AttachmentType.ZIP
        )
        allure.attach(
            page.screenshot(), name="失败截图", attachment_type=AttachmentType.PNG
        )
        allure.attach(
            "\n".join(console) or "(无 console 输出)",
            name="console",
            attachment_type=AttachmentType.TEXT,
        )
    else:
        context.tracing.stop()

trace.zip 用 AttachmentType.ZIP 挂上去之后，点开就是 Playwright Trace Viewer，能一帧一帧看 DOM 快照与网络。AttachmentType.TEXT 用来挂 console 则不合适——它会被当成纯文本显示，长的 JSON 会糊成一片，所以 console 里只留 type 与 text，别把 location 整个对象 dump 进去。

把 spec 的步骤映射成 Allure 的 step

Allure 的层级是 feature（业务域）→ story（场景）→ step（步骤）→ attachment（证据）。这套结构与 spec 的结构几乎同构：spec 里的业务域对应 feature，场景标题对应 story，编号步骤对应 step，期望结果对应断言所在的 step。映射做对了，报告读起来就是一份带截图的验收文档；不做映射，报告里只有一个绿色的用例名。

做法分两步。第一步写个小解析器，把 Markdown 里的编号步骤与期望结果读成列表，顺带校验 spec 是否存在——spec 被删了但用例还在，是 Agent 工作流里最常见的一种漂移。第二步在用例里用 allure.step 包住每个动作，step 的标题直接取 spec 的原文，而不是自己另写一遍。

python — tools/spec_reader.py
import pathlib
import re
from dataclasses import dataclass


@dataclass
class SpecCase:
    title: str
    steps: list
    expected: list


def load_case(spec_path: str, section: str) -> SpecCase:
    text = pathlib.Path(spec_path).read_text(encoding="utf-8")
    block = re.search(
        rf"#### {re.escape(section)} (.+?)\n(.*?)(?=\n#### |\n## |\Z)",
        text,
        flags=re.S,
    )
    if block is None:
        raise LookupError(f"{spec_path} 中找不到 {section}，spec 已漂移")

    body = block.group(2)
    steps = re.findall(r"^\d+\.\s+(.+)$", body, flags=re.M)
    expected = re.findall(r"^-\s+(.+)$", body, flags=re.M)
    return SpecCase(title=block.group(1).strip(), steps=steps, expected=expected)

用例这边，allure.step 用上下文管理器包住一组动作，嵌套时会自动缩进，报告里能看到清晰的层次。断言那一步的标题建议直接拼上期望原文，失败时报告上就能看到「期望什么」与「实际什么」并排。

python — tests/test_guest_checkout.py
import allure
import pytest

from tools.spec_reader import load_case

SPEC = "specs/checkout/guest-checkout.md"
CASE = load_case(SPEC, "1.1")


@pytest.mark.smoke
@pytest.mark.agent_generated
@allure.feature("结算")
@allure.story(CASE.title)
@allure.severity(allure.severity_level.CRITICAL)
def test_guest_checkout(page, base_url):
    with allure.step(CASE.steps[0]):
        page.goto(f"{base_url}/cart")
        page.get_by_role("button", name="去结算").click()

    with allure.step(CASE.steps[1]):
        page.get_by_label("姓名").fill("张三")
        page.get_by_label("手机号").fill("13800000000")
        page.get_by_label("详细地址").fill("示例市示例路 1 号")

    with allure.step(CASE.steps[2]):
        page.get_by_role("radio", name="在线支付").check()
        page.get_by_role("button", name="提交订单").click()

    with allure.step("断言: " + CASE.expected[0]):
        order_no = page.get_by_test_id("order-no")
        assert order_no.inner_text().startswith("GUEST-")

    with allure.step("断言: " + CASE.expected[2]):
        assert page.get_by_role("button", name="提交订单").is_disabled() is False

用 get_by_role 与 get_by_label 而不是 CSS，不只是可读性问题：语义定位对 DOM 结构变化更稳，generator 生成这类定位时，healer 需要出手的概率会明显下降。

失败取证的另一半：让证据一站式可读

有了 trace、截图、console 三件套，还要解决「打开报告时先看哪个」。Allure 的附件按挂载顺序排列，所以命名要带序号：01-失败截图、02-console、03-trace.zip。人打开报告的第一眼应该是截图，确认是白屏还是弹窗，再顺着 console 看报错，最后才拖进 trace 里逐帧回放。

console 采集有个坑：page.on 只对新产生的消息生效，页面跳转后旧监听仍然有效，但如果你的 fixture 在 goto 之后才挂监听，前面所有请求日志全丢。所以监听必须在 new_page() 紧接着注册。

再补一层 environment.properties，写清浏览器版本、被测环境地址、代码版本。Allure 会自动把它渲染成报告首页的环境栏；没有这一栏，同一份报告过两周就没人说得清是在什么环境上跑的。

python — tests/conftest.py 环境信息写入
import os
import pathlib
import subprocess


def pytest_configure(config):
    results = pathlib.Path("reports/allure-results")
    results.mkdir(parents=True, exist_ok=True)
    commit = subprocess.run(
        ["git", "rev-parse", "--short", "HEAD"],
        capture_output=True, text=True,
    ).stdout.strip() or "unknown"

    lines = [
        f"Browser={os.getenv('BROWSER_NAME', 'chromium')}",
        f"BaseUrl={os.getenv('BASE_URL', 'http://localhost:3000')}",
        f"Commit={commit}",
        f"AgentSuite={os.getenv('AGENT_SUITE', 'planner+generator')}",
    ]
    (results / "environment.properties").write_text(
        "\n".join(lines), encoding="utf-8"
    )

自愈过的用例，必须在报告里显形

healer 把一条用例修绿，从流程上说是好事，从信号上说很危险：这条用例的断言可能已经被顺手改松了。所以报告里必须一眼看出「哪些用例这次是自愈过的」，并且给它单独的筛选维度，而不是混在绿色里。

做法是一个台账加一个自动标记的 fixture。healer 每改一条用例，就往 tests/healed.json 追加一条记录：用例 nodeid、时间、改了哪个定位器、谁触发的。conftest 在每条用例开始时读台账，命中就动态打上 healed 标签与 Allure tag。这样既能按标签筛选，也能在 Allure 的 tag 视图里看到自愈密度。

配套的纪律是：自愈记录只增不删，用例被人工复核确认无误后，在台账里补一个 reviewed 字段，而不是删掉那一行。删除等于销毁证据，而这条证据在事后复盘「为什么回归没抓到问题」时往往是决定性的。

python — tests/conftest.py 自愈标注
import json
import pathlib

import allure
import pytest

LEDGER = pathlib.Path("tests/healed.json")


def _healed_map() -> dict:
    if not LEDGER.exists():
        return {}
    return {row["nodeid"]: row for row in json.loads(LEDGER.read_text("utf-8"))}


@pytest.fixture(autouse=True)
def mark_healed(request):
    entry = _healed_map().get(request.node.nodeid)
    if entry is None:
        return
    request.node.add_marker(pytest.mark.healed(reason=entry["reason"]))
    allure.dynamic.tag("healed")
    allure.dynamic.parameter("自愈时间", entry["at"])
    allure.attach(
        json.dumps(entry, ensure_ascii=False, indent=2),
        name="自愈记录",
        attachment_type=allure.attachment_type.JSON,
    )

这里的取舍要讲清：给自愈用例单独打标签，会让「绿色」的数量看起来少一点，但换来的是可信。反过来，如果把自愈当成普通修复、不做任何标记，两三个月后你会得到一套没人敢信的绿色回归。宁可在报告上难看一点。

标记与分组：smoke、regression、agent_generated

分组的目的不是好看，是让「跑哪些」变成一个可组合的表达式。本地改完一个页面，只想跑冒烟与相关业务域；发版前跑全量回归；评审 Agent 生成的新用例时，只跑 agent_generated 那批。三种诉求对应三个标记，再加上 healed，四个维度基本够用。

标记必须注册在 pytest.ini 里，否则 pytest 会给一堆警告，而警告在 CI 日志里会淹没真正的错误。另外一个容易忽略的点：smoke 与 regression 是互斥的设计还是包含关系，要提前定。我倾向于互斥——冒烟是发版前十分钟必须绿的子集，回归是全量，同一条用例只挂一个，选择表达式才不会写成一团。

ini — pytest.ini
[pytest]
testpaths = tests
addopts = -q --alluredir=reports/allure-results
markers =
    smoke: 发版前必绿的子集
    regression: 全量回归
    agent_generated: Agent 生成，需人工评审后保留
    healed: 近期被 healer 修改过定位或等待

选择表达式写起来很直接：pytest -m 'smoke and not healed' 就是「冒烟里没被自愈污染的那批」。这句话能写出来，说明标记体系是健康的；如果每次都要翻文档拼表达式，说明维度设计错了。

怎么防止 Agent 生成的用例膨胀

Agent 最大的副作用是产能过剩：一次规划生成二十条用例，其中八条与存量重复，五条覆盖的是同一个表单的不同文案。三个月后用例数翻倍，运行时间翻倍，通过率没变，维护成本却压垮了唯一的负责人。

三道闸门。第一道，spec 层面去重：同一业务域下，步骤序列的指纹（步骤标题排序后取哈希）相同就算重复，规划阶段就合并。第二道，代码层面查孤儿：每条用例头部必须写 # spec: 路径#小节，没有出处的直接拒绝；反过来，spec 里的小节没有对应用例，也要报出来，防止规划写了一堆没人实现的场景。第三道，配额：单个 PR 新增用例数设上限（比如 15 条，示例值），超过就得拆 PR 并说明覆盖了什么新风险。

python — tools/fingerprint.py 规划去重与孤儿检查
import hashlib
import pathlib
import re

def fingerprint(steps: list) -> str:
    normalized = "|".join(sorted(s.strip() for s in steps))
    return hashlib.sha1(normalized.encode("utf-8")).hexdigest()[:12]


def audit() -> int:
    seen = {}
    dup = []
    for spec in pathlib.Path("specs").rglob("*.md"):
        text = spec.read_text(encoding="utf-8")
        for section, body in re.findall(
            r"#### (\d+\.\d+)[^\n]*\n(.*?)(?=\n#### |\n## |\Z)", text, flags=re.S
        ):
            steps = re.findall(r"^\d+\.\s+(.+)$", body, flags=re.M)
            fp = fingerprint(steps)
            if fp in seen:
                dup.append((spec, section, seen[fp]))
            seen[fp] = f"{spec}#{section}"

    covered = {
        m.group(1)
        for f in pathlib.Path("tests").rglob("test_*.py")
        for m in re.finditer(r"# spec: (\S+#\d+\.\d+)", f.read_text("utf-8"))
    }
    orphan_specs = [key for key in seen.values() if key not in covered]

    for spec, section, origin in dup:
        print(f"重复规划: {spec}#{section} 与 {origin} 步骤相同")
    for key in orphan_specs:
        print(f"未实现: {key}")
    return 1 if dup or orphan_specs else 0

这段脚本跑在提交前的本地钩子里，比放进 CI 更有用——生成完立刻就知道自己多写了几条重复的。等它稳定了再挪进流水线当门禁，顺序别反。

从零跑通：一条命令序列

下面这条序列假设你已经有一个能访问的测试环境，并且把 BASE_URL 配好了。顺序上有个关键点：先有 seed，再有 spec，最后才有用例。seed 是 planner 的入口，没有它，规划里会塞满「先登录」这类空话。

shell — 最小跑通路径
# 1. 用 planner 生成 specs/checkout/guest-checkout.md
#    在 AI 客户端里输入 prompts/planner.md 的内容，并附上 seed 文件

# 2. 人工评审 spec：步骤可执行、期望可断言、数据明确

# 3. 让 generator 参考 spec 产出实现（或按 spec 手写 pytest）

# 4. 只跑冒烟
pytest -m "smoke and not healed" -v

# 5. 出报告
allure generate reports/allure-results -o reports/allure-report --clean
allure open reports/allure-report

# 6. 失败后触发 healer，改动会写入 tests/healed.json
#    再跑一次，报告里能看到 healed 标签

第一步不要跳过评审。spec 是唯一能约束生成质量的文档，评审它比评审代码便宜一个数量级。第四步用 -m 过滤而不是靠目录结构，是因为同一条用例可能既属于冒烟又属于某个业务域，标签能表达多对多关系，目录不能。

常见坑：现象、原因、解法

这些坑几乎每个搭这套东西的人都踩过一遍，提前知道能省半天。

现象原因解法
Allure 里没有 trace 附件用例自己 new_page()，绕过了 fixture统一从 page fixture 拿页面
报错 Tracing is already started插件 --tracing 与手动 tracing 同时开只保留一种，删掉 addopts 里的选项
报告里附件全部丢失allure-pytest 版本与 pytest 大版本不匹配固定版本组合，升级后跑一次带附件的失败用例
Greenlet 相关异常sync_api 与 async_api 在同一进程混用整个项目只用一种 API 风格
报告只有用例名、没有步骤只写了断言，没有用 allure.step 包住动作按 spec 步骤逐个包 step
自愈过的用例看起来和正常一样healer 直接改代码，没写台账自愈脚本必须同步写 healed.json

还有两个不在表里的判断题。第一，不要为了让报告好看而把 allure.step 写得极细，一步一个点击会让报告变成操作日志，人反而找不到关键动作；按 spec 的粒度走，通常三到五步一条用例。第二，不要在用例里动态生成 step 标题（比如拼时间戳），Allure 的历史趋势会因此把同一条用例当成不同的，趋势图直接废掉。

最后是检查清单：每条用例有 spec 出处；每个 spec 小节有对应用例；失败必带截图、console、trace 三件套；自愈过的用例带 healed 标签且能在报告里筛出；environment.properties 有浏览器版本与 commit；reports/ 可以随时删。pytest -m smoke 十分钟内能绿，这套骨架就值得留下来了。
