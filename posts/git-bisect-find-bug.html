Git Bisect：用二分法找到引入 Bug 的提交

环境搭建

terminal
# 安装 Git
# 配置用户
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
# 验证
git --version
terminal — 初始化仓库
mkdir my-project && cd my-project
git init
echo "hello" > test.py
git add .
git commit -m "初始提交"

基础应用：分支操作

terminal
# 创建 + 切换分支
git checkout -b dev
git commit -m "dev 修改" --allow-empty
git checkout main
git merge dev

# 查看日志
git log --oneline --graph

项目进阶：Feature 分支 + MR 流程

terminal
# Feature 分支
git checkout -b feature/login
git commit -m "feat: 用户登录" --allow-empty

# 提 MR（在 GitHub/GitLab 上）
# 评审通过后合并
git checkout main
git pull origin main
git merge --squash feature/login
git commit -m "feat: 用户登录"
git push origin main
git branch -d feature/login

bisect 的基本原理

bisect 就是二分查找：你知道「最新是坏的」、「某条旧的提交是好的」，Git 自动取中间那一条让你测，你告诉它「好」还是「坏」，它再取下一个中间点。每次减半，log(N) 次就能定位。

前提：你有一个「好」的提交（确认功能正常的版本）和一个「坏」的提交（确认功能异常的版本）。中间有多少条提交都无所谓。

手动 bisect：逐步走一遍

假设你确认 v1.2.0 是好的（上周的 tag），main 是坏的（今天）：

terminal — 手动 bisect 完整流程
# 1. 开始 bisect
git bisect start

# 2. 标记"坏"的提交（当前 main）
git bisect bad HEAD

# 3. 标记"好"的提交（上周的 tag）
git bisect good v1.2.0

# Git 提示：Bisecting: 12 revisions left to test after this（约 4 步）
# 自动切到中间某个提交（比如 8f3a2c1）

# 4. 你在当前提交上跑测试（手动）
python -m pytest tests/test_login.py -v
# 结果：失败 → 这条提交是"坏"的
git bisect bad

# Git 又切到另一个中间提交（比如 a5b6c7d）
python -m pytest tests/test_login.py -v
# 结果：通过 → 这条提交是"好"的
git bisect good

# 继续... 大约 4~7 次后，Git 会告诉你答案：
# 提示：8f3a2c123... is the first bad commit
# 提示：commit 8f3a2c123...（标题：refactor: 重构登录接口）

# 5. 结束 bisect，回到原来的分支
git bisect reset

找到「引入 Bug 的第一条提交」后，用 git show 8f3a2c123 看它具体改了什么，再找对应开发确认。

自动化 bisect：让脚本替你判断

如果测试是自动化的（比如一条 pytest 命令就能跑），可以让 bisect 自动判断「好/坏」，全程不用你手动操作：

terminal — 自动 bisect
# 一条命令搞定：Git 自动切提交、跑测试、判断好/坏
git bisect start
git bisect bad HEAD
git bisect good v1.2.0
git bisect run python -m pytest tests/test_login.py -x --tb=line

# 自动跑完所有需要测的提交，直接给出结果：
# 提示：8f3a2c123... is the first bad commit

-x 是 pytest 的「遇到第一个失败就停」参数，配合 bisect 能省时间（不用等整条用例跑完）。

测试工程师的三个实用场景

场景一：定位「某条用例何时开始失败」

CI 上 test_checkout 突然挂了，不确定是哪次改动引入的。用 bisect 定位后，直接告诉开发「你的 8f3a2c1 改了什么导致这个」，定位时间从「天级」降到「分钟级」。

场景二：定位「数据库慢查询是哪次 SQL 改动引入」

性能测试发现某接口从 200ms 变到 2s。用 bisect 找到引入慢查询的提交，配合 git show 看 SQL 改动，快速定位。

场景三：定位「配置变更后某功能异常」

运维改了一条配置，某个功能挂了。如果配置变更有 Git 记录（比如 config.yaml 在仓库里），用 bisect 找到「第一次改坏配置」的那条提交。

bisect 的进阶技巧

限定范围

如果确定 Bug 在最近的 50 条提交里，限定范围能加速：

terminal
git bisect start
git bisect bad HEAD
git bisect good HEAD~50   # 只查最近 50 条

跳过无关提交

如果某些提交你确定和 Bug 无关（比如只改了文档），可以跳过：

terminal
git bisect skip abc123   # 跳过某条提交

用 git log 缩小范围后再 bisect

terminal — 先 log 后 bisect
# 先看最近 20 条，缩小范围
git log --oneline -20

# 找到可疑的时间点，用 commit ID 限定
git bisect start
git bisect bad HEAD
git bisect good 8f3a2c1   # 某条确定的好提交

常见错误

  • 没跑完 bisect 就 reset：白干了。bisect 过程中不要急着 reset，等 Git 给出结果。
  • 测试脚本不稳定（偶发失败）：bisect 依赖「确定性判断」，如果测试本身 flaky，bisect 结果不可信。先用稳定的测试。
  • 没标记 good 提交：bisect 不知道「好」在哪，会往无穷远处查。必须给一个确认正常的提交。

一条铁律：bisect 找的是「第一个坏的提交」，但不一定是唯一原因。可能是两个提交合在一起才触发 Bug（交互效应）。如果 bisect 指向的提交看起来没问题，扩大范围再查。
