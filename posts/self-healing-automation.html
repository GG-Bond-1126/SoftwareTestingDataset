自动化脚本自愈：执行稳定性从 70% 到 95% 的工程做法

环境搭建

terminal
# 安装 Python 3.10+
python -m venv venv
venv\Scripts\activate
pip install pytest
pytest --version

基础应用：第一个测试用例

python
def test_basic():
    assert 1 + 1 == 2
    print("基础用例通过 ✓")

项目进阶：fixture + 参数化 + CI

python
import pytest

@pytest.fixture
def data():
    return [1, 2, 3, 4, 5]

@pytest.mark.parametrize("n, expected", [(3, 6), (5, 15)])
def test_sum(data, n, expected):
    assert sum(data[:n]) == expected

传统 UI 自动化的死循环大家都熟：初期投入大 → 界面一改批量失效 → 维护量超过新增量 → 团队失去信任 → 项目搁置。

行业里对痛点有过量化描述：脚本初次创建投入巨大，界面微调或版本迭代就会造成大批量脚本失效；执行中遇到弹窗、网络抖动、页面异常极易中断；故障定位平均耗时超过 30 分钟；同时脚本高度依赖代码能力，业务人员难以参与测试设计。

自愈（self-healing）就是冲着这几条来的。

自愈的三个技术支点

  1. 智能元素定位：不再依赖固定 XPath、绝对路径或坐标，而是多特征融合识别控件。元素属性变了、DOM 结构调了，仍能定位到目标。
  2. 脚本自愈：界面微调导致定位失效时，自动更新定位路径并验证，不必人工改脚本。
  3. 智能执行与异常处理：动态决策执行策略——智能等待、智能重试、智能跳过；自动处理弹窗、广告、登录态失效；失败自动截图、录屏、留日志。

自愈的本质不是“让脚本永远绿”，而是把「环境扰动」和「产品缺陷」区分开。前者自动恢复，后者必须报出来。

公开的落地数据

Testin 云测的 XAgent 用了多智能体分工：生成 Agent 负责用例与脚本生成、自愈 Agent 处理执行扰动、错误诊断 Agent 解析日志与截图。公开报道给出的数字是：

环节改进前改进后
单条脚本生成耗时约 1 小时约 20 分钟
脚本执行稳定性行业普遍约 70%95% 以上
故障定位耗时人工平均约 30 分钟5 分钟以内

浪潮的实践案例里也有类似的闭环：脚本报错触发自愈修复智能体，自动完成错误诊断、根因分析、脚本修复，验证通过后自动重跑；再由报告生成智能体聚合结果与缺陷数据，输出标准化报告。

自愈的边界：必须留痕、必须可审

自愈最大的风险是“过度自愈”——把产品真实的异常当成环境扰动处理掉。因此至少要有四条约束：

  • 分类先行：明确区分元素变更、环境抖动、数据问题、真实业务缺陷，只有前三类允许自愈。
  • 变更留痕：每次自愈记录原定位、新定位、触发原因、证据（截图/DOM 片段），可追溯。
  • 二次确认：自愈后的路径要重跑验证，不能“改完就算过”。
  • 人工复核入口：高频自愈的元素要进入待办，推动开发修正稳定的定位标识（如 test-id）。

如果某个元素每周都在自愈，那不是脚本脆弱，而是产品缺少稳定的可测性标识。正确做法是推动开发补 test-id，而不是让自愈一直兜着。

该看的四个指标

指标含义健康信号
执行稳定性无人工干预下通过的比例持续 ≥ 95%
自愈率触发自愈后恢复成功的比例上升但不过高
误自愈率把真实缺陷自愈掉的比例必须接近 0
平均定位时长从失败到定位根因的时间逐季下降

「自愈率过高」和「误自愈率过高」一样是警报：前者说明产品可测性差，后者说明判定逻辑有问题。

落地顺序建议

  1. 先治理可测性：推动关键元素补 test-id，这是性价比最高的一步。
  2. 再引入智能定位：先覆盖高频失效的元素，不追求全量替换。
  3. 然后接自愈闭环：诊断 → 修复 → 验证 → 重跑，全链路留证据。
  4. 最后接报告与趋势：把自愈数据纳入质量看板，反向推动开发改进。

自愈能让自动化“活下来”，但让自动化“有价值”的仍然是断言设计——脚本稳定地跑过，却什么都没验证，只是把失败推迟了。
