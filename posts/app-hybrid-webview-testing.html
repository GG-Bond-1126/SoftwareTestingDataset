Hybrid 与 WebView 测试：上下文切换与 JS 桥

Hybrid 的测试难度被低估了

我们那个 App 有大促、会员、帮助中心三个板块是 H5，按页面数算大约占 38%，按用户停留时长算超过一半。自动化刚接手时，这部分用例的失败率是原生页面的 2.6 倍，最典型的一句报错是 no such element，而截图里元素清清楚楚地摆在那里。

根因几乎都一样：脚本还停在原生上下文里，只能看到 WebView 容器这一个节点。切换上下文本身不难，难的是知道什么时候切、切完等什么、以及桥接口出错时该怎么判断责任方。这篇按这四个问题展开，代码都来自实际项目。

先看清架构：原生壳、H5 与桥

Hybrid 里其实有三层被测对象，测试策略完全不同。把它们混在一起，就会出现「H5 页面用原生定位器找元素」这种低级但高频的错误。

层次典型内容定位方式谁来测
原生壳导航栏、返回、分享、容器生命周期UiAutomator2 / XCUITestApp 自动化
H5 页面表单、列表、活动页CSS 选择器 / XPath / JSApp 自动化 + 前端单测
JS 桥登录、支付、定位、相册、埋点execute_script 直接调用专项用例，重点在异常分支

实践里最容易漏的是第三层。H5 与原生之间的每一个桥方法，本质上都是一个跨语言的接口，参数类型、回调时机、异常传递都需要单独验证。很多团队把桥当成黑盒，只在 UI 上点一遍「支付成功」，结果线上出现参数为空、回调触发两次这类问题，排查时两边互相甩锅。

打开调试开关，先让 WebView 可被看见

Android 的 WebView 默认不允许远程调试，必须在代码里显式打开。正确做法是只在 debug 构建里开启，线上包绝不能带这个开关，否则任何人连上 adb 就能读取页面内容与登录态。

开关打开后，桌面 Chrome 访问 chrome://inspect 就能看到设备上的 WebView 列表，可以直接审查元素、看 console、抓网络请求。如果浏览器发现不了设备，可以用 adb 把 devtools 的 socket 转发出来，再用 DevTools 协议直连，这种方式在 CI 里更可控。

kotlin — 只在 debug 构建开启调试
import android.os.Build
import android.webkit.WebView

class MainActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        if (BuildConfig.DEBUG) {
            WebView.setWebContentsDebuggingEnabled(true)
        }
        setContentView(R.layout.activity_main)
    }
}
bash — 找到 WebView 进程并转发端口
# 1. 查看设备上所有 webview 的 devtools socket
adb shell cat /proc/net/unix | findstr webview_devtools_remote

# 输出类似：
# @webview_devtools_remote_12873

# 2. 把该 socket 转发到本机 9222
adb forward tcp:9222 localabstract:webview_devtools_remote_12873

# 3. 浏览器打开 http://localhost:9222/json 查看可调试页面
# 或直接用 chrome://inspect 的 Discover USB devices

上下文切换：时机比方法更重要

Appium 把每个 WebView 暴露成一个上下文，名字形如 WEBVIEW_com.demo.app，原生上下文固定叫 NATIVE_APP。切换只有一行代码，真正决定成败的是时机。

页面刚跳转时，driver.contexts 里往往还没有 WEBVIEW 项，因为 WebView 实例尚未创建；等它出现后立刻切过去，DOM 可能还在加载，元素依旧找不到。正确的做法是两段等待：先等上下文出现，再切过去等 document.readyState 变成 complete。我们的经验值是从点击到可操作平均 600ms，弱网下能到 3 秒，所以上下文等待给 10 秒、DOM 等待给 8 秒比较稳。

还有两个容易忽略的细节。多个 WebView 同时存在时，要按业务挑选而不是简单取最后一个，否则会切到隐藏的广告页。页面里嵌了广告或客服 SDK 时，contexts 会同时出现多个 WEBVIEW，我们按进程名与域名过滤，只切业务页面；切错的表现很隐蔽，定位不报错，但拿到的元素是广告里的同名按钮。切回原生必须放在 finally 里，一旦断言失败跳过恢复，后续用例全部受影响。

python — 可复用的上下文切换
import time
from contextlib import contextmanager


def wait_webview(driver, keyword: str = "com.demo.app", timeout: float = 10.0):
    deadline = time.time() + timeout
    while time.time() < deadline:
        for ctx in driver.contexts:
            if ctx.startswith("WEBVIEW") and keyword in ctx:
                return ctx
        time.sleep(0.3)
    raise RuntimeError(f"未发现 WebView 上下文: {driver.contexts}")


@contextmanager
def webview(driver, keyword: str = "com.demo.app", dom_timeout: float = 8.0):
    origin = driver.current_context
    ctx = wait_webview(driver, keyword)
    driver.switch_to.context(ctx)

    deadline = time.time() + dom_timeout
    while time.time() < deadline:
        state = driver.execute_script("return document.readyState")
        if state == "complete":
            break
        time.sleep(0.2)
    else:
        raise TimeoutError(f"DOM 在 {dom_timeout}s 内未就绪: {ctx}")

    try:
        yield driver
    finally:
        driver.switch_to.context(origin)

用法很直接：with webview(driver): 里写 H5 定位，出了代码块自动回到原生，即使中间抛异常也不会留下脏上下文。这个封装后来被复制到 iOS，只需要把关键字换成 WEBVIEW 与 bundle id 的组合。

H5 元素定位：CSS 优先，XPath 兜底

WebView 里的定位器和浏览器里完全一致，但有几条经验值得固定下来。第一，CSS 选择器优先，它比 XPath 快 2 到 5 倍，可读性也好。第二，优先用业务属性而不是样式类名，前端改版时 data-testid 通常不会动，而 el-button--primary 这种类名会随组件库升级消失。

第三，如果元素在 iframe 里，必须先切 frame 再定位，Appium 的 switch_to.frame 支持索引、name 和 WebElement 三种方式，用完要切回默认内容。第四，滚动要显式做，WebView 不会因为元素存在就自动滚到可视区域，点击前先 scrollIntoView。另外，H5 的页面切换没有原生转场动画，URL 变了不代表 DOM 换完了，仍然要等目标元素出现，不能只看 readyState。

python — H5 定位与滚动
from appium.webdriver.common.appiumby import AppiumBy

# 推荐：业务属性，前端承诺长期稳定
buy_btn = driver.find_element(
    AppiumBy.CSS_SELECTOR, "[data-testid='sku-A1001'] .buy-btn"
)

# 元素存在但在视口外，WebView 不会自动滚动
driver.execute_script(
    "arguments[0].scrollIntoView({block: 'center'});", buy_btn
)
buy_btn.click()

# iframe 内的元素，先切进去，处理完切回
driver.switch_to.frame(driver.find_element(AppiumBy.TAG_NAME, "iframe"))
driver.find_element(AppiumBy.CSS_SELECTOR, "#pay-confirm").click()
driver.switch_to.default_content()

JS 桥的测试点：参数、回调、异常

桥是 Hybrid 里最容易出生产事故的地方。Android 侧用 addJavascriptInterface 把原生对象挂到 window 上，H5 通过 window.JSBridge.xxx 调用；iOS 侧走 WKScriptMessageHandler。无论哪种实现，测试都要覆盖四类问题。

  • 参数校验：传 null、空串、超长字符串、特殊字符、错误类型，原生侧必须给出明确错误码，而不是崩溃或静默失败。
  • 回调时机：成功与失败回调都必须恰好触发一次。桥的常见 bug 是超时后又回调一次，导致 H5 重复跳转。
  • 异常传递：原生抛异常时要能被 H5 捕获并提示，不能让页面一直停在 loading。
  • 权限边界：未登录页面不应能调用涉及用户信息的桥方法，这是安全问题，不只是功能问题。

这些用例不需要点 UI，直接用 execute_script 调桥，速度快、断言准。下面这段先验证正常返回，再验证异常参数不会让页面卡死，最后检查回调只执行一次。

python — 直接调用 JS 桥做断言
result = driver.execute_script("return window.JSBridge.getUserInfo()")
assert result["userId"] == "10086"
assert result["vipLevel"] == 3
assert "token" not in result, "桥不应把 token 暴露给 H5"

# 异常参数：原生应返回错误码，而不是抛未捕获异常
bad = driver.execute_script(
    "try { return window.JSBridge.pay(null); }"
    "catch (e) { return {error: String(e)}; }"
)
assert bad.get("error") or bad.get("code") != 0

# 回调只允许触发一次
driver.execute_script(
    "window.__payCount = 0;"
    "window.JSBridge.pay({orderId: 'P20261123001', amount: 1999},"
    "  function(res){ window.__payCount += 1; window.__payResult = res; });"
)
driver.execute_script("return window.__payResult")
count = driver.execute_script("return window.__payCount")
assert count == 1, f"支付回调触发了 {count} 次"

注意 execute_script 的返回值必须是可序列化的 JSON，原生对象、函数、undefined 都会变成 null。调试时如果发现返回值永远是空，先确认 JS 里有没有写 return，这是最常见的误会。

H5 与原生数据同步

登录态同步是最典型的场景：用户在原生登录，进入 H5 却要求重新登录，或者退出登录后 H5 里的 token 还在。这类问题的根因通常是三套存储各说各话：原生存 SharedPreferences，H5 读 localStorage，Cookie 又是另一份。

我们的约定是单一事实来源放在原生，H5 启动时通过桥拉一次用户信息，写入自己的内存态，不落 localStorage。退出登录时原生主动调用 H5 的清理方法，同时清 Cookie。验证方式是在切换上下文后直接读存储，再和原生侧的值比对，而不是只看页面显示。

python — 登录态一致性断言
with webview(driver):
    cookie = driver.execute_script("return document.cookie")
    token = driver.execute_script("return localStorage.getItem('access_token')")
    assert "session_id=" in cookie
    assert token is None, "H5 不应把 token 落到 localStorage"

    user = driver.execute_script("return window.__APP_USER__")
    assert user["userId"] == "10086"

# 原生侧退出登录后，H5 存储必须同步清空
driver.find_element(AppiumBy.ID, "mine_logout").click()
with webview(driver):
    assert driver.execute_script("return document.cookie") == ""
    assert driver.execute_script("return window.__APP_USER__") is None

WebView 内登录与支付的坑

登录方面，最常见的三个坑是：Cookie 没有同步到 WebView，导致 H5 一直未登录；onPageFinished 触发时 JS 还没执行完，注入的用户信息被覆盖；以及在 H5 里点击登录跳回原生后，回退时 WebView 缓存了旧页面。处理方式分别是：登录成功后主动 CookieManager.flush()；注入时机改到 onPageCommitVisible 或在 H5 侧回调；返回时调用 reload() 而不是依赖缓存。

支付更麻烦。H5 拉起微信或支付宝通常用自定义 scheme，WebView 默认会报 ERR_UNKNOWN_URL_SCHEME，必须由原生拦截并转交系统。测试时要覆盖三种情况：已安装对应 App、未安装、安装但版本过低。另外，支付结果页往往依赖 onPageFinished 后的轮询，如果 H5 在 iframe 里跑第三方收银台，跨域限制会让 JS 桥直接失效，这种场景只能靠原生回调或服务端通知兜底。

还有一个小但很坑的点：H5 里的文件上传控件 input type=file 会唤起系统选择器，自动化无法直接操作。需要提前在原生侧实现 onShowFileChooser 的测试钩子，或者改用接口造数据绕过上传流程。

最后一点值得单独断言：支付完成后 H5 与原生必须拿到同一个订单状态。我们见过 H5 显示成功、原生订单列表还是待支付的组合，根因是桥回调只传了展示文案，没有回传订单号与状态码。验证时不要只看成功页，切回原生再查一次订单详情，两边状态对不上就是 bug。

踩坑与边界

症状：切到 WEBVIEW 后所有定位都超时，但 chrome://inspect 能看到页面正常。原因：页面在 iframe 里，顶层 document 只有一个空的 iframe 节点。处理：先列出所有 frame，再逐个切换尝试，找到包含目标元素的那个，用完切回默认内容。

症状：调试开关打开了，Chrome 里却看不到设备。原因：WebView 的调试开关在进程启动时才生效，热更新或动态加载的 WebView 可能没走到那段代码；也可能是数据线只供电不传数据。处理：确认构建类型是 debug、换线、执行 adb devices 看设备是否 authorized，必要时重启 App 进程。

症状：同一段 JS 在浏览器里返回对象，在 Appium 里返回 null。原因：execute_script 只能序列化 JSON 兼容的值，DOM 节点和函数都会被丢弃。处理：在 JS 里先把结果转成普通对象或 JSON 字符串，再 return。

症状：iOS 16.4 以上设备，driver.contexts 永远只有 NATIVE_APP。原因：从 iOS 16.4 起 WKWebView 默认不可检查，必须显式把 isInspectable 设为 true，否则 WebKit 不暴露调试端口，Appium 也就枚举不到 WEBVIEW 上下文。处理：创建 WKWebView 后设置该属性，且仅限 debug 构建，线上包保持关闭。

Hybrid 测试的核心不是把 H5 当成黑盒点一遍，而是清楚地知道每个动作发生在哪一层、数据在哪一层落地。上下文、DOM 就绪、桥的回调，这三件事都有明确的等待条件和断言方式，写进封装里，团队里谁写用例都不会再踩同样的坑，这比多写一百条用例更有价值。
