大模型评测：评测集、指标与 LLM 裁判

评测最容易做假的地方，是用一个平均分决定上线。我们曾经拿着 4.6 分的总评去评审，老板问了一句「退款场景怎么样」，一查，P0 的 18 条用例里挂了 5 条。平均分没有骗人，它只是把最要命的部分平均掉了。

这篇文章讲一套能扛住追问的评测体系：评测集怎么建、指标怎么算、LLM 裁判怎么校准、结果怎么分层看。代码可以直接跑，指标口径都写清楚，避免「我们的准确率 92%」这种没法比较的结论。

为什么平均分会骗人

我们那个问答系统每天的调用里，82% 是闲聊和通用咨询，18% 是订单、退款、发票这类业务问题。评测集如果按线上流量比例采样，通用问题会占绝大多数，模型在这些问题上表现好，平均分自然高。但业务方真正在意的，恰恰是那 18%。

更隐蔽的问题是 用例难度分布。同一个模型，在简单改写题上准确率 94%，在需要跨文档推理的题上只有 61%，一平均就是 85%，看着很体面。所以我们的第一条原则是：先分层，再算分；分层不通过，总分没有意义。

改造后我们把评测结果按 P0、P1、P2 三档拆开，任何一次发版必须满足 P0 零失败、P1 通过率不低于 90%、P2 只做趋势记录。执行半年，线上严重问题从每月 3.2 起降到 0.3 起。

评测集怎么建

评测集是这套体系里最贵的资产，也是最容易被糊弄的。我们从三个来源按 5:3:2 的比例混合，每一条都带标注规范，不允许「看着还行」这种判定。

来源占比获取方式作用
真实问题50%线上日志脱敏后分层抽样保证分布贴近真实
边界构造30%多轮追问、超长输入、空答案、跨文档压出模型的能力边界
线上失败回流20%差评、转人工、人工复核标记防止同一个坑踩两次

每条用例至少包含六个字段：id、场景、优先级、问题、参考答案要点、判定规则。判定规则是关键，它规定了什么算通过。比如退款类问题，规则写的是「必须包含退款时限与到账方式，允许措辞不同」，而不是「与参考答案一致」。

规模上不要迷信大。我们 620 条用例，跑一次全量 9 分钟、花费约 11 元，团队愿意每天跑。如果搞到 5000 条、跑一次一小时，就没人会跑，评测集等于不存在。先做到 300 条覆盖 P0，再慢慢长。

四个必须算清楚的指标

指标不在多，在于每个都能回答一个具体问题。下面四个是我们固定上报的口径，缺一个都会被追问。

指标定义回答什么问题我们的基线
准确率判定通过的用例数 / 总用例数整体对不对P0 需 100%
召回率该答的题里，实际答出来的比例有没有大量拒答偷懒不低于 92%
通过率按场景加权的通过比例业务方视角的可用度P1 不低于 90%
Kappa裁判与人工标注的一致性扣除随机因素评测结论可不可信不低于 0.6

准确率和召回率必须一起看。只报准确率，模型可以通过疯狂拒答把准确率刷到 99%；只报召回率，模型可以通过乱答把召回刷满。两个一起看，才逼着模型在该答的时候答对。

Kappa 是很多人忽略的指标。它衡量的是「扣除瞎猜也能对的那部分之后，真实一致程度」。两个标注员一致率 85% 听着不错，但如果类别只有两类、分布又极不均衡，Kappa 可能只有 0.3，说明这份标注基本不可用。

评测脚本：逐用例落盘，才能算翻转率

评测脚本有两个硬要求：一是每条用例结果必须落盘，包含模型原始输出和判定依据；二是判定逻辑要可追溯，失败必须能说清是「没答出来」还是「答错了」。只有落盘了，才能算翻转率、才能做版本对比。

python · eval/run_eval.py
import json
import os
import time
from pathlib import Path
from openai import OpenAI

client = OpenAI(api_key=os.environ["LLM_API_KEY"],
                base_url=os.environ["LLM_BASE_URL"])
MODEL = os.environ.get("EVAL_MODEL", "deepseek-chat")

def judge_case(case: dict, output: str) -> tuple[bool, str]:
    if not output.strip():
        return False, "empty_output"
    if output.strip() in ("不知道", "无法回答"):
        return False, "refused"
    for kw in case.get("must_include", []):
        if kw not in output:
            return False, f"missing:{kw}"
    for bad in case.get("must_exclude", []):
        if bad in output:
            return False, f"forbidden:{bad}"
    return True, "ok"

def main(cases_path: str, tag: str) -> None:
    cases = [json.loads(line) for line in
             Path(cases_path).read_text(encoding="utf-8").splitlines() if line.strip()]
    rows = []
    for case in cases:
        t0 = time.time()
        resp = client.chat.completions.create(
            model=MODEL, temperature=0,
            messages=[{"role": "user", "content": case["question"]}],
        )
        output = (resp.choices[0].message.content or "").strip()
        passed, reason = judge_case(case, output)
        rows.append({
            "id": case["id"], "scene": case["scene"], "p": case["priority"],
            "passed": passed, "reason": reason, "output": output,
            "latency_ms": int((time.time() - t0) * 1000),
        })
    out = Path(f"reports/{tag}.jsonl")
    out.parent.mkdir(exist_ok=True)
    out.write_text("\n".join(json.dumps(r, ensure_ascii=False) for r in rows),
                   encoding="utf-8")
    p0 = [r for r in rows if r["p"] == "P0"]
    print(f"total={len(rows)} pass={sum(r['passed'] for r in rows) / len(rows):.1%} "
          f"p0_fail={sum(not r['passed'] for r in p0)}")

if __name__ == "__main__":
    main("cases/eval_v3.jsonl", "baseline-20261120")

有了每一版的结果文件，翻转率就是一次集合运算。我们只看两个数：fixed（基线失败本次通过）和 broke（基线通过本次失败）。发布评审时，broke 列表里每一条都要有人解释。

Kappa：判断评测结论可不可信

Kappa 的算法不复杂，难的是把它用在对的地方。我们用它做两件事：验证两名标注员是否一致、验证裁判模型与人工是否一致。低于 0.6 就不能拿这份标注下结论，必须回去改判定规则或重新培训。

python · eval/kappa.py
from collections import Counter

def cohen_kappa(rater_a: list[str], rater_b: list[str]) -> float:
    if len(rater_a) != len(rater_b) or not rater_a:
        raise ValueError("两列标注长度必须一致且非空")
    n = len(rater_a)
    po = sum(1 for x, y in zip(rater_a, rater_b) if x == y) / n
    ca, cb = Counter(rater_a), Counter(rater_b)
    labels = set(ca) | set(cb)
    pe = sum((ca[l] / n) * (cb[l] / n) for l in labels)
    if pe == 1:
        raise ValueError("全部标注同标签，Kappa 无定义")
    return round((po - pe) / (1 - pe), 3)

if __name__ == "__main__":
    human = ["pass", "fail", "pass", "pass", "fail", "pass"]
    judge = ["pass", "fail", "pass", "fail", "fail", "pass"]
    print("Kappa =", cohen_kappa(human, judge))  # 0.615

实操建议：不要用 1 到 5 分的原始分算 Kappa，先粗化成三档（不合格 / 勉强 / 合格）再算。五分制里 4 分和 5 分的区别非常主观，直接算会把一致性拉得很低，但业务上这两档其实都可以接受。

LLM 裁判的偏见与校准

用 GPT-4o-mini 这类模型当裁判，成本是人工的百分之一，但有三种稳定的偏见，不校准就会把评测带偏。

位置偏见：成对比较时，放在前面的答案平均得分高 0.2 到 0.3 分。处理方法是交换顺序各评一次，取平均，或者干脆改成单答案绝对评分，不给对照。

长度偏见：裁判偏爱长答案，哪怕信息量一样。我们在裁判 Prompt 里明确写「不要因为更长而加分」，并且在评分后做一次相关性检查，如果分数与长度的相关系数超过 0.5，说明这条裁判规则失效了。

自我偏好：用 A 模型评 A 模型的输出会偏袒。裁判模型必须和被测模型不同家，这是硬约束。

python · eval/calibrate_judge.py
import json
from eval.kappa import cohen_kappa

def bucket(score: int) -> str:
    return "bad" if score <= 2 else ("ok" if score == 3 else "good")

def calibrate(samples_path: str) -> dict:
    rows = [json.loads(l) for l in open(samples_path, encoding="utf-8")]
    human = [bucket(r["human_score"]) for r in rows]
    judge = [bucket(r["judge_score"]) for r in rows]
    kappa = cohen_kappa(human, judge)
    # 长度偏见：分数与输出长度的相关系数
    import statistics as st
    xs = [len(r["output"]) for r in rows]
    ys = [r["judge_score"] for r in rows]
    mx, my = st.mean(xs), st.mean(ys)
    cov = sum((x - mx) * (y - my) for x, y in zip(xs, ys))
    r = cov / (len(xs) * st.pstdev(xs) * st.pstdev(ys))
    return {"n": len(rows), "kappa": kappa, "len_corr": round(r, 3)}

if __name__ == "__main__":
    print(calibrate("cases/judge_calibration.json"))

我们的校准集 120 条，人工打三档，裁判打五分制再粗化。第一次跑 Kappa 是 0.41，几乎不可用；改了裁判 Prompt、加了评分锚点示例之后到 0.68，才敢让它参与 P2 的日常评测。P0 永远人工判定，不交给裁判。

分层看结果：P0 是红线，不是指标

分层不是把结果拆开看，而是把决策规则也拆开。我们的规则写在发布流程里，不是口头约定。

层级范围判定发布影响
P0涉及金额、退款、隐私、法律条款人工判定，逐条签字一条失败即阻断
P1主要业务路径规则断言 + 裁判通过率低于 90% 阻断
P2通用咨询、闲聊规则断言只记录趋势

为了让「P0 零失败」可持续，我们把 P0 用例控制在 60 条以内，每条都能在 30 秒内人工判定。P0 一旦膨胀到 200 条，人工评审就会变成点通过，规则形同虚设。

不要用平均分对外汇报。我们对内也只看分层结果，唯一会看的总数是「P0 失败数」和「P1 通过率」。平均分只在做月度趋势时出现，且必须附上分层数据。

用 DeepEval 和 Ragas 补语义指标

规则断言能覆盖事实和格式，覆盖不了「答得切不切题」「忠于不忠于检索内容」。这部分我们用 DeepEval 的 faithfulness 和 answer relevancy，Ragas 作为交叉验证，两边差异超过 0.15 就人工看。

python · eval/deepeval_smoke.py
from deepeval.metrics import FaithfulnessMetric, AnswerRelevancyMetric
from deepeval.test_case import LLMTestCase

def score_semantic(question: str, answer: str, contexts: list[str]) -> dict:
    case = LLMTestCase(input=question, actual_output=answer,
                       retrieval_context=contexts)
    faith = FaithfulnessMetric(threshold=0.7, model="gpt-4o-mini")
    relev = AnswerRelevancyMetric(threshold=0.7, model="gpt-4o-mini")
    faith.measure(case)
    relev.measure(case)
    return {"faithfulness": round(faith.score, 3),
            "answer_relevancy": round(relev.score, 3),
            "faith_reason": faith.reason[:120]}

Ragas 那侧我们只跑一个最小对照，确认同一批样本的 faithfulness 不在两个工具间来回跳：

python · eval/ragas_crosscheck.py
from datasets import Dataset
from ragas import evaluate
from ragas.metrics import faithfulness

def ragas_faithfulness(rows: list[dict]) -> float:
    ds = Dataset.from_list([{
        "question": r["question"],
        "answer": r["answer"],
        "contexts": r["contexts"],
    } for r in rows])
    result = evaluate(ds, metrics=[faithfulness])
    return round(float(result["faithfulness"]), 3)

这类库的价值是省掉写裁判 Prompt 的时间，不是替你定义什么叫好。阈值、样本、场景权重，仍然得自己定。

接到发布流程

评测作业挂在发版流水线上，与单测并列。流程是：模型或 Prompt 变更触发全量评测，生成结果文件，自动与上一版做 diff，输出 fixed / broke 两个列表，最后按分层规则给出放行或阻断。

有个细节很救命：结果文件按日期和 commit 命名，保留最近 30 次。出问题时能回看「这个问题是哪次发版引入的」，不用靠人回忆。我们靠这个机制定位过一次由分词器升级引起的中文标点丢失，只花了 20 分钟。

踩坑与边界

坑一：评测集和线上分布脱节。早期评测集全是同事自己编的题，措辞规整、意图明确，模型考了 93 分，线上真实用户口语化提问只有 71 分。后来强制 50% 来自线上日志，分数掉到 84，但这才是真实水平。

坑二：裁判换模型不重测。裁判从 gpt-4o-mini 换成另一个便宜模型，分数整体上浮 0.4 分，团队以为模型变好了。换裁判等于换尺子，必须重跑校准集，Kappa 达标才能用。

坑三：用例一次判死。模型输出有随机性，同一条用例跑三次可能两过一挂。我们的规则是关键用例跑三次取多数，非关键用例跑一次；稳定性低于 80% 的用例单独标记，不进阻断。

坑四：只看通过率不看翻转。某次发版总通过率从 88% 涨到 90%，但 broke 列表有 14 条，其中 3 条是 P0 相关的语义漂移。总账变好掩盖了局部退化，所以翻转率必须单独看。

指标改造前改造后

一句话总结：评测体系的价值不在于那个分数，而在于它能不能在发版前告诉你哪一条红线被踩了。能回答这个问题，评测就是资产；答不了，评测就是一份好看的 PPT。
