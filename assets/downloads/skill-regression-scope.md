# 回归范围分析：从改动到用例选择

## 硬性约束（优先级最高，与其他章节冲突时以本节为准）

1. 只能依据三类信息输出：用户提供的需求文档 / 接口文档 / 代码 / 日志原文、当前会话上下文、本 skill「输入」一节所列的文件。禁止凭想象补充业务规则、字段名、接口地址、阈值、状态码、版本号或历史数据。
2. 每条产出都要可回溯，必须标注来源：文档章节或条款、文件路径与行号、日志片段、接口字段。标不出来源的条目不得进入正式产出。
3. 信息不足时不许编造填补。缺失项一律进入「待确认清单」，逐条写清：缺什么、影响哪条结论、需要谁提供。
4. 凡是基于经验补出的内容，必须以「推断：」开头，并写明依据与置信度（高 / 中 / 低）。置信度为低的推断不能当结论用。
5. 禁止虚构引用：不编造文档条款号、版本号、链接、指标数值、报错原文。引用原文时逐字摘录并注明位置。
6. 资料互相矛盾时（文档与代码不一致、两处规则冲突）不要自行取舍，把两种说法并列，标明冲突点和需要确认的问题。
7. 输出前逐条自检：这条有来源吗？没有就移到「待确认清单」。自检不通过不许输出。

## 待确认清单（输出必带）

无论信息是否充足，输出末尾都保留这一节；没有待确认项时写「无」，不许省略该节。每行格式：

| 序号 | 缺失或不确定的内容 | 影响 | 需要谁提供 |

## 适用场景

- 每次发版前要靠人拍脑袋决定跑哪些用例，经常漏测。
- 全量回归要 6 小时，跑不完，只能砍用例，但砍得没有依据。
- 微服务拆分后，一个改动影响哪些下游服务说不清。
- 需要把回归范围结论落成可执行的 pytest 标记，而不是一张口头清单。

以下情况不要用：

- 改动集中在纯配置或文案，没有代码逻辑变化。
- 依赖关系图本身缺失且短期内无法补齐，此时先补图再做范围分析。
- 发布窗口极紧且改动风险极高，应直接全量回归。

## 输入

必需：

1. git diff，包含基线分支与目标分支，建议用三点比较。
2. 依赖关系图，至少包含模块到接口、接口到表、服务到服务的调用关系。
3. 用例清单，包含用例编号、覆盖模块、优先级、历史失败率。

建议补充：

4. 近 90 天缺陷分布，含模块与根因分类。
5. 变更说明或 PR 描述，用于校正模型对改动意图的理解。
6. 上次回归的耗时数据，用于评估取舍空间。

输入缺失时：依赖图缺失的部分按「未知影响」处理，默认全选该模块用例，不要默认跳过。

## 上下文与历史文档规范

本节规定每次调用前要准备哪些材料、怎么截取、历史文档放在哪里。材料不齐时按「输入缺失」处理，不要用经验补。

### 本次任务需要的材料

| 材料 | 必需 | 截取范围 | 格式 |
| --- | --- | --- | --- |
| 代码改动 | 是 | 三点 diff，保留全部 hunk，剔除锁文件、生成物与纯格式化文件 | unified diff，首行写基线分支与目标 commit |
| 接口变更清单 | 是 | 只保留新增、删除、字段变更的接口，最多 60 条 | 表格：方法 / 路径 / 变更类型 / 关联模块 |
| 依赖关系 | 是 | 模块到接口、接口到表、服务到服务，最多两跳 | 表格或 YAML，注明导出时间与版本 |
| 历史缺陷分布 | 是 | 近 90 天，按模块与根因聚合到条数 | 表格：模块 / 根因分类 / 次数 / 最近一次日期 |
| 上次回归结果 | 建议 | 只取失败用例、跳过用例与分模块耗时 | 表格：用例编号 / 结果 / 耗时 / 失败原因 |
| 用例清单 | 是 | 只保留编号、模块、优先级、历史失败率四列 | CSV 或 Markdown 表 |

截取规则：

1. 单轮材料总长控制在 20000 字以内，超出时按模块拆成多轮，每轮只处理一个模块。
2. diff 超过 600 行时，先给文件级统计，再对受影响模块给函数级 hunk。
3. 每份材料第一行写来源标记，格式为：来源：相对路径 | 版本或 commit | 导出时间。
4. 不要贴整个仓库目录树，只给两跳以内的目录。

### 历史文档怎么挂

固定目录如下，根路径按自己的仓库替换：

- qa-ai-context/regression-scope/
  - current/
    - diff.patch：三点 diff，基线为 release/2026.10
    - api-changes.md：本次接口变更清单
    - deps.yaml：依赖图导出，含版本与导出时间
    - case-index.csv：用例编号、模块、优先级、历史失败率
    - task.md：发版说明、改动意图、发布窗口与可用回归时长
  - history/
    - regressions/
      - 2026-10-28.md：上次回归的范围、耗时、失败与漏测
      - 2026-10-14.md：上一次回归
      - index.md：历次回归索引，含版本、耗时、漏测条数
    - defects/
      - 2026-Q3.csv：近 90 天缺陷，含模块与根因分类
      - rootcause-taxonomy.md：根因分类口径
    - deprecated/
      - deps-2025.yaml：旧依赖图，仅作对比
      - api-2024.md：旧版接口文档，禁止作为依据

引用与维护规则：

1. 引用格式：结论里写相对路径加小节名，例如 history/regressions/2026-10-28.md 第 2 节；不要写「上次的经验」这类无法核对的来源。
2. 回归记录只读最新三份。更早的记录只用于统计漏测趋势，不能作为本次跳过用例的理由。
3. 上次跳过且通过的用例，不能因为「上次也没事」再次跳过；改动不同，依据必须重新取。
4. 过时文档放进 deprecated，首行写：状态：已过期 | 失效版本：2026.07 | 替代文件：current/deps.yaml。skill 不得引用，除非用户明确要求做版本对比。
5. 冲突裁定：current 与 history 冲突以 current 为准；current 内部冲突以代码与接口文档为准；仍然冲突时把两种说法并列，写进待确认清单。

## 执行步骤

1. 解析 diff，提取变更文件、变更函数、涉及的接口路径与数据库表名。
2. 按依赖图向上找调用方，向下找被调用方，得到一跳与两跳影响面。
3. 用历史缺陷分布加权，最近有缺陷的模块提高优先级。
4. 把受影响模块映射到用例集，逐条标注必测、可选中、可跳过。
5. 给每条可跳过用例写明理由，理由必须来自依赖图或历史数据，不接受「感觉不会影响」。
6. 输出结论后用规则做一次交叉检查：有代码改动的模块不允许整体跳过。
7. 生成 pytest 标记文件与命令行，交给 CI 直接执行。
8. 上线后统计漏测情况，把漏测用例补进必测集并回写依赖图。

## 输出格式

1. 影响面摘要：改动文件数、涉及接口数、涉及表数、受影响模块列表。
2. 用例决策表：用例编号、模块、决策（必测/可选/跳过）、理由。
3. 风险提示：依赖图缺失、跨服务调用未覆盖、数据变更不可逆。
4. 执行命令：pytest 标记表达式，或带用例列表的文件路径。

结论必须能落到命令，只给文字结论视为未完成。

## 质量检查清单

- 每个改动文件都能映射到至少一个模块，没有未归属文件。
- 每个涉及的表都有对应的数据校验用例。
- 可跳过用例占比不超过 40%，超过说明依赖图或历史数据不可信。
- 每条跳过理由可追溯到具体证据，例如「该接口无调用方，依赖图 v3 确认」。
- 生成的 pytest 命令能直接执行，标记名与用例库一致。
- 风险提示不为空，至少列出一条不确定性。
- 漏测复盘有记录，且对应规则已更新。

## 反例

- 只看改了哪些文件，不看谁调用了这些文件，导致下游服务漏测。
- 把「改动很小」当成跳过理由。
- 跳过理由写成「开发说没问题」。
- 生成的标记文件里混入已删除的用例编号，pytest 直接报错。
- 依赖图三个月没更新，仍然拿来当唯一依据。
- 只输出一张模块清单，没有用例级决策，执行阶段仍然靠人挑。
