# 业务测试用例生成：从需求到可执行用例

## 硬性约束（优先级最高，与其他章节冲突时以本节为准）

1. 只能依据三类信息输出：用户提供的需求文档 / 接口文档 / 代码 / 日志原文、当前会话上下文、本 skill「输入」一节所列的文件。禁止凭想象补充业务规则、字段名、接口地址、阈值、状态码、版本号或历史数据。
2. 每条产出都要可回溯，必须标注来源：文档章节或条款、文件路径与行号、日志片段、接口字段。标不出来源的条目不得进入正式产出。
3. 信息不足时不许编造填补。缺失项一律进入「待确认清单」，逐条写清：缺什么、影响哪条结论、需要谁提供。
4. 凡是基于经验补出的内容，必须以「推断：」开头，并写明依据与置信度（高 / 中 / 低）。置信度为低的推断不能当结论用。
5. 禁止虚构引用：不编造文档条款号、版本号、链接、指标数值、报错原文。引用原文时逐字摘录并注明位置。
6. 资料互相矛盾时（文档与代码不一致、两处规则冲突）不要自行取舍，把两种说法并列，标明冲突点和需要确认的问题。
7. 输出前逐条自检：这条有来源吗？没有就移到「待确认清单」。自检不通过不许输出。

## 待确认清单（输出必带）

无论信息是否充足，输出末尾都保留这一节；没有待确认项时写「无」，不许省略该节。每行格式：

| 序号 | 缺失或不确定的内容 | 影响 | 需要谁提供 |

## 适用场景

- 需求评审通过，需要把需求点与业务规则展开成可执行的业务（功能）用例。
- 老模块补回归用例，已有历史用例需要对齐颗粒度，避免重复造。
- 新人或外包接手模块，需要一套不依赖口口相传、照着自己就能跑完的用例。
- 需求变更后，需要按当前生效版本重写受影响场景的用例。

以下情况不要用：

- 只需要评审覆盖、不写执行步骤，应使用测试点生成 skill。
- 需要写接口契约、字段边界、状态码断言、幂等校验，属于接口测试用例 skill。
- 性能、安全、兼容性等专项测试，应使用对应专项 skill。
- 需求本身还没评审，输入里大量写着「待确认」，应先做需求拆解。

## 输入

必需：

1. 需求点清单，每条含需求编号、角色、触发条件、期望结果。
2. 业务规则表，每条含规则编号、判定条件、结果、例外与优先级。
3. 页面流程，含页面名称、入口、跳转条件、返回路径、角色可见性。
4. 引用清单，逐条写清用途、文件路径与章节，只允许引用清单内的内容。

建议补充：

5. 数据字典，含字段名、类型、取值或枚举、单位、默认值、脱敏要求。
6. 历史用例的编号、标题、模块与优先级，用于去重和颗粒度校准。
7. 近半年该模块的历史缺陷，归到根因分类并统计次数。
8. 文档清单 INDEX.md，标明当前生效版本与废弃文档替代关系。

输入缺失时：不猜、不补，缺口写进「待确认清单」；可以输出草稿，但必须在草稿开头说明哪些场景因缺料无法覆盖。

## 执行步骤

1. 先读引用清单与 INDEX.md，确认当前生效版本，列出本次实际引用的路径与章节。
2. 按需求编号分组，一个需求点一组；组内先主流程，再规则分支，最后异常与权限。
3. 每条用例绑定一个需求编号和至少一个业务规则编号；绑不上的场景不写进正式产出。
4. 前置条件写到账号角色、数据状态、环境与开关，保证脱离其他用例也能独立复现。
5. 步骤按「页面 → 控件 → 动作」组织，每步只做一个动作，页面名与控件名使用界面可见文案。
6. 测试数据写具体值；金额、时间、状态类数据写清构造方式或来源。
7. 预期结果只写可观察的现象：页面文案、状态变化、站内信或短信、单据状态，不写接口字段与状态码。
8. 用历史用例做去重，同一前置条件 + 同一动作 + 同一预期视为重复，保留信息更全的一条。
9. 用历史缺陷根因做反向补漏，同一根因至少对应一条用例。
10. 标注每条用例的来源，来源写到文件路径加章节；标不出来源的移入待确认清单。
11. 输出前按「质量检查清单」逐条自检。

## 输出格式

输出一张 Markdown 表格，列固定且顺序不可调整：

| 编号 | 模块 | 场景 | 前置条件 | 步骤 | 测试数据 | 预期结果 | 优先级 | 关联需求 | 来源 |

字段要求：

1. 编号：TC-模块缩写-需求序号-两位序号，例如 TC-ORD-014-02，模块内连续不跳号。
2. 模块：与需求模块名一致，例如 订单-退款。
3. 场景：一句话写清角色、条件与目标，不超过 40 字。
4. 前置条件：账号角色、数据状态、环境与开关，用分号分隔，不写点击动作。
5. 步骤：每步一个动作，用分号分隔，格式为 页面名 + 控件名 + 动作。
6. 测试数据：具体值，禁止出现「有效」「合法」「正常」「合理」这类形容词。
7. 预期结果：可观察、可判定的现象，不写 HTTP 状态码、JSON 字段、数据库字段值。
8. 优先级：只取 P0 / P1 / P2。涉及资金、权限、不可逆状态变更的 P0；主流程与核心规则的 P1；展示、文案、排序的 P2。
9. 关联需求：需求编号 + 规则编号，例如 F-ORD-014 / R-ORD-07。
10. 来源：文件路径加章节，例如 docs/requirements/order/v1.4/rules.md 第 2.1 节。

表格之后输出两段：

1. 覆盖说明：按需求编号统计用例条数，列出没有用例的需求点。
2. 待确认清单：按硬性约束保留该节，没有条目时写「无」。

不要输出接口断言、字段级校验、状态码说明；也不要输出调用脚本。

## 质量检查清单

- 每条用例都绑定需求编号和至少一个业务规则编号，没有孤立用例。
- 前置条件可独立构造，不写「接上一条用例」。
- 步骤里每个动作都指明页面与控件名称，不熟悉业务的人能照着执行。
- 测试数据是具体值，没有「有效」「合法」「正常」「合理」这类词。
- 预期结果可观察、可判定，没有「显示正确」「功能正常」这类结论。
- 全表没有接口字段断言、JSON 结构校验、HTTP 状态码校验。
- 覆盖至少主流程、规则分支、异常、权限四类，异常路径不为零。
- 同一前置条件与动作的重复用例已合并，编号连续。
- 每条都有来源，或已进入待确认清单。
- 待确认清单存在，且与正文一致。

## 反例

- 步骤写「进入订单页正常下单」，没有入口路径和控件名，新人无法执行。
- 测试数据写「有效手机号」「随机金额」「稍后重试」，无法复现。
- 预期结果写「下单成功，数据正确」，执行时无法判定通过还是失败。
- 在业务用例里写「断言 code=200，data.orderId 非空」，把两类用例混成一条。
- 一条用例塞进五个场景，失败后无法定位是哪个规则出问题。
- 直接抄历史用例，不核对当前版本规则，把已下线的入口写进前置条件。
- 需求没写清的地方自己编一条规则，不留待确认，评审时才被发现。
- 优先级全填 P1，等于没有优先级，冒烟子集无法裁剪。
