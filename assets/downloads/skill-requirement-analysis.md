# 需求拆解：从 PRD 到可测需求点

## 硬性约束（优先级最高，与其他章节冲突时以本节为准）

1. 只能依据三类信息输出：用户提供的需求文档 / 接口文档 / 代码 / 日志原文、当前会话上下文、本 skill「输入」一节所列的文件。禁止凭想象补充业务规则、字段名、接口地址、阈值、状态码、版本号或历史数据。
2. 每条产出都要可回溯，必须标注来源：文档章节或条款、文件路径与行号、日志片段、接口字段。标不出来源的条目不得进入正式产出。
3. 信息不足时不许编造填补。缺失项一律进入「待确认清单」，逐条写清：缺什么、影响哪条结论、需要谁提供。
4. 凡是基于经验补出的内容，必须以「推断：」开头，并写明依据与置信度（高 / 中 / 低）。置信度为低的推断不能当结论用。
5. 禁止虚构引用：不编造文档条款号、版本号、链接、指标数值、报错原文。引用原文时逐字摘录并注明位置。
6. 资料互相矛盾时（文档与代码不一致、两处规则冲突）不要自行取舍，把两种说法并列，标明冲突点和需要确认的问题。
7. 输出前逐条自检：这条有来源吗？没有就移到「待确认清单」。自检不通过不许输出。

## 待确认清单（输出必带）

无论信息是否充足，输出末尾都保留这一节；没有待确认项时写「无」，不许省略该节。每行格式：

| 序号 | 缺失或不确定的内容 | 影响 | 需要谁提供 |

## 适用场景

- 需求评审会前一天，需要把 PRD 拆成可讨论、可分配的结构。
- PRD 只有原型图和零散描述，业务规则、状态流转、字段口径都没写清。
- 需要把结果直接交给测试点生成环节，避免二次理解造成偏差。
- 老系统改造，需要先摸清现有规则与本次改动的差异。

以下情况不要用：

- 纯文案、图片、样式调整，没有可验证的业务规则变化。
- 需求已冻结、用例已完整覆盖，只剩补执行数据。
- 支付清结算等强合规场景且没有领域专家复核，此时 AI 只做初稿索引，不做结论。

## 输入

必需：

1. PRD 原文，Markdown、飞书文档导出文本或直接粘贴均可，需包含目标、主流程、字段说明。
2. 一句话业务背景，例如「会员日发券，目标是提升复购」。
3. 上下游系统清单，例如订单、库存、支付、消息。

建议补充：

4. 近半年历史缺陷列表，包含模块与问题描述。
5. 现有接口文档或数据库字段说明。
6. 术语表，统一口径，避免「优惠券」与「券码」混用。

输入缺失时：先按已有信息产出，把缺失项写进待确认问题，不要自行编造业务规则。

## 上下文与历史文档规范

### 本次任务需要的材料

| 材料 | 截取哪一部分 | 贴入方式 | 全文还是摘要 |
| --- | --- | --- | --- |
| PRD 原文 | 目标、主流程、规则、字段说明的全部章节 | 按原文章节顺序粘贴，保留标题层级 | 全文 |
| 上下游系统清单 | 与本需求有交互的系统及接口名 | 一行一个系统，注明调用方向 | 全文 |
| 历史需求 | 同模块最近 3 个版本的变更记录 | 只贴变更段落与影响范围 | 摘要 |
| 历史缺陷 | 近半年同模块缺陷 | 标题、根因分类、严重级别、发生次数，去掉复现步骤 | 摘要 |
| 接口文档 | 本次改动涉及的字段与错误码 | 按接口逐个粘贴字段表 | 只贴相关段落 |
| 线上数据 | 涉及规则的量级与分布 | 总量、占比、峰值 | 摘要 |

执行要求：

1. PRD 必须给全文，不能只给改动章节。规则之间存在引用关系，缺章节会导致模型把其他章节的约束当成不存在。
2. 历史缺陷只给根因分类与次数，不给复现步骤，避免模型照抄单个历史 bug。
3. 代码与日志只在判断现状时提供，且必须注明「这是现状，不是需求」，否则模型会把现有实现当成应然行为。
4. 单轮材料超过 8000 字时按章节拆成多轮，先通读全文，再追加接口文档与缺陷摘要，最后提出拆解要求。

### 历史文档目录约定

```text
docs/
  requirements/
    coupon/
      v2.3/
        prd.md
        change-log.md
      v2.2/
        prd.md
  defects/
    2026H1/
      coupon.md
  _archive/
    [已废止]-coupon-prd-v1.8.md
```

1. 需求文档路径为 `docs/requirements/{模块}/v{版本}/prd.md`，变更记录放同目录 `change-log.md`。
2. 历史缺陷按半年度归档，路径为 `docs/defects/{年度}{H1 或 H2}/{模块}.md`。
3. 确认不再使用的文档移入 `docs/_archive/`，文件名前加 `[已废止]`，首行写明被哪一版替代、从哪天起失效。

### 引用与冲突

1. 引用格式统一为《文档名》v版本 §章节，例如《会员日发券 PRD》v2.3 §3.2；没有行号的文档只写章节标题。
2. 同一规则有多个版本时，以版本号最大且状态为已评审的为准，其余版本只用于对比差异。
3. 文档与代码不一致时，两者并列写入歧义列表，不改写任何一方；代码只作为现状证据，不作为需求依据。
4. 线上行为与文档冲突时，先记入待确认清单，由产品确认是文档漏更新还是线上有缺陷，不由模型裁定。
5. 标注 `[已废止]` 的文档只能用于追溯历史决策，不能作为规则来源；引用时必须写明它已被哪一版替代。

## 执行步骤

1. 通读 PRD，标注三类句子：出现数字的、出现「可以」「不允许」的、出现状态变化的。
2. 按功能点、业务规则、约束、数据字典四类归档，一条只归一类，避免重复。
3. 每条需求点写成「条件 + 动作 + 结果」，保证可以被验证。
4. 对每条规则追问四件事：边界在哪、异常怎么走、权限差异是什么、并发下会怎样。
5. 把 PRD 中互相矛盾或未定义的地方抽到歧义列表，每条给出两种可能的解释。
6. 把必须由产品确认的问题抽到待确认问题，附上影响范围，方便会上直接问。
7. 输出 JSON，字段严格按输出格式，不增加自定义字段。
8. 对照质量检查清单自检，任一项不通过则回到第 2 步重做。

## 输出格式

先给一段不超过 100 字的结论，说明 PRD 完整度、主要风险、建议评审重点。

再给 JSON，结构如下：

```json
{
  "feature_points": [
    {"id": "F-01", "name": "领取优惠券", "actor": "会员", "trigger": "点击领取按钮", "result": "账户新增一张未使用券"}
  ],
  "rules": [
    {"id": "R-01", "desc": "同一用户同一活动每天最多领取 1 张", "type": "limit"}
  ],
  "constraints": [
    {"id": "C-01", "desc": "券面额不得大于订单金额的 50%"}
  ],
  "data_dictionary": [
    {"field": "coupon_status", "type": "enum", "values": ["unused", "used", "expired"], "required": true}
  ],
  "ambiguities": [
    {"id": "A-01", "point": "退款后券是否退回", "options": ["原路退回", "不退回"]}
  ],
  "questions": [
    {"id": "Q-01", "question": "券过期前是否需要提前一天提醒", "impact": "影响定时任务与消息模板"}
  ],
  "missing_branches": [
    {"id": "M-01", "branch": "库存不足时领券", "suggestion": "明确失败文案与是否允许重试"}
  ]
}
```

结论之后不要输出 JSON 以外的解释文字，避免下游解析失败。

## 质量检查清单

- 每个功能点都有唯一 ID，格式为 F-两位数字。
- 每条规则都能用一个具体输入判断真假，不接受「合理」「友好」这类描述。
- 每个枚举字段列出全部取值，而不是只有正常与异常两种。
- 歧义不少于 3 条，少于 3 条通常说明拆得不够细。
- 每条待确认问题都写明影响范围，写不出影响说明问题不重要。
- 缺失分支至少覆盖：空值、越权、重复提交、并发、超时。
- 输出 JSON 能通过 jsonschema 校验，且没有多余字段。

## 反例

- 把「用户体验更好」写成需求点，没有可验证结果，等于没写。
- 自行补全业务规则，例如 PRD 没写退款是否退券，就直接写成「退款后原路退回」。
- 一条需求点塞三个动作，例如「领取、扣库存、发消息」，失败时无法定位是哪个环节。
- 字段只写「字符串」，不写长度、枚举值、是否必填。
- 输出中文键名，例如用「功能点」替代 feature_points，下游脚本无法直接消费。
- 把历史缺陷里已经修好的问题当成新规则写进 rules。
