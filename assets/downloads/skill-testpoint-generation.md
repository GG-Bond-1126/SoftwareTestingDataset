# 测试点生成：从需求点到测试场景

## 硬性约束（优先级最高，与其他章节冲突时以本节为准）

1. 只能依据三类信息输出：用户提供的需求文档 / 接口文档 / 代码 / 日志原文、当前会话上下文、本 skill「输入」一节所列的文件。禁止凭想象补充业务规则、字段名、接口地址、阈值、状态码、版本号或历史数据。
2. 每条产出都要可回溯，必须标注来源：文档章节或条款、文件路径与行号、日志片段、接口字段。标不出来源的条目不得进入正式产出。
3. 信息不足时不许编造填补。缺失项一律进入「待确认清单」，逐条写清：缺什么、影响哪条结论、需要谁提供。
4. 凡是基于经验补出的内容，必须以「推断：」开头，并写明依据与置信度（高 / 中 / 低）。置信度为低的推断不能当结论用。
5. 禁止虚构引用：不编造文档条款号、版本号、链接、指标数值、报错原文。引用原文时逐字摘录并注明位置。
6. 资料互相矛盾时（文档与代码不一致、两处规则冲突）不要自行取舍，把两种说法并列，标明冲突点和需要确认的问题。
7. 输出前逐条自检：这条有来源吗？没有就移到「待确认清单」。自检不通过不许输出。

## 待确认清单（输出必带）

无论信息是否充足，输出末尾都保留这一节；没有待确认项时写「无」，不许省略该节。每行格式：

| 序号 | 缺失或不确定的内容 | 影响 | 需要谁提供 |

## 适用场景

- 需求点清单已经评审通过，需要转成可评审的测试点，而不是直接写用例。
- 老模块补测试，只有零散用例，需要先补齐检查项。
- 用例评审前，需要一张能快速扫完的测试点总表。
- 回归范围分析完成后，需要针对受影响的模块补充测试点。

以下情况不要用：

- 需求点本身还没评审，输入里还写着「待确认」，此时应先做需求拆解。
- 只需要补执行步骤，检查项已经确定。
- 性能、安全等专项测试，应使用对应专项 skill。

## 输入

必需：

1. 需求点清单，包含功能点、规则、约束、数据字典，字段与需求拆解输出一致。
2. 业务规则表，至少包含规则编号、触发条件、结果。
3. 目标模块所属业务域，例如交易、营销、会员。

建议补充：

4. 近半年该模块的历史缺陷，含缺陷描述与严重级别。
5. 现有测试点或用例编号，用于去重与关联。
6. 线上流量占比，用于排优先级。

输入缺失时：在输出末尾单独列出「输入不足导致覆盖不全的部分」，不要跳过方法不写。

## 上下文与历史文档规范

### 本次任务需要的材料

| 材料 | 截取哪一部分 | 贴入方式 | 全文还是摘要 |
| --- | --- | --- | --- |
| 需求点清单 | 本次模块的功能点、规则、约束、数据字典 | 按功能点分组粘贴，保留 F- / R- / C- 编号 | 全文 |
| 业务规则表 | 规则编号、触发条件、结果 | 原表粘贴，不改写措辞 | 全文 |
| 历史缺陷 | 近半年同模块缺陷的根因分类与次数 | 一行一条，附严重级别 | 摘要 |
| 历史用例库 | 同模块的编号、标题、前置条件 | 只要这三列，用于去重 | 摘要 |
| 线上流量占比 | 各功能点访问占比与失败率 | 给百分比，不给明细日志 | 摘要 |
| 接口错误码 | 与本次规则相关的错误码及含义 | 只贴相关错误码 | 只贴相关段落 |

执行要求：

1. 一次只喂一个功能点或一个模块的 20 到 30 条，禁止把整份 PRD 一次性贴入。
2. 历史用例超过 300 条时先按标题关键词粗筛，只贴筛后的 50 条，避免上下文被稀释。
3. 缺陷描述只保留根因与次数，去掉复现步骤，防止模型复述单个缺陷。
4. 线上流量占比用于排优先级，缺失时不得自行假设占比，写入待确认清单。

### 历史文档目录约定

```text
qa/
  testcases/
    coupon/
      v2.3/
        case-index.md
      legacy/
        [已废止]-case-2025.md
  testpoints/
    coupon/
      v2.3/
        tp.md
  defects/
    2026H1/
      coupon.md
```

1. 用例索引路径为 `qa/testcases/{模块}/v{版本}/case-index.md`，只保留编号、标题、前置条件三列。
2. 测试点表路径为 `qa/testpoints/{模块}/v{版本}/tp.md`，版本号与需求点文件保持一致。
3. 停止维护的用例库移入 `legacy/`，文件名前加 `[已废止]`，不参与去重。

### 引用与冲突

1. 测试点必须写关联需求，引用格式为需求编号加版本，例如 F-01@v2.3。
2. 历史用例只用于去重和回归范围参考，引用时写《用例索引》v2.3 #TC-118。
3. 同一检查项在两个版本中描述不同时，以最新评审版为准，旧版写进去重记录的合并来源。
4. 无法判断哪一版有效时，两条都保留并写入待确认清单，不自行删除。
5. 标注 `[已废止]` 的用例库不参与去重，避免把废弃检查项重新拉回正式产出。

## 执行步骤

1. 按功能点分组，一组内先写主流程测试点，再写规则与约束测试点。
2. 对每个有取值范围的字段套等价类与边界值，边界取最小、最小减一、最大、最大加一。
3. 对多条件组合的规则画判定表，条件数不超过 4 个时做全组合，超过 4 个时用正交表并说明取舍。
4. 对有状态字段的场景画状态迁移图，列出合法迁移、非法迁移、重复迁移。
5. 每条规则补异常分支：空值、超长、类型不符、越权、重复提交、并发。
6. 用历史缺陷做反向检查，同一个原因导致的缺陷必须至少对应一条测试点。
7. 生成编号后去重，判定标准是「同一前置条件 + 同一操作 + 同一预期」视为重复。
8. 按模块统计方法分布，任一方法为 0 时说明覆盖有缺口，回到第 2 步补。

## 输出格式

输出一张 Markdown 表格，列固定为：

| 编号 | 模块 | 测试点 | 方法 | 优先级 | 关联需求 |

编号规则：TP-功能点序号-两位序号，例如 TP-01-03。

表格之后输出两段：

1. 覆盖度自查：按方法统计条数，列出缺失的方法。
2. 去重记录：合并了哪些编号，合并原因。

不要输出执行步骤、测试数据、预期结果的详细描述，这些属于用例阶段。

## 质量检查清单

- 每个功能点至少 3 条测试点，其中至少 1 条异常。
- 每个有范围的字段都有边界值测试点，且明确写了边界取值。
- 判定表条件覆盖率不低于 90%，未覆盖的组合写明原因。
- 有状态字段必须覆盖非法迁移，例如已过期券再次使用。
- 权限相关功能必须有越权测试点，且区分不同角色。
- 并发测试点写明并发量与判定标准，例如 50 并发只允许成功 1 次。
- 每条测试点都能对应到一个需求编号，没有孤立测试点。
- 去重后编号连续，无跳号。

## 反例

- 测试点写成「测试优惠券功能正常」，没有前置条件和预期，无法评审。
- 只写正向流程，异常分支全部靠执行时临场想。
- 边界值只写「最小值」，不写最小减一。
- 把用例步骤塞进测试点，例如「打开页面，点击领取，输入手机号」，粒度过细。
- 为了凑数量把同一检查项换个说法写三遍，去重时全部被合并。
- 优先级全填 P1，等于没有优先级。
